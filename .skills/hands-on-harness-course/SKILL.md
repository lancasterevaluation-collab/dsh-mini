# Skill: hands-on-harness-course（超详解技术教材生成 playbook）

> **目标**：把源码/设计转化成教材，标准是「**读者读完后能关掉文档从零重写**」（L3），不是「读者觉得有道理」（L1）。
> **立场**：**教材的质量由"读者能做到什么"衡量，不由"写了多少字"衡量**；但达到 L3 需要极高密度，所以字数自然很大（单篇 80–140 KB 是正常值）。
> **正文语言**：中文；**代码、标识符、路径、命令、术语保留英文**。

## 何时用

- 要为一套已有源码写"逐行讲解"式教程
- 要把一门课从"概览版"升级到"能独立复现版"
- 要为新写的模块产出配套教材

## 核心判据：五级能力

每一篇都必须声明目标级别，并给出对应的验收方式。

| 级别 | 判定 | 验证方式 |
|---|---|---|
| **L1 读懂** | 能解释这段代码**为什么**这么写 | 合上文档口述 3 分钟 |
| **L2 改动** | 能按需求改一处，知道牵连什么 | 改完通过已有验收判据 |
| **L3 重建** | **关掉文档**从零写出这个部件 | 写完通过全部演示 |
| **L4 设计** | 为没见过的需求选对扩展点 | 说出"挂在哪、为什么、代价是什么" |
| **L5 评审** | 判断别人的设计对不对 | 给陌生代码指出分层问题 |

**L3 是分水岭。** 能读不等于能写；"学完不会做"几乎全部卡在这里。
**默认目标：每个核心部件达到 L3。**

## 流程

### Phase A · 事实化（写任何字之前）

1. **读源码全文**，而不是凭印象。记下行数与文件清单。
   - 反例（本 skill 创立时的真实失误）：凭记忆写"289 行"，实际是 419 行。
2. **核对每个数字**：行数、阈值、默认值、输出片段。
3. **跑一遍演示**，把真实输出抄进文档（不许编造输出）。
4. **列缺口**：这个模块**没有**解决什么？留给后面哪一步？

### Phase B · 结构（16 节，缺一不可）

| # | 节 | 内容契约 |
|---|---|---|
| 1 | **元信息** | 文件+行数 / DSH 或上游对应 / 目标级别 / 预计阅读与动手时间 |
| 2 | **本篇新词** | 本篇首现术语 + 一句话 + **"为什么必须懂"** |
| 3 | **第 0 节 · 成品预览** | 做出什么 / 运行什么样 / 在课程中的位置 |
| 4 | **第 0.5 节 · 系统视角** | 位置图 + 下游依赖表（带依赖强度）+ **三个连锁影响分析** |
| 5 | **L0 要解决的问题** | 上一步留下的**具体缺陷**，带现象、报错原文、"何时爆炸" |
| 6 | **L1 设计与原理** | 为什么这么设计；关键概念；替代方案的对比 |
| 7 | **L2 决策表** | 决策 × 选择 × 替代方案 × **代价落在谁身上** |
| 8 | **L3 实现（逐行讲解）** | 完整代码 + 逐行/逐块解释（见下方铁律） |
| 9 | **L4 运行与验证** | 运行命令、输出**逐条解读**、验收判据表 |
| 10 | **L5 语法速查** | 本篇出现的**全部**语言语法 + 易踩规则 |
| 11 | **L6 关文档重写判据** | 按 ★ 分级要写什么 + 卡住时问自己什么 + 分级判定 |
| 12 | **L7 挑战题** | **不给答案**的设计题（4–6 道） |
| 13 | **L8 自检清单** | 理解/实现/语法/系统四层，逐条打勾 |
| 14 | **L9 仍未解决** | 分两类：后续会解决的 / **当前实现的真实缺陷** |
| 15 | **L10 提问训练** | 五个问题层次 + 五种模板 + 本篇 12 个好问题 + **问题升级练习** |
| 16 | **L11 系统影响回溯** | 重看第 0.5 节：哪些预判被推翻；通向下一步的桥 |

### Phase C · 三条贯穿机制

| 机制 | 形式 | 训练什么 |
|---|---|---|
| **停下来想一想** | 散布在 L1/L2/L3 末尾的提问块，**不给答案** | 主动加工 |
| **先问再答** | 给出我们的选择**之前**先问"你会怎么选？" | 设计判断力 |
| **问题升级** | 把模糊问题改写成精确问题的练习 | 提出好问题的能力 |

### Phase D · 质量门（每篇完成前逐条自检）

- [ ] 源码行数、输出片段、数字**全部核对过**，无编造
- [ ] L3 的代码块与真实文件**一字不差**
- [ ] 每段代码后都有"做什么 + 为什么 + 不这样会怎样"
- [ ] 第 0.5 节有 ≥3 个连锁影响分析
- [ ] L9 有 ≥3 个**真实缺陷**（不是"以后会做"，而是"现在就是不够好"）
- [ ] L5 语法速查覆盖本篇**全部**新语法
- [ ] L6 有 ★ 分级判据和"卡住问自己什么"
- [ ] L10 有 ≥10 个本篇引出的问题，分 L3/L4/L5 三层
- [ ] 单篇 ≥ 80 KB（低于说明讲得不够细）

### Phase E · 交付与迭代

1. 先写一篇**作为标杆**，让用户确认密度与风格
2. 确认后按顺序批量推进，每轮 1–2 篇（密度决定速度上限）
3. **采纳读者的问题**：读者提出的问题如果暴露了设计缺口，**改设计并记录这个过程**（见下方红线 3）

## 写作铁律

### 铁律 1 · 逐行讲解

**代码块必须与真实文件一字不差**，然后逐行/逐块解释三件事：

```
这段在做什么  +  为什么这么写  +  不这么写会怎样
```

**不要只讲"关键代码"。** 读者卡住的地方往往是"我以为我懂了"的那几行。

**每种语言构造第一次出现时，就地解释它的语法**，不要默认读者知道。

### 铁律 2 · 系统视角

**每篇都必须回答**：改错这里会炸到哪几步？

三个必备要素：

| 要素 | 形式 |
|---|---|
| 位置图 | 在整体架构中的坐标 |
| 下游依赖表 | 产物 × 消费者 × 用途 × **依赖强度（🔴强/🟡弱/🟢可选）** |
| 连锁影响分析 | **≥3 条**"改动 → 传导 → 后果"链，**优先选"不报错只变差"的那类** |

### 铁律 3 · 缺陷要坦白

L9 必须列出**当前实现的真实缺陷**，每一条写清：

```
缺陷描述  +  后果  +  修法  +  当初为什么这么选
```

**不要写"以后会做"来冒充缺陷。** 缺陷是"现在这里就是不够好"。

### 铁律 4 · 术语三层兜底

新词栏 + 正文首现解释 + 术语表兜底。**缺一层即不合格。**

术语表条目格式：`白话解释` + `没有它会怎样` + `首次出现于第几步`。

### 铁律 5 · 提问训练

**每篇必须**：
- 教读者区分问题层次（事实 / 机制 / 设计 / 系统 / 科研）
- 给 5 种提问模板
- 列 12 个本篇引出的问题（分三层）
- 给一个"问题升级"练习（模糊 → 精确，附提升点说明）

---

## 红线

1. **不编造数字与输出**。任何数字要么核对过源码，要么标注"待核实"。宁可留空。
2. **不把"讲清楚"当终点**。L1 达标不算完成，**L3 才是默认目标**。
3. **读者的提问优先于原计划**。如果读者的一个问题暴露了设计缺口，**改设计**，并把"问题 → 缺口 → 修正"的过程写进文档。这是本 skill 最有价值的机制。
4. **不为凑字数注水**。密度来自"每个变量、每行代码、每个决策都讲透"，不是来自重复。
5. **不隐藏失败**。写文档过程中发现自己之前的错误（记错行数、公式写错），**必须在文档里更正并记录**。

## 输入

| 输入 | 必需 | 说明 |
|---|---|---|
| 源码文件 | ✅ | 要讲解的模块，读全文 |
| 可运行演示 | 推荐 | 跑一遍，把真实输出抄进文档 |
| 上游参照物 | 推荐 | 真实生产系统的对应实现（用于对照） |
| 读者画像 | ✅ | 默认"零基础 + 有科研需求" |
| 单篇字数下限 | 默认 80 KB | 低于此值说明密度不够 |

## 输出

`docs/NN-<英文名>.md`，每篇 80–140 KB，遵守 Phase B 的 16 节结构。

配套三份常驻文档：

| 文档 | 作用 |
|---|---|
| `glossary.md` | 术语表（三层兜底的第 3 层） |
| `README.md` | 规范与进度表 |
| `00-graduation.md` | 能力矩阵与毕业标准 |
