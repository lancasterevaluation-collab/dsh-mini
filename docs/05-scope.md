## 本篇新词

> 全部术语在 [`glossary.md`](glossary.md)。先花 60 秒扫一遍。

| 词 | 一句话 | 为什么必须懂 |
|---|---|---|
| **scope（作用域）** | 一个隔离区域：域内提供的东西只有域内看得见 | 让不同 agent 用不同配置 |
| **isolation（隔离）** | scope 要达到的效果：两边互不干扰 | 并行做 A/B 实验的前提 |
| **shadowing（遮蔽）** | 内层提供的东西盖住外层的同名东西 | 作用域生效的机制 |
| **lookup chain（查找链）** | 查找时"先局部、后全局"的顺序 | 决定遮蔽是否生效 |
| **局部层 / 全局表** | 两层服务存储：前者私有、后者共享 | 本步的全部内容 |
| **叠加（additive）** | 新能力是"多加一层"，不是"替换旧层" | 好分层的标志 |

### 下游：谁在用作用域隔离

| 第 5 步的产物 | 谁消费 | 用来做什么 | 依赖强度 |
|---|---|---|---|
| `isolate()` | 第 7 步（每个会话的工具集）、第 8 步（每个 agent 的配置） | 让不同 agent 看到不同能力 | 🔴 强 |
| 局部层查找 | 第 6 步的 agent 预设 | 按预设覆盖服务 | 🔴 强 |

| `ownerOf` 的"（局部）"标注 | 调试 | 区分局部与全局 | 🟢 可选 |

**注意第三行** —— 这是**与你的科研直接相关的**：

> **没有作用域隔离，并行实验根本无法进行** —— 一改就是全局改，实验组和对照组会互相污染。

### 连锁影响分析

#### 连锁 1：如果局部层不检查重名

```
isolate('tools', A) 可以重复调用 → 同一个容器里塞两份 tools
   ↓
后面那个覆盖前面那个（Map.set 语义）
   ↓
★ 前面那份永远查不到，也无法单独撤销 ★
   ↓
如果撤销顺序不对：撤销后一个 → 前面那个"复活"
   ↓
★ 服务的行为在看代码时无法预测 ★
```

**所以 `isolate` 只检查自己的局部层是否重名** —— 加了检查就避免了"隐式覆盖"。

**注意它不检查祖先** —— 因为**遮蔽祖先是它的目的**。

#### 连锁 2：如果查找顺序反了（全局优先）

```
查找：先全局，命中就返回；没有才看局部
   ↓
isolate('tools', 只读) 之后，get('tools') 仍返回全局的全量
   ↓
★ 遮蔽完全失效 ★
   ↓
但不会报错 —— 你只会觉得"为什么我的 isolate 没生效？"
```

**这是"沉默失效"**：功能写了、不生效、且无错误提示。

**正确顺序是"局部优先"** —— 这是 CSS、JavaScript 作用域、模块解析的通用语义：**内层覆盖外层**。

#### 连锁 3：如果 `#local` 也做成共享的

```
把 #local 和 #registry 一样在构造函数里继承
   ↓
所有容器共用一张局部表
   ↓
agent1.isolate('tools', 只读) 之后，agent2 也看到只读
   ↓
★ 隔离彻底失效 —— 而且比第 3 步的"全局"更糟 ★
```

**更糟在哪**：全局表至少还是"大家一样"的诚实语义；而**共享的"局部"表**会让 `ownerOf` 报出误导性信息（"agent1（局部）"但 agent2 也能看到）。

**所以 `#local` 声明处那行注释必须写明"不共享"**：

```ts
/**
 * 第 5 步新增：本容器**局部**提供的服务（只对本容器及其子树可见）。
 * 注意它**不共享** —— 每个容器有自己的局部层，这是作用域隔离的载体。
 */
```

**它和第 3、4 步的所有其他共享字段完全相反**，不标出来一定会被误读。

### 现在该建立的三个习惯

| 习惯 | 做法 | 训练什么 |
|---|---|---|
| **扩展时问"是加一层还是改一层"** | 优先加一层（旧的作兜底） | 保持向后兼容 |
| **遮蔽类功能要问"谁优先"** | 内层优先是通用语义 | 语义一致性 |
| **给"反直觉的字段"加注释** | 和其他字段相反的，必须标出来 | 降低误读成本 |

### 0.1 第 4 步留下的具体缺陷：**一切都是全局的**

第 3 步为了"插件之间能协作"，把服务放进了**全树共享的命名空间**。这在单 agent 场景没问题，但一旦出现"多个 agent 并存"，立刻爆炸。

## L1 设计与原理

### 1.1 隔离的两个层次

| 层次 | 问题 | 我们的做法 |
|---|---|---|
| **服务隔离** | 同一个服务名，不同 agent 看到不同的值 | ✅ **本步实现** |
| **事件隔离** | 同一条事件，只在某个作用域内触发监听器 | ❌ **不做**（见 1.6） |

**先做服务隔离**，因为它是"不同 agent 不同工具集"的直接答案。

### 1.2 查找链：从一层变成两层

#### 第 3、4 步的查找

```
ctx.get('tools')
   │
   └─ 全局注册表  ← 唯一路径
```

#### 第 5 步的查找

```
ctx.get('tools')
   │
   ├─ ① 沿容器树向上找「局部层」  ← 命中就返回，不再往下走
   │      自己 → 父 → 祖父 → … → root
   │
   └─ ② 全局注册表               ← 兜底
```

**这就是"遮蔽"（shadowing）：局部那层把全局那层盖住了。**

```
        root（全局：tools = 全量工具集）
          │
    ┌─────┴─────┐
    ▼           ▼
 agent1      agent2
 tools=只读    tools=读写        ← 各自局部的 tools，盖住全局的
```

#### 为什么是"沿树向上"而不是"只看自己"

**因为要支持继承**。演示 4 验证了：

```
--- agent1 的孙子看到（继承）---
["read_file"]
```

**孙容器自己没有 `isolate('tools')`，但它沿树向上找到了 `agent1` 的。**

**这符合"作用域"的直觉**：内层能看见外层的，反之不行。

#### 查找的完整代码

```ts
get<T>(name: string): T | undefined {
  // 第 5 步：先沿容器树向上找「局部层」—— 命中就返回，不再往下走
  for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
    if (node.#local.has(name)) return node.#local.get(name) as T
  }
  // 再回落到全局注册表
  const entry = this.#registry.get(name)
  return entry === undefined ? undefined : (entry.value as T)
}
```

**注意 `for` 循环的三段结构**：

```ts
for (let node: Context | undefined = this; node !== undefined; node = node.#parent)
//   ────────────┬───────────         ─────┬─────         ─────────┬────────
//          起点是自己                 终止条件              沿父链上移
```

**这是"沿树向上遍历"的标准写法。**

**为什么不用递归？**

```ts
const findLocal = (ctx: Context | undefined): unknown | undefined => {
  if (ctx === undefined) return undefined
  if (ctx.#local.has(name)) return ctx.#local.get(name)
  return findLocal(ctx.#parent)
}
```

**可以，但它要作为类的方法**（因为要访问 `#local` 和 `#parent`），**而且每次多一层函数调用**。

**`for` 循环版本更紧凑。**

### 1.3 `isolate` 与 `provide` 的分工

| 方法 | 写哪里 | 可见范围 | 重名检查 |
|---|---|---|---|
| `provide(name, value)` | 全局注册表 | **全树** | 全局表里是否已有 |
| `isolate(name, value)` | 本容器局部层 | **本容器及其子树** | **只看自己** |

**最关键的区别在最后一列**：

```ts
// provide：全局唯一 → 重名报错
if (this.#registry.get(name) !== undefined) throw new Error(`服务重复注册：...`)

// isolate：只检查自己的局部层 → 允许遮蔽
if (this.#local.has(name)) throw new Error(`本作用域已有局部服务 "${name}"`)
```

**为什么 `isolate` 不检查全局表？** 因为**遮蔽全局正是它的用途**。

**为什么 `isolate` 要检查自己的局部层？** 因为**同一容器里塞两份同名局部服务是纯粹的混乱**。

**所以规则是**：

> **同一层内不允许重名，层与层之间允许遮蔽。**

**这条规则在 CSS（同选择器的规则合并 vs 不同优先级覆盖）、模块系统（`import` 遮蔽外层变量）里都成立。**

### 1.4 遮蔽的四种情形

| 情形 | 例子 | 结果 |
|---|---|---|
| **遮蔽全局** | `agent1.isolate('tools', 只读)` | agent1 看到只读，root 看到全量 |
| **兄弟互不影响** | agent1 和 agent2 各 isolate | 互不干扰 |
| **向下继承** | agent1 的孙子 | 继承 agent1 的局部 |
| **遮蔽祖先的局部** | 孙子自己 isolate | 覆盖 agent1 的（**越近越赢**） |

**"越近越赢"是查找链的直接推论** —— `for` 循环从 `this` 开始向上走，**第一个命中的就是最近的**。

### 1.5 为什么这是「叠加」而不是「改写」

**这一节是全篇的核心论证。**

第 3 步的 1.8 节我写过：

> **局部层是"可选的额外层"，不是替换全局层。**
> **所以第 3 步的代码在第 5 步只需要"加一条查找路径"，不需要重构。**
> **这是好分层的标志 —— 扩展是叠加，不是改写。**

**现在验证这句话：**

| 改动 | 类型 |
|---|---|
| 加 `#local` 字段 | **纯新增** |
| 加 `isolate()` 方法 | **纯新增** |
| `get` 加一个 `for` 循环 | **前置插入** |
| `has` 加一个 `for` 循环 | **前置插入** |
| `serviceNames` 收集两层 | **扩展** |
| `ownerOf` 加一个 `for` 循环 | **前置插入** |

**没有一处改动了原有逻辑**：

```ts
// 原有逻辑（原样保留）
const entry = this.#registry.get(name)
return entry === undefined ? undefined : (entry.value as T)
```

**它只是从"唯一路径"变成了"兜底路径"。**

#### 如果第 3 步设计得不好会怎样

**假设第 3 步是这么写的**：

```ts
provide(name, value) { this.#services.set(name, value) }
get(name) { return this.#services.get(name) }     // ← 存储和查找同一张表，没有"兜底"的概念
```

**那么第 5 步要**：

1. 把 `#services` 拆成两层
2. 改所有读写它的地方
3. 想清楚"往哪写"的语义

**这是重构，不是扩展。**

| | 好设计（第 3 步） | 坏设计（假设版） |
|---|---|---|
| 存储 | 全局注册表（明确的"共享层"） | 一个笼统的 `#services` |
| 语义 | "这是**全局**命名空间" | "这是服务表" |
| 加局部层 | **在前面插一层** | 拆表 + 改语义 |

**关键差别是第 3 步的注释里那句**：

```ts
/**
 * @param name 服务名，**全树唯一**
 */
```

**"全树唯一"这四个字明确了它的定位** —— 它是**共享层**，不是"唯一的层"。

> **教训：设计数据存储时，明确它是"哪一层"，而不只是"存什么"。**

### 1.6 事件为什么不隔离（已知限制）

**第 4 步的事件是全局的 —— 任何容器 `emit` 的事件，所有监听器都能收到。**

| 为什么不做 | 说明 |
|---|---|
| **复杂度高** | 要按作用域路由监听器 |
| **语义模糊** | 全局监听器和局部监听器的**顺序**怎么定？ |
| **实用性低** | 单 agent 场景没有需求 |

**DSH 确实做了** —— 它有 `packages/core/scope/src/scoped-events.generated.ts`，但那是**代码生成**出来的（由 `scripts/gen-scoped-events.ts` 生成）。

**代价**：一个想"只监听自己作用域内事件"的 agent **做不到**，必须在监听器里自己判断。

**第 15 步的诊断层会遇到这个问题**（要按 agent 归因失败），**那时的解法是"在 payload 里带上作用域标识"** —— **用数据解决问题，而不是用机制**。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 隔离粒度 | **服务级** | 也做事件隔离 | 服务隔离够用；事件隔离列入 L9 |
| 2 | 隔离方式 | **显式 `isolate()`** | 自动按插件隔离 | 显式更可控；自动隔离会回到"插件互不可见"（第 3 步连锁 1） |
| 3 | 查找顺序 | **局部优先，全局兜底** | 全局优先 | 局部优先才能遮蔽（通用语义） |
| 4 | 重名检查 | **只查自己的局部层** | 也查全局 / 祖先 | 允许遮蔽是目的；层内唯一避免混乱 |
| 5 | 查找方向 | **沿树向上** | 只看自己 | 支持继承；换来"越近越赢" |
| 6 | 局部层存储 | `Map`（**不共享**） | 也共享 | 共享会彻底破坏隔离 |
| 7 | 与 `provide` 的关系 | **两个方法** | 一个方法加开关参数 | 两个名字语义清晰；开关容易写错 |
| 8 | 事件隔离 | **不做** | 做作用域路由 | 复杂度高；代价是监听器要自己过滤 |

### 关于第 7 条的论证

```ts
// 方案 A：两个方法（我们选的）
ctx.provide('tools', registry)          // 全局
ctx.isolate('tools', readOnlyRegistry)  // 局部

// 方案 B：一个方法加开关
ctx.provide('tools', registry, { scope: 'global' })
```

| 维度 | 两个方法 | 一个方法加开关 |
|---|---|---|
| 可读性 | `ctx.isolate(...)` 一眼知道是隔离 | 要读参数 |
| 拼错风险 | 方法名错会报错 | `scope: 'glboal'` 可能静默退化 |
| 发现性 | IDE 补全能列出两个方法 | 要记得有这个选项 |

**这是"显式大于隐式"的直接应用。**

**DSH 有一条更具体的表述**：

> 「Untyped runtime branches that select between service providers must be explicit.」

**翻译**：在"选哪个 provider"这件事上必须显式。**因为隐式选择会导致"我以为我用的是 A，实际是 B"。**

### 关于第 4 条的完整性论证

**"只查自己的局部层"会不会导致问题？**

```
root
 └── parent          isolate('x', B)
      └── child       isolate('x', A)

child.get('x')   → A（越近越赢）
parent.get('x')  → B
root.get('x')    → 全局的（如果有）
```

**这是正确的** —— 每一层看到的是"从自己出发最近的覆盖"。

**没有冲突**，因为"同一层内不允许重名"保证了一层最多一个。

### 关于第 8 条的影响面

| 谁会受影响 | 怎么受影响 |
|---|---|
| 第 15 步的诊断 | 要按 agent 归因，但事件不区分来源 → **payload 要带 agent 标识** |
| 第 16 步的实验对照 | 两个实验组的事件会混在一起 → **靠标识区分** |
| 单 agent 场景 | **无影响** |

**结论：不做事件隔离，但要求"事件 payload 里带足够的标识信息"。**

## L3 实现：逐行讲解

### 3.0 改动清单（只有这些）

```
新增

  isolate() 方法       约 25 行

  get()                +4 行
  has()                +3 行
  serviceNames()       重写（收集两层）

```

**这就是"叠加"的具体形态** —— 新增为主，改造都是"在前面加一层查找"。

### 3.1 `#local` 字段

```ts
  /**
   * 第 5 步新增：本容器**局部**提供的服务（只对本容器及其子树可见）。
   *
   * 注意它**不共享** —— 每个容器有自己的局部层，这是作用域隔离的载体。
   */
  #local = new Map<string, unknown>()
```

#### 三个细节

**① 内联初始化（不依赖构造参数）**

```ts
#local = new Map<string, unknown>()
```

**对比 `#registry`**：

```ts
#registry: Map<string, ServiceEntry>          // ← 构造函数里赋值（因为要共享）
#local = new Map<string, unknown>()           // ← 内联（不共享，每个容器一份）
```

**这个差别本身就是设计**：**共享的必须在构造函数里 `parent.#x`，不共享的可以内联。**

**看到内联初始化，就知道它不共享。**

**② 值的类型是 `unknown`（不是 `ServiceEntry`）**

```ts
#local = new Map<string, unknown>()
//                  ↑ 直接存值，不存 { owner, value }
```

**为什么全局表要 `ServiceEntry` 而局部表不用？**

| 表 | 需要 owner 吗 | 为什么 |
|---|---|---|
| 全局表 | ✅ 需要 | **多个容器往同一张表写**，撤销时要判断"这条是不是我的" |
| 局部表 | ❌ 不需要 | **一张表只属于一个容器**，撤销时无条件删即可 |

**这个差别有个直接后果**：局部表的撤销函数**不需要 owner 检查**。

```ts
// 全局表（第 3 步）
const remove = (): void => {
  const current = this.#registry.get(name)
  if (current !== undefined && current.owner === this) {   // ← 要检查
    this.#registry.delete(name)
  }
}

// 局部表（第 5 步）
const remove = (): void => {
  this.#local.delete(name)                                 // ← 不用检查
}
```

> **"是否需要归属信息"取决于"这张表是否被多方写入"。**

**③ 注释里必须写"不共享"**

前面 0.5 节连锁 3 讲过：**它和其他共享字段完全相反。**

**从注释就能看出差别**：

```ts
/** 事件名 → 分发器。和第 3 步的注册表一样，由根容器持有、全树共享。 */
#dispatchers

/** 第 4 步新增：全部「依赖未齐、等待启动」的插件容器。共享。 */
#pending

/** 第 5 步新增：本容器**局部**提供的服务…… 注意它**不共享** */
#local
```

**每一处共享/不共享都在注释里标明了。** 这不是啰嗦 —— 因为**这是最容易写错的地方**。

### 3.2 `isolate()` 方法

```ts
  isolate<T>(name: string, value: T): Disposer {
    this.#assertAlive()
    if (this.#local.has(name)) {
      throw new Error(`[${this.name}] 本作用域已有局部服务 "${name}"`)
    }

    this.#local.set(name, value)
    const remove = (): void => {
      this.#local.delete(name)
    }
    this.#effects.push(remove)
    return remove
  }
```

#### 与 `provide` 的逐行对比

| 行 | `provide` | `isolate` |
|---|---|---|
| 生命周期检查 | `this.#assertAlive()` | 同 |
| 重名检查 | 查 **全局表** | 查 **自己的局部表** |
| 写 | `#registry.set(name, {owner: this, value})` | `#local.set(name, value)` |
| 撤销 | 检查 owner 后删 | 直接删 |
| 登记 + 返回 | `push` + `return` | 同 |

**五行里三行相同、两行不同。** 这就是"同一模式的两个变体"。

#### 为什么不抽公共函数

**可以抽**，比如：

```ts
#register(map, name, value, { checkGlobal, needOwner }): Disposer { ... }
```

**但会让代码更难读** —— 因为两个变体的**差异点恰恰是语义核心**（写哪张表、检查什么）。

**抽象掉差异，等于隐藏了关键信息。**

> **判断标准：差异是"配置"还是"语义"？**
> 配置 → 可以抽公共函数；**语义 → 应该显式分开写。**

#### 错误信息里的"本作用域"

```
[dup] 本作用域已有局部服务 "x"
```

**注意它说的是"本作用域"而不是"全树"** —— 因为重名的范围就是本容器。

**对比 `provide` 的信息**：

```
[root] 服务重复注册："config"（已被容器 "plugin-config" 注册）
```

**它有"被谁占的"，因为全局表有 owner 信息。**

**局部表没有 owner，所以 `isolate` 的错误信息里也没有** —— **能说什么，取决于有什么数据。**

### 3.3 `get()` 的改造

```ts
  get<T>(name: string): T | undefined {
    // 第 5 步：先沿容器树向上找「局部层」—— 命中就返回，不再往下走
    for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
      if (node.#local.has(name)) return node.#local.get(name) as T
    }
    // 再回落到全局注册表
    const entry = this.#registry.get(name)
    return entry === undefined ? undefined : (entry.value as T)
  }
```

#### 逐部分

**① 循环的三段**

```ts
for (let node: Context | undefined = this; node !== undefined; node = node.#parent)
//   ────────────┬───────────         ─────┬─────         ─────────┬────────
//         起点 = this                 终点             每轮上移一层
```

**注意 `node` 的显式类型标注**：

```ts
let node: Context | undefined = this
```

**为什么要标 `| undefined`？** 因为终点条件要求它**可能为 undefined**（`node !== undefined`）。

**如果不标**：

```ts
for (let node = this; node !== undefined; node = node.#parent)
```

TS 会把 `node` 推断成 `Context`，然后 `node = node.#parent`（类型是 `Context | undefined`）**会报错**。

**显式标注让循环能自然终止。**

**② 命中即返回**

```ts
if (node.#local.has(name)) return node.#local.get(name) as T
```

**`return` 而不是 `break`** —— 因为**要立刻跳过全局查找**。

**如果写成 `break` 然后继续往下走，就会退化成"全局优先"。**

**③ 全局兜底原样保留**

```ts
const entry = this.#registry.get(name)
return entry === undefined ? undefined : (entry.value as T)
```

**这段代码一个字没改。** 这就是"叠加"的最直接证据。

**④ `as T` 的两次使用**

```ts
return node.#local.get(name) as T          // 局部层
return entry.value as T                     // 全局层（原有）
```

**两处都有同一个问题**（第 3 步缺陷 3）：**`as` 运行时无检查**。

**局部层让这个问题更突出**：因为**同一个服务名在不同容器里可能是完全不同的类型**。

```ts
root.provide('tools', { type: 'full' })
agent.isolate('tools', ['read_file'])       // ← 数组！类型完全不同

const t = agent.get<{ type: string }>('tools')   // ← 编译通过，运行时会崩
```

**这是作用域隔离带来的新风险**，写进 L9。

### 3.4 `has()` 的改造

```ts
  has(name: string): boolean {
    for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
      if (node.#local.has(name)) return true
    }
    return this.#registry.has(name)
  }
```

**和 `get` 完全同构** —— 只是把"返回值"换成"返回 true"。

**为什么 `has` 必须跟着改？**

因为 `require` 用的是 `has`：

```ts
require<T>(name: string): T {
  if (!this.has(name)) { throw ... }
  return this.get<T>(name) as T
}
```

**如果只改 `get` 不改 `has`**：

```
agent.isolate('tools', 只读)
agent.require('tools')
   ↓ has('tools') → 查全局 → 有（返回 true，没报错）
   ↓ get('tools') → 查局部 → 返回只读  ✅
```

**这个场景恰好能工作**。但反过来：

```
root 没有 'local-only' 这个服务
agent.isolate('local-only', X)
agent.require('local-only')
   ↓ has('local-only') → 只查全局 → false → ★ 报错"找不到服务" ★
   ↓ 但它明明存在（在局部层里）
```

**这是"局部独有的服务无法被 require"的 bug。**

**所以 `has` 必须和 `get` 保持同构** —— 这是**"两个方法必须一起改"的典型例子**。

> **教训：改查找逻辑时，要找出所有"做同类查找"的方法，一起改。**

### 3.5 `serviceNames()` 的改造

```ts
  serviceNames(): string[] {
    const names = new Set<string>()
    for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
      for (const name of node.#local.keys()) names.add(name)
    }
    for (const name of this.#registry.keys()) names.add(name)
    return [...names]
  }
```

#### 用 `Set` 去重

**因为同一个名字可能同时在局部层和全局表里**（遮蔽的情形）：

```
node.#local = { tools: 只读 }
#registry   = { tools: 全量 }

names = new Set(['tools', 'tools'])   →  ['tools']   ← 去重
```

**如果直接用数组 push，会出现重复项。**

#### 两层嵌套循环

```ts
for (let node = this; ...) {         // 外层：沿树向上
  for (const name of node.#local.keys()) { ... }   // 内层：这一层的全部名字
}
```

**注意内层用的是 `node.#local`（当前层的），不是 `this.#local`。**

**这是"沿树上移时，每层都要看"的实现。**

#### 语义的变化

**改之前**：返回全局表的全部名字。

**改之后**：返回**这个容器能看见的**全部名字。

**这是一个语义变化** —— 方法名没变，但含义从"全局有什么"变成了"我能看见什么"。

**这是对的**，因为调用方（`require` 的错误信息）想要的是"我有哪些可选"。

**但要注意**：如果有代码依赖"`serviceNames()` 返回全局表内容"，它现在会看到更多名字。

**我们没改名字**，因为这算是"语义修正"而不是"破坏性变更"。**但这值得在 L9 里提一句。**

### 3.6 `ownerOf()` 的改造

```ts
  ownerOf(name: string): string | undefined {
    for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
      if (node.#local.has(name)) return `${node.name}（局部）`
    }
    return this.#registry.get(name)?.owner.name
  }
```

#### 返回值加了标记

```ts
return `${node.name}（局部）`
// → "agent1（局部）"
```

**为什么加"（局部）"？**

因为**只看名字不够**：

```
"agent1"           ← 是 agent1 全局注册的？还是它局部提供的？
"agent1（局部）"    ← 明确是局部的
```

**在这个方法的用途（排查"这东西谁挂上来的"）下，这个区别很重要** —— 因为它决定了"改变它的影响范围有多大"。

#### 一个新的不一致

**返回值的格式有两种**：

| 来源 | 格式 |
|---|---|
| 局部层 | `"agent1（局部）"` |
| 全局表 | `"plugin-config"` |

**加后缀是一种"在字符串里编码结构化信息"的做法** —— 严格说应该返回结构化数据：

```ts
ownerOf(name): { name: string; scope: 'local' | 'global' } | undefined
```

**我们没这么改**，因为：

1. `ownerOf` 是调试方法（不是核心 API）
2. 改返回类型会破坏第 3 步的调用（演示里的 `${name} ← ${ownerOf(name)}`）

**这是个"为了兼容而保留的将就写法"**，写进 L9。

### 3.7 三处循环的形态对比

**`get` / `has` / `ownerOf` 里有三段几乎一样的循环**：

```ts
// get
for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
  if (node.#local.has(name)) return node.#local.get(name) as T
}

// has
for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
  if (node.#local.has(name)) return true
}

// ownerOf
for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
  if (node.#local.has(name)) return `${node.name}（局部）`
}
```

**它们可以抽成一个"查找最近的局部层"的辅助方法**：

```ts
#findLocal(name: string): { node: Context; value: unknown } | undefined {
  for (let node: Context | undefined = this; node !== undefined; node = node.#parent) {
    if (node.#local.has(name)) return { node, value: node.#local.get(name) }
  }
  return undefined
}
```

**然后三个方法都调它。**

**为什么我们没抽？**

| 理由 | 说明 |
|---|---|
| 每个循环只有 3 行 | 抽取的收益有限 |
| 返回结构会引入新类型 | `{ node, value }` 是个只为内部使用的类型 |
| **`ownerOf` 需要 `node`（容器名），另两个需要 `value`** | 抽取后返回要带两个东西，反而不简洁 |

**但是**：这是"三次法则"的边界情况 —— **如果第 6 步再需要一次同样的查找，就该抽了。**

**这不是"想清楚了才不做"，而是"现在不做，理由是收益低"。**

> **要区分这两种"不做"：**
> - 「想清楚了，收益低」→ **可以接受**
> - 「没想到要抽」→ **技术债**

## L5 语法速查（本篇新增）

> 第 1–4 步的语法分别在 [`01`](01-llm.md#l5-本篇-typescript-语法速查) / [`02`](02-tools.md#l5-语法速查本篇新增) / [`03`](03-context.md#l5-语法速查本篇新增) / [`04`](04-events.md#l5-语法速查本篇新增) 里。

| 语法 | 例子 | 含义 | 注意 |
|---|---|---|---|
| **for 三段式遍历链表** | `for (let n = this; n !== undefined; n = n.#parent)` | 沿指针链上移 | **`n` 要显式标 `\| undefined`** |
| `Set` 去重 | `new Set([...a, ...b])` | 合并两个集合并去重 | 保序 |
| `Map.keys()` | `node.#local.keys()` | 迭代器 | `for...of` 直接用 |
| **私有字段跨实例** | `node.#local` | 同类实例可访问 | 第 3 步讲过 |
| 内联初始化 vs 构造赋值 | `#local = new Map()` / `#registry = parent.#registry` | 看是否共享 | 内联 = 不共享 |

### 本篇新增的两条规则

**规则 17：`for` 循环里沿指针上移时，变量必须标 `| undefined`**

```ts
// ✅
for (let node: Context | undefined = this; node !== undefined; node = node.#parent) { }

// ❌ TS 报错：类型 Context 不能赋值给 Context | undefined 的…… 其实是反过来
for (let node = this; node !== undefined; node = node.#parent) { }
```

**原因**：`node = node.#parent` 的右侧类型是 `Context | undefined`，而 TS 把 `node` 推断成 `Context`。

**规则 18：内联初始化的字段一定是不共享的**

```ts
#registry = ...      // ❌ 这样写就没法共享了（每个容器新建一个）
#local = new Map()   // ✅ 内联 = 不共享 = 正是我们想要的
```

**这是一个可以"读出来"的信号**：**看到内联初始化，就知道这个字段每个容器一份。**

## L7 挑战题（不给答案）

### 挑战 1 · 验证"越近越赢"

演示里没有验证"孙子自己 isolate 会覆盖 agent1 的"。

**要求**：

1. 加三层嵌套：root → agent1（isolate 只读）→ 孙（isolate 读写）
2. 验证孙看到读写、agent1 看到只读
3. **再验证**：撤销孙的之后，它回落到 agent1 的只读（不是回落到全局）

### 挑战 2 · 抽出"查找最近的局部层"

三处循环可以抽成一个 `#findLocal`。

**要求**：

1. 抽出这个方法
2. 让 `get` / `has` / `ownerOf` 都用它
3. **比较：抽取前后的行数、可读性、类型复杂度**

**思考**：抽取**真的更好**吗？在什么情况下更好？

### 挑战 3 · 让 `isolate` 也能"跨容器"

现在 `isolate` 只对**自己的子树**有效。

**问题**：

1. 如果一个容器想给**兄弟**提供局部服务，能做到吗？
2. 如果做不到，应该给它这个能力吗？（提示：那就不叫"隔离"了）
3. **DSH 里 `ctx.isolate(name)` 的语义是什么？**（去看它的 README）

**这道题考察的是"抵抗扩大范围诱惑"的能力。**

### 挑战 4 · 给事件加作用域

第 4 步的事件是全局的（已知限制）。

**要求**：

1. 给 `emit` 加一个可选的"作用域过滤"
2. 只有"在这个作用域内的监听器"才被调用
3. **分析**：全局监听器和局部监听器的**顺序**该怎么定？

**思考**：这个复杂度值得吗？**在什么场景下才值得？**

### 挑战 5 · 解决 `as T` 的类型风险

**问题**（L9 缺陷 2）：同一个服务名在不同作用域里可以是不同类型，而 `as T` 让编译器闭嘴。

**要求**：

设计一个方案，让"局部服务"的读取**在类型上更安全**。

**三种思路**：

| 思路 | 做法 |
|---|---|
| A | 集中式服务类型表（`interface Services { tools: ToolRegistry }`） |
| B | 局部服务用独立的名字空间（`local:tools`） |
| C | 服务带类型标签，运行时校验 |

**分析三者代价**，说明你在真实项目里会选哪个。

### 当前实现的真实缺陷

#### 缺陷 1 · 事件不做作用域隔离

**问题**：第 4 步的 `Dispatcher` 是全树的，任何容器 `emit` 的事件所有监听器都能收到。

**后果**：

- 第 15 步诊断要按 agent 归因失败 → **事件不区分来源，必须靠 payload 里的标识**
- 第 16 步的实验对照 → 两个实验组的事件混在一起

**修法**：DSH 用**代码生成**的方案（`scripts/gen-scoped-events.ts` 生成路由表）。

**为什么不做**：复杂度高（要按作用域路由 + 要定顺序语义），而**单 agent 场景没有需求**。

#### 缺陷 2 · 局部服务引入了新的类型风险 ★

```ts
root.provide('tools', { type: 'full' })
agent.isolate('tools', ['read_file'])              // ← 完全不同的类型

const t = agent.get<{ type: string }>('tools')     // ← 编译通过
t.type                                              // ← 运行时 undefined
```

**问题**：**同一个服务名在不同作用域里可以是不同类型**，而 `as T` 让编译器闭嘴。

**这是第 3 步缺陷 3 的放大版** —— 第 3 步只有"类型不可靠"，第 5 步多了"**同名不同型**"。

**修法**：见挑战题 5。

**为什么没做**：那需要一个集中式的服务类型表，**与"字符串查表"的简洁性冲突**。

#### 缺陷 3 · `ownerOf` 用字符串后缀编码结构信息

```ts
return `${node.name}（局部）`
```

**问题**：把"来源类型"编码进字符串，而不是返回结构化数据。

**后果**：调用方要**解析字符串**才能知道是局部还是全局 —— 而解析中文括号很脆弱。

**修法**：返回 `{ name: string; scope: 'local' | 'global' }`。

**为什么没做**：会破坏第 3 步演示里的调用（`` `${name} ← ${ownerOf(name)}` ``），且 `ownerOf` 只是调试方法。

**这是"为了兼容而将就"** —— 但代价是"这个 API 不好用"。

#### 缺陷 4 · `serviceNames()` 的语义变了但名字没变

**改之前**：返回全局表的全部名字。

**改之后**：返回**这个容器能看见的**全部名字（局部 + 全局）。

**问题**：**方法名没变，含义变了。**

**后果**：如果有代码依赖"它返回全局内容"，现在会看到更多。

**为什么没改名**：这算是"语义修正"（调用方想要的本就是"我有哪些可选"）。

**但严格说，这是一个未记录的破坏性变更。**

#### 缺陷 5 · 局部层没有"列举"能力

**你能问"这个容器看见了哪些服务"（`serviceNames`），但不能问"这个容器自己局部提供了哪些"。**

**后果**：调试时想知道"这个作用域改了什么"，**必须对比父子两级的 `serviceNames`**。

**修法**：加一个 `localNames()`。

**为什么不加**：目前没人需要。**但第 8 步创建 agent 时可能会需要**（要打印"这个 agent 的定制配置"）。

#### 缺陷 6 · `isolate` 不能被 `inject` 满足

**问题**：第 4 步的 `inject` 用 `this.#registry.has(name)` 检查依赖：

```ts
const missing = deps.filter((name) => !this.#registry.has(name))
```

**它只查全局表 —— 不查局部层。**

**后果**：

```
某个插件 inject: ['tools']
但 'tools' 只被 isolate 在另一个作用域里（全局没有）
   ↓
★ 这个插件的依赖永远"不满足"，永远挂起 ★
```

**这是"两个机制没有对接"的典型问题** —— 第 4 步写 `inject` 时，局部层还不存在。

**修法**：把 `deps.filter(...)` 改成用 `child.has(name)`（这样会查局部层）。

**为什么没改**：**改动很小，但会改变语义** —— "依赖是全局的"还是"依赖是作用域可见的"？

**这是个真实的设计问题**，需要先想清楚"inject 的作用域语义"再改。

**它写进第 6 步的设计笔记。**

## L11 系统影响回溯

### 11.1 三个预判的检验

| 第 0.5 节的问题 | 现在你应该能答的 |
|---|---|
| 孙子自己 isolate 会怎样？ | 覆盖 agent1 的（**越近越赢**）；撤销后**回落到 agent1 的只读**（不是全局） |
| 先 `isolate('x', A)` 再 `provide('x', B)` 会报错吗？ | **不会** —— 因为 `provide` 只检查全局表，而 `isolate` 写的是局部表。**两者互不知道对方存在** |
| 事件隔离怎么改？ | 需要"监听器带作用域标记 + emit 时过滤"。**代价是顺序语义和复杂度**，见缺陷 1 |

**第 2 个问题的答案值得展开**：

```
ctx.isolate('x', A)     局部层: { x: A }
ctx.provide('x', B)     全局表: { x: B }      ← 不报错

ctx.get('x') → A（局部优先）
root.get('x') → B
```

**这看起来"能工作"，但它是一个陷阱** —— 因为**同一个容器里有两份 `x`，语义上说不清**。

**正确的用法是把它们用在不同层**：

```
root.provide('x', 默认值)          ← 全局默认
agent.isolate('x', 定制值)         ← 局部覆盖
```

**"同一个容器里既 provide 又 isolate 同一个名字"应该被禁止**，但我们没有检查。

**这是缺陷 5 之外的另一个小缺口**，值得在挑战题里让读者发现。

### 11.2 本篇的"锚点"一句话

> **新能力应该是"在前面多加一层查找"，而不是"改写原来的逻辑"。**

它在后面的影子：

| 哪一步 | 同一思想的再现 |
|---|---|
| 第 6 步 | profile 的层层叠加 —— 每一层都"覆盖前面、不修改前面" |
| 第 7 步 | 会话日志的投影 —— 原始事件不动，投影是"另外算出来的" |
| 第 9 步 | 重试是"再发一次"，不修改原来的请求构造 |
| 第 10 步 | 守卫是"在执行前插一层检查"，不改工具实现 |
| 第 16 步 | 演化是"改配置"，不改代码 |

**"叠加"是整个系统的一致设计哲学** —— 而它在第 5 步第一次被明确验证。

### 11.3 通向第 6 步的桥

**第 5 步结束时，系统状态：**

```
✅ 插件能提供能力、监听事件、声明依赖
✅ 同一个服务名能在不同作用域解析出不同的值
❌ 但一切仍然要手工装载：new Context、await plugin(...)、isolate(...)
❌ 没有"配置"，所有装配都在代码里
```

**第 6 步要解决"配置即组合"。** 带着这些问题进入：

1. 现在要装 5 个插件，得写 5 行 `await ctx.plugin(...)`。**怎么把它们变成数据？**
2. 如果两个 profile 有 80% 相同的插件，**怎么复用那 80%**？
3. 层叠时，**后一层怎么"覆盖"前一层的某个插件配置**？
4. **第 4 步的挂起机制在这里有什么用？**（提示：装载顺序自由了）
5. **如果我改了一个配置但没生效，怎么知道实际生效的是什么？**（提示：`dump-config`）

**第 5 个问题是第 6 步的一个关键设计点** —— **"改了没生效"是配置系统最经典的故障，而 dump 是唯一的解药。**
