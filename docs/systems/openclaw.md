## 本篇新词

> 这些词在本篇有**特定于 OpenClaw 的含义**，和通用术语不完全一样。通用术语见 [`../glossary.md`](../glossary.md)。

| 词 | 在本篇的含义 |
|---|---|

| **compaction safeguard** | 内建的压缩保护钩子 |
| **runtime policy** | 按模型/提供方选择用哪个 harness（`agentRuntime.id`） |

## 第 0 节 · 这个系统是什么

### 0.1 一句话定位

> **一个"本地优先、用聊天软件当界面、模型可替换"的长运行智能体。**

### 0.2 基本事实

| 项 | 值 |
|---|---|
| 作者 | Peter Steinberger |
| 许可证 | MIT |
| 规模 | 200,000+ GitHub stars（据称是史上增长最快的仓库之一） |
| 形态 | 长运行运行时 / 多渠道助手运行时 |
| 语言 | TypeScript（Node） |
| 界面 | **WhatsApp / Telegram / Signal / Discord / Slack / iMessage** —— **没有自建 UI** |
| 模型 | 模型无关（Claude / GPT / DeepSeek / 本地 Ollama…） |

### 0.3 它刻意做的三个选择

**这三个选择是它"病毒式传播"的原因**（据多方分析归因）：

| 选择 | 含义 | 对比 |
|---|---|---|
| **local-first** | 会话、记忆、配置都是本地的纯文本（Markdown/YAML） | 对比：云端 SaaS 的黑箱 |
| **聊天软件即界面** | 不写自己的 UI，直接用你已有的 IM | 对比：Claude Code 的终端、Web 版的自建 UI |
| **真·模型无关** | 没有订阅绑定，模型是可替换模块 | 对比：Codex 绑定 OpenAI 模型 |

**第 2 条最反直觉，也最有洞察**：

> **"用户已经有一个每天打开的界面了 —— 为什么要让他们再学一个？"**

**这条选择的代价**：无法做丰富的交互（IM 的富媒体能力有限）。
**收益**：零学习成本、零安装成本（在手机上就能用）。

### 0.4 在 Harness-Bench 里的位置

你的 `harness-bench-zh.md` 里有它的成绩：

| harness | 总分 | 完成度 | 过程分 | 工具 | 一致性 | token(K) | 轮数 |
|---|---|---|---|---|---|---|---|
| **OpenClaw** | **52.4** | 60.0 | 100.0 | 79.5 | 74.0 | 82.1 | 5.0 |

**52.4 是"可配置 harness"里最低的一个**（NanoBot 76.2，Hermes 71.2，ZeroClaw 61.4）。

**但注意它的"完成度 60.0 而过程分 100.0"** —— 这个组合很有意思：

> **它做的每一步都是"对的"（过程分满分），但只完成了 60% 的任务。**

**解读**：它的**过程质量高但推进能力弱** —— 可能在"长任务的持续推进"上不足。

**这正是它被归类为"长运行运行时"却得分低的原因**（长运行不等于长推进）。

## L0 · 它要解决的问题

**因为我们没有它的设计文档，所以这一节是"从它的形态反推它要解决什么"。**

### 0.1 从三个选择反推

| 它的选择 | 反推的问题 |
|---|---|
| local-first | "我不想把我的对话和记忆交给一个云端服务" |
| 聊天软件即界面 | "我不想为了用 AI 再装一个 App / 学一个新界面" |
| 模型无关 | "我不想被某一家的订阅和价格绑住" |
| 长运行 + heartbeat | "我希望它是我常驻的助手，而不是我打开才活的工具" |

### 0.2 它和 Claude Code 的定位差异

**这个对比最清楚**：

| | Claude Code | OpenClaw |
|---|---|---|
| 场景 | **在代码库里干活** | **日常生活与工作的助手** |
| 界面 | 终端 | 聊天软件 |
| 会话 | 一次任务一个会话 | **常驻，跨渠道** |
| 环境 | 你的项目目录 | 你的机器（多目录） |
| 模型 | Anthropic（可换但设计围绕 Claude） | **真正无关** |

**关键差异在"常驻"**：

> **Claude Code 是"我打开它干活，干完关掉"。**
> **OpenClaw 是"它一直在，我在手机上发条消息给它"。**

**这个差异决定了架构上的两个后果**：

1. **必须有心跳/定时**（因为它不总是被用户唤醒）
2. **必须跨会话记住事情**（因为它不区分"这次任务"和"上次任务"）

### 0.3 它给我们的启示（对做 harness 的人来说）

**问自己一个问题**：

> **如果你的 agent 要"常驻"，你的架构要改什么？**

| 我们的 lab | 常驻场景要加的 |
|---|---|
| 一次 `loadProfile` + 跑任务 + 退出 | 常驻进程 + 消息队列 |
| 会话是独立的文件 | 会话之间要能**互相引用**（"上次说的那个事"） |
| 没有定时 | **心跳/调度** |
| 一个前端（CLI） | **多渠道适配层** |

**这四个都会在第 12–14 步（记忆/技能/检索）遇到** —— 因为**常驻的前提是"记得住"**。

## L1 · 架构地图

**这一节的数据全部来自官方架构文档（✅ 已核实）。**

### 1.1 目录结构

```
src/
├── agents/
│   ├── embedded-agent-runner/     ★ 内建的 attempt loop
│   │                               （run.ts + 模型选择/提供方归一化 +
│   │                                每提供方请求参数 + 压缩 + 会话接线）
│   ├── sessions/                  会话持久化、资源发现、会话内扩展加载、
│   │                              提示模板、skills、主题、TUI 工具渲染器
│   ├── runtime/                   ★ 门面：把 agent-core 接到插件 SDK 的 LLM 运行时
│   ├── agent-tools*.ts            工具定义、参数 schema、**工具策略**、
│   │                              **tool-call 前后适配器**、宿主/沙箱编辑工具
│   ├── agent-hooks/               ★ 内建运行时钩子：
│   │                              compaction safeguard / compaction instructions /
│   │                              context pruning
│   └── harness/                   ★ harness 注册表、选择策略、生命周期
└── llm/                           模型/提供方注册表、传输助手、提供方特定流式

packages/
└── agent-core/                    ★ 可复用核心 @openclaw/agent-core：
                                   agent loop、harness 类型、messages、
                                   压缩助手、提示模板、skills、
                                   会话存储契约
```

### 1.2 从目录结构能读出什么

**逐条分析（✅ 基于官方文档的职责描述）**：

#### ① `packages/agent-core/` —— 抽出来的可复用核心

**注意它在 `packages/` 而不是 `src/`** —— 这意味着它是**独立发布的包**（`@openclaw/agent-core`）。

**它包含的东西**：agent loop、harness 类型、messages、压缩助手、提示模板、skills、**会话存储契约**。

**"会话存储契约"这个措辞很重要** —— **契约（contract）意味着"只有接口，没有实现"**。

> **核心包不关心会话存在哪里，只定义"必须提供什么能力"。**

**这是"依赖抽象"的应用** —— 和我们在第 3 步做的 `provide`/`require` 是同一个思想，只是粒度更大（整个会话存储）。

#### ② `src/agents/runtime/` —— 门面（facade）

文档说它是"把 `@openclaw/agent-core` 接到插件 SDK 的 LLM 运行时"。

**这个"接线"动作值得注意**：

```
@openclaw/agent-core（纯核心）
        ▲
        │ 门面接线
        ▼
openclaw/plugin-sdk（插件契约）
```

**为什么要门面？**

因为**核心包不该知道插件系统** —— 它只定义抽象的 LLM 运行时接口，**由门面把具体实现接上去**。

**这是"核心 vs 外壳"分离的经典做法。**

#### ③ `src/agents/harness/` —— harness 注册表

**这是 OpenClaw 最有特色的设计**：

> **它自己的 agent loop 只是"内建的一个 harness"，插件可以注册别的。**

**证据（✅ 官方文档）**：

- 内建 runtime id 是 `openclaw`
- 插件 harness 注册额外 id（例如 `codex`）
- runtime policy 按 `agentRuntime.id`（模型/提供方维度）选择
- `auto` 会优先选兼容的插件 harness，否则回退内建

**这个设计的意义**：

```
用户的配置：agentRuntime: { id: 'auto' }
   ↓
如果当前模型有对应的插件 harness（比如用 GPT 时用 codex harness）
   → 用它
   ↓
否则
   → 用内建的 openclaw harness
```

**这和我们在第 6 步做的"配置选择插件"是同一个模式**，但**粒度更细** —— 它按"模型/提供方"选择**执行后端**。

**对我们的启示**：

> **"agent loop 本身"也可以是一个可替换的插件。**
>
> 我们的第 8 步会把 agent loop 实现成一个插件 —— **而 OpenClaw 把它做成了"可以有多个、按模型选择"**。

#### ④ `src/agents/agent-hooks/` —— 内建运行时钩子

三个钩子（✅）：

| 钩子 | 作用（据名称与文档） |
|---|---|
| `compaction safeguard` | 压缩的保护机制 |
| `compaction instructions` | 压缩的指令 |
| `context pruning` | 上下文裁剪 |

**"safeguard"（保护）这个词值得注意** —— 它暗示**压缩本身可能出错，需要一个保护层**。

**我们在第 10 步会遇到同样的问题**（压缩后信息丢失）。

**而 Claude Code 的逆向分析里有一个惊人的细节**（⚠️ 二手）：

> 曾经有 1,279 个会话出现了**最多 3,272 次连续压缩失败**，全球每天浪费约 25 万次 API 调用 —— 修复是**三行代码**（加了一个连续失败的熔断器）。

**如果这个数字是真的**，它说明：**压缩失败会形成死循环，而"熔断"是最简单的解药。**

**我们在第 10 步应该实现一个"连续失败熔断"。**

#### ⑤ `src/agents/agent-tools*.ts` —— 工具层

三个值得注意的点（✅）：

| 特性 | 对应我们的第几步 |
|---|---|
| 参数 schema | 第 2 步 |
| **工具策略（tool policy）** | 第 10 步（守卫/审批） |
| **tool-call 前后适配器** | 第 10 步（`tools/pre-execute` 和 `tools/post-execute`） |
| 宿主/沙箱编辑工具 | 第 10 步（沙箱） |

**"前后适配器"这个命名直接对应我们的 waterfall 钩子**：

```
tool-call 前 → 检查/改写/拒绝
tool-call 后 → 检查/改写结果
```

**这说明"工具执行管线的前后钩子"是一个收敛的设计** —— 多个独立系统都这么做。

#### ⑥ `src/llm/` —— 模型层

职责（✅）：模型/提供方注册表、传输助手、**提供方特定流式**。

**"提供方特定流式"值得注意** —— 它说明**流式在不同提供方之间不统一**，需要分别处理。

**这正是我们第 1 步"不做流式"的代价** —— 一旦要做，就要面对"每家的流式格式不同"。

### 1.3 边界规则（✅ 官方文档明确写了）

**这三条边界规则很有价值**：

| 规则 | 含义 |
|---|---|
| 核心通过 OpenClaw 模块/SDK barrel 调用内建运行时 | **没有外部 agent 框架依赖残留** |
| 插件用文档化的 entrypoint，**不 import `src/**` 内部** | **插件不能碰内部实现** |
| 内建 runtime id 是 `openclaw`，插件 harness 注册别的 id | **可替换，但可辨识** |

**第二条是关键**：

> **插件只能用公开的 `openclaw/plugin-sdk/*`，不能 `import 'src/agents/...'`。**

**这是"公开 API vs 内部实现"的强制隔离。**

**对比我们的 lab**：

| | OpenClaw | 我们的 lab |
|---|---|---|
| 插件能 import 什么 | 只能 `plugin-sdk/*` | **任何文件**（没有强制） |
| 怎么保证 | **构建/检查规则** | ❌ 没有 |
| 后果 | 内部重构不破坏插件 | **内部重构可能悄悄破坏插件** |

**这是一个真实的缺口**，值得记下来（我们的 lab 应该加一条 lint 规则）。

### 2.2 三个值得深入的设计

#### 设计 1：agent loop 是可替换的后端（`harness/`）

**这是 OpenClaw 最有借鉴价值的设计。**

**它的形态**：

```
      用户配置：agentRuntime.id
              │
      ┌───────┴───────┐
      ▼               ▼
  'auto'           'codex' / 'openclaw' / …
      │               │
      │ 按模型/提供方选择
      ▼
  插件 harness（如果兼容）
      │ 否则
      ▼
  内建 openclaw harness
```

**为什么这个设计好？**

| 好处 | 说明 |
|---|---|
| **模型与 harness 解耦** | 不同模型可能适合不同的循环策略 |
| **可实验** | 换 harness 就能做对照实验 —— **这正是你的研究方向** |
| **降级安全** | 插件 harness 不可用时有内建兜底 |

**对我们第 8 步的启示**：

> **我们打算把 agent loop 实现成一个插件。**
> **OpenClaw 的思路更进一步：可以同时有多个，按配置/模型选择。**

**而这直接关系到你的科研**：

> **"harness 干预 vs 自我修正"的实验，需要能同时跑多个 harness 变体。**
> **`harness/` 这种"注册表 + 选择策略"的结构，天生支持这种对照。**

#### 设计 2：会话存储是"契约"而不是实现

**`@openclaw/agent-core` 里有"会话存储契约"**（✅）。

**这意味着**：

```
agent-core（核心）
  └─ 定义：SessionStorage 接口（create / load / save / ...）
        ↑
        │ 实现
        │
  src/agents/sessions/（具体实现：文件系统）
```

**对比我们的第 7 步**：

| | OpenClaw | 我们的 lab |
|---|---|---|
| 存储 | **契约 + 实现分离** | `Session` 类直接 `writeFile` |
| 换后端 | 换实现即可 | **要改 `Session` 类** |

**这是个真实的差距** —— 我们的 `Session` 把"状态管理"和"持久化"混在一起了。

**DSH 做的是分离的**（`SessionPersistence` 接口 + JSONL 后端 + 其他后端）。

**我们应该在第 7 步的 L9 里记下这条** —— 先记着，后面重构。

#### 设计 3：`local-first` 的具体形态

**"会话、记忆、配置都是本地纯文本"**（Markdown/YAML）。

**这对你的科研有一个直接的好处**：

> **纯文本意味着可以用 `git` 管理、可以用 `diff` 对比、可以用脚本处理。**

**而 Claude Code 的会话存储是 JSONL 文件**（也在本地）。

**共同点**：**本地 + 纯文本 + 可 diff。**

**这说明"可检查性"是一个被多个系统都追求的性质** —— 而它**恰好是科研的硬要求**。

**反面对比**：如果 agent 的记忆存在一个不可读的二进制数据库里，**你就无法审计"它到底记住了什么"**。

### 2.3 它和 Hermes 的分工（一个有意思的对比）

**你的 harness-bench 摘要里有一句话**（⚠️ 来自二手对比来源）：

> **OpenClaw 的 skills 是用户手写的 Markdown；Hermes 从自己的经验里生成 skills 并修剪它们。**

**这个对比很重要**：

| | OpenClaw | Hermes |
|---|---|---|
| 技能从哪来 | **用户写** | **agent 自己生成** |
| 谁维护 | 用户（+ ClawHub 社区） | **Curator 自动维护** |
| 质量保证 | 人的判断 | **自动扫描 + 回滚** |
| 风险 | 用户不写就没有 | **自动生成的质量不可控** |

**这不是"谁更好"的问题，是"谁承担维护成本"的问题**：

> **OpenClaw 把维护成本放在用户身上（所以有 ClawHub 让社区分担）。**
> **Hermes 把维护成本放在机器身上（所以需要 Curator）。**

**你的第 12–16 步走的是 Hermes 的路线** —— 所以 `13-skills.md` 要重点参考 Hermes。

## L4 · 可迁移的设计模式

**这一节是给做 harness 的人的。**

### 模式 1 · 「核心包 + 门面接线」

```
packages/agent-core/        纯核心，不认识插件系统
      ▲
      │ 门面
src/agents/runtime/         接线到 plugin-sdk
```

**为什么值得学**：

> **核心包一旦知道插件系统，它就不能被单独复用，也不能被单独测试。**

**我们的对应**：`kernel/`（纯能力，不认识框架）+ `framework/`（框架）+ `plugins/`（接线）。

**我们做对了这一条** —— 第 1、2 步的代码**至今不认识任何框架概念**。

### 模式 2 · 「执行后端可替换」

**`harness/` 注册表**：多个 agent loop 实现，按配置/模型选择。

**迁移价值**：

| 场景 | 用法 |
|---|---|
| 科研对照 | 同时实现两个 loop 变体，跑同一批任务 |
| 模型适配 | 有的模型适合不同的循环策略 |
| 降级 | 插件失败时回退内建 |

**我们的第 8 步应该照这个思路设计** —— **不是"写一个 loop"，而是"定义 loop 的接口 + 写一个实现"**。

### 模式 3 · 「前后适配器包裹调用」

```
tool-call → [前适配器链] → 执行 → [后适配器链] → 结果
```

**我们的对应**：`tools/pre-execute` → 守卫 → `tools/execute` → `tools/post-execute`（第 10 步）。

**验证**：**多个独立系统都收敛到这个形状** —— 说明它是"工具安全"的标准结构。

### 模式 4 · 「压缩需要保护层」

**`compaction safeguard`** 这个钩子的存在，说明：

> **压缩是一个"可能出错且出错后果严重"的操作 —— 所以它需要独立的安全网。**

**具体的安全网应该包括**：

| 保护 | 作用 |
|---|---|
| 备份被压缩的内容 | 出错能恢复 |
| 熔断 | 连续失败就停（⚠️ Claude Code  reportedly 有三行熔断的教训） |
| 压缩后校验 | 关键信息还在吗 |

### 模式 5 · 「本地纯文本」

**会话/记忆/配置全是可读文本。**

**为什么值得学**：

> **可读 = 可用 git 管理 = 可 diff = 可脚本处理 = 可审计。**

**这一条和你的科研直接相关**：

```
如果你的 agent 记忆存在不透明的数据库里
   → 你无法审计"它记住了什么"
   → 你无法在论文里引用它
   → 你无法复现"当时的记忆状态"
```

**而 Hermes 用的是 SQLite + FTS5**（可读性差但检索强）—— **这是一个真实的取舍**：

| 方案 | 可审计 | 检索 |
|---|---|---|
| 纯文本 | ✅ 高 | ❌ 要自己实现 |
| SQLite | ⚠️ 中 | ✅ 强 |

**Hermes 的做法是"两者都要"**：记忆是纯文本（`MEMORY.md`），会话检索用 SQLite。

## L5 · 已知问题与弱点

### 5.1 从 Harness-Bench 看

**数据（⚠️ 来自你本地的论文中译）**：

```
OpenClaw: 总分 52.4（可配置 harness 中最低）
          完成度 60.0 / 过程分 100.0 / 工具 79.5 / 一致性 74.0
          token 82.1K / 轮数 5.0
```

**三个观察**：

| 观察 | 解读 |
|---|---|
| 过程分 **100.0** 但完成度只有 60.0 | **每步都对，但推不到终点** |
| 轮数只用 5.0（最低） | **它很快就不做了** |
| token 82.1K（中等） | 不是"烧了很多 token 但没做完" |

**综合解读（❓ 我的推断）**：

> **它的失败模式可能是"过早停止"** —— 过程质量高，但**在长任务上没有持续推进的策略**。
>
> 这和它"长运行运行时"的定位形成反差：**长运行的是进程，不是任务的推进深度**。

**对照 Hermes**（同样定位"长运行"）：

```
Hermes: 总分 71.2 / 过程分 85.5 / token 139.7K / 轮数 22.6
```

**Hermes 用了 4.5 倍的轮数、1.7 倍的 token，换来高 19 分的成绩。**

**这是一个"投入换产出"的对比** —— 而**它正好是你可以研究的题目**：

> **"什么时候继续尝试是有价值的？"** —— 这正是你的方向（干预 vs 自我修正）的核心问题。

### 5.2 架构上的潜在风险（❓ 推断）

| 风险 | 理由 |
|---|---|
| **没有自建 UI 限制了反馈质量** | IM 里难以展示 diff、文件树、多步计划 |
| **常驻进程的状态管理复杂** | 心跳 + 多渠道 + 并发会话 |
| **技能依赖用户维护** | 不写就没有；质量参差 |
| **模型无关的代价** | 无法针对某个模型做深度优化 |

**第三条是关键** —— **它和 Hermes 的分歧点**，也是**你的第 13 步（技能系统）要做的选择**。
