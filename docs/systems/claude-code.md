## L0 · 它要解决什么问题

**这一节可以相对确信，因为它是从"用法"反推的（官方文档在这里可用）。**

### 0.1 它的核心问题：在真实代码库里自主干活

| 挑战 | Claude Code 的应对（✅ 官方文档层面） |
|---|---|
| 代码库很大，塞不进上下文 | 工具化的搜索/读取（Explore 子代理） |
| 任务很长，上下文会满 | **压缩** |
| 需要并行做多件事 | **子代理 + worktree 隔离** |
| 危险操作 | **权限分级 + 审批** |
| 用户要边看边想 | **流式输出** |

### 0.2 一个关键的设计判断

**"minimal loop inside a thick harness"** 这个结论（⚠️ 多来源一致）值得展开：

> **核心循环故意保持简单；复杂度全部推到外围的"层"里。**

**为什么这是个好判断？**

| 做法 | 后果 |
|---|---|
| 主循环里塞满功能 | 改一处要理解全部，且容易互相干扰 |
| **主循环最小 + 功能在外围** | 每加一个能力 = 加一层或加一个工具 |

**这和我们在第 4 步说的"行为挂在扩展点上，不写死在调用链里"是同一个原则。**

**但 Claude Code 走得更远** —— 它连"扩展点"本身都是隐式的（没有公开的插件 API），**而是靠"工具 + 外围层"**。

**对比**：

| | Claude Code | DSH / 我们的 lab |
|---|---|---|
| 扩展方式 | **加工具 / 加外围层** | 加插件（有正式契约） |
| 契约 | ❌ 无公开契约 | ✅ Service Definition |
| 第三方能扩展吗 | ⚠️ 受限（MCP / hooks / skills） | ✅ 可以 |

**这个对比很有价值**：

> **"最小核心 + 厚外围"和"插件树"是两个不同的可扩展性路线。**
>
> **前者适合单一产品（团队自己加层），后者适合生态（第三方加插件）。**

### 0.3 为什么它要做"厚外围"

**从它的场景看**：

| 需求 | 需要的"层" |
|---|---|
| 大规模代码库 | 搜索 / 探索子代理 |
| 长任务 | 压缩 |
| 危险操作 | 权限 |
| 团队协作 | worktree / 邮箱 / 协调者 |
| 用户定制 | skills / hooks / MCP |

**这些都是"在外围加的"。**

**对你的启示**：

> **做 harness 时，先问"我的核心循环最小能到什么程度"。**
> **因为核心越小，它能被复用的范围越大。**

## L1 · 架构地图

**⚠️ 本节的所有内容都是二手，仅供理解形状，不要引用具体名字。**

### 1.1 一个保守的架构形状

**综合多来源，可以画出这样的形状**（❓ 结构性推断）：

```
┌──────────────────────────────────────────────────┐
│  外围层（"thick harness"）                        │
│  权限 · 压缩 · 子代理 · 技能 · hooks · MCP ·      │
│  会话持久化 · 任务规划 · worktree 隔离            │
└──────────────────────┬───────────────────────────┘
                       │ 包裹
                       ▼
┌──────────────────────────────────────────────────┐
│  核心循环（"minimal loop"）                        │
│                                                    │
│    while (还有事做) {                              │
│      response = 调模型(messages, tools)             │
│      if (response 没有工具调用) break               │
│      执行工具 → 结果塞回 messages                   │
│    }                                               │
└──────────────────────────────────────────────────┘
                       │ 调用
                       ▼
              模型 API（Claude）
```

**这张图里，只有"核心循环"是我比较确信的**（因为它和所有 agent 一样，没有别的做法）。

### 1.2 三个"层"的具体形态（⚠️ 均为转述）

#### 层 1：上下文压缩（多来源一致 ✅ 存在，细节 ⚠️）

**"多层策略"这个结论是可信的**，因为：

- 多个独立分析都描述了分层
- 而且**逻辑上必要**（一次任务可能触发多种压缩需求）

**报告的分层**（⚠️ 具体名称与阈值不确定）：

| 层 | 触发 | 做什么 |
|---|---|---|
| microcompact | 每轮 | 清掉陈旧的工具结果（**cache 感知**：只压不在缓存里的尾部） |
| snip | 消息太长 | 删中间的老消息（保留系统提示 + 近期轮次） |
| 自动摘要 | 接近容量上限 | fork 一个子代理做结构化摘要 |
| session memory | 同上 | 用持续维护的"会话记忆"代替完整摘要 |
| context collapse | 读时 | **读时投影**（像数据库视图），不改原消息 |
| reactive compact | 413 错误 | 紧急兜底 |

**其中"context collapse 是读时投影"这一条**（⚠️ 单一来源）**如果为真，非常精彩**：

> **它不在写的时候改数据，而在读的时候投影 —— 原始数据不动。**

**这和我们第 7 步的"只存事实、派生视图"是同一个思想**（虽然我们的场景不同）。

**⚠️ 还有一个细节**（单一来源，谨慎）：

> 压缩后系统会恢复"最近读的 top 5 个文件"，并重新注入 skills 和当前 plan。

**如果为真**，说明**压缩不是无脑摘要，而是要重建"工作现场"**。

**这个洞察值得学**：压缩的目标不是"变短"，而是"**在变短的同时保住继续工作所需的状态**"。

#### 层 2：子代理（✅ 官方文档有用法层，⚠️ 实现层不确定）

**官方文档层面（✅）**：

- 有 `Task` / Agent 工具
- 支持 `isolation: "worktree"`（在临时 git worktree 里跑，无改动则自动清理）
- **非 fork 的子代理从全新上下文开始**，只拿到 `prompt` 字符串（**所以父代理必须显式传递路径和错误**）
- 内置类型：general-purpose / Explore（只读、一次性）/ Plan / Verification

**⚠️ 转述的实现细节**：

| 说法 | 说明 |
|---|---|
| in-process teammate | 同进程，用 `AsyncLocalStorage` 隔离上下文 |
| **fork 模式** | 子进程，**新 `messages[]` 但共享父的 file-state cache 和 prompt-cache 前缀** |
| 文件邮箱 | `~/.claude/mailboxes/` 之类，轮询通信 |
| Coordinator / swarm | 协调者模式与"自动认领任务"模式 |

**"fork 共享 prompt-cache 前缀"这一条**（⚠️）**如果为真，很精巧**：

> **子代理理论上应该"完全隔离"，但它故意保留缓存前缀以省钱。**

**这是"隔离"与"成本"的又一次权衡** —— 和 Hermes 的"技能注入用 user 消息"是同一类取舍。

**✅ 官方文档明确的一条重要的**：

> **非 fork 子代理只拿到 prompt 字符串，没有父对话历史。**

**这条对使用者影响很大**（你必须显式传递所有上下文）—— **而它是官方文档说的，可以放心引用。**

#### 层 3：权限（⚠️ 细节存疑）

**官方文档层面（✅）**：有权限模式、有审批。

**⚠️ 转述**：有"两阶段分类器"（先小范围扫描，再大范围推理）。

**⚠️⚠️ 单一来源**：有 `tengu_` 前缀的隐藏 feature flag（88+ 编译期 / 600+ 运行期），以及"反蒸馏"机制（往 API 流量里注入假工具）。

**第二条我持保留态度** —— **这类"内幕"最容易是编的。**

## L2 · 关键机制拆解

### 2.1 唯一能放心讲的一条：prompt-cache 稳定性

**"prompt-cache 稳定性是核心设计驱动"这个结论**（⚠️ 多来源一致，且**逻辑上必然**）。

**为什么必然？**

```
Claude Code 的会话很长（可能几十轮）
   ↓
每轮都重发全部历史
   ↓
如果不命中缓存 → 每次请求都全量计费
   ↓
长会话的成本会爆炸
```

**所以它必须保证"前缀不变"** —— 而这意味着：

| 不能做的事 | 原因 |
|---|---|
| 改系统提示 | 整个前缀失效 |
| 在历史中间插入内容 | 后面的全失效 |
| 改工具注册顺序 | 工具定义在系统提示区 |
| 改消息的序列化格式 | 字节不同 = 缓存不命中 |

**这一条对我们的教学价值最大** —— **它把"缓存友好"从一个模糊的性能建议，变成了具体的架构约束。**

**我们的 lab 在第 1 步就遇到过**（`rawArguments` 保真），但**没有系统地考虑它**。

**第 8 步（循环）应该显式地把这条列为设计约束。**

### 2.2 从"压缩"学到的三件事

**即使具体数字不可信，"压缩该怎么做"这三条是可信的**：

#### ① 压缩必须是分层的

**理由**：不同的压力需要不同的对策。

| 压力 | 对策 |
|---|---|
| 几个陈旧工具结果 | **局部替换**（最便宜） |
| 消息太多 | **删中间**（保留头尾） |
| 接近上限 | **摘要**（最贵） |
| 已经报错 | **紧急兜底** |

**我们第 10 步的 `compaction-basic` 只做了"摘要"这一层** —— **太粗。**

#### ② 压缩必须 cache 感知

**"只压不在缓存里的部分"**（⚠️ 但如果为真，非常聪明）：

> **压缩本身会破坏缓存 —— 所以"压缩节省的 token"必须大于"缓存失效的代价"。**

**这是一个可以计算的决策**：

```
节省 = 被清掉内容的 token 数
代价 = 缓存失效导致后续请求的额外成本
如果 节省 < 代价 → 不压
```

**这个思路值得借鉴**（虽然我们的场景简单得多）。

#### ③ 压缩要"重建工作现场"，不只是"变短"

**恢复最近读的文件、重新注入 skills 和 plan**（⚠️ 若为真）。

**这解释了压缩的真正目标**：

> **不是"让上下文变短"，而是"保留继续工作所需的状态，丢掉可以重新获取的"。**

**判断标准**：

| 内容 | 该丢吗 |
|---|---|
| 读过的大文件内容 | ✅ 丢（能重读） |
| 当前计划 | ❌ 留（重建成本高） |
| 用户的关键指令 | ❌ 留 |
| 失败的错误信息 | ⚠️ 看情况 |

### 2.3 一条我认为值得警惕的"发现"

**⚠️ 转述**：有分析称，曾经有 **1,279 个会话出现了最多 3,272 次连续压缩失败**，每天浪费约 **25 万次 API 调用**，修复是**三行代码**（加熔断）。

**我对这个数字持保留态度**（⚠️ 单一来源 + 细节过于戏剧化）。

**但它指向的工程问题是真的**：

> **一个反复失败但被无限重试的操作，会形成"资源黑洞"。**

**这正好呼应我们第 7 步 L9 缺陷 6 和第 4 步缺陷 6**（"挂起的插件没有超时"、"没有熔断"）。

**无论那个数字真假，"加熔断"这个教训都是对的。**

| 核心循环 | **刻意最小** | 第 8 步（计划） | ⭐⭐⭐ **设计原则** |
| 上下文压缩 | **多层 + cache 感知 + 重建现场** | 第 10 步（计划单层） | ⭐⭐⭐ **要补** |
| 子代理 | ✅ 多种模式（含 worktree） | 不在范围内 | ⭐ 了解即可 |
| prompt-cache 稳定性 | **核心设计驱动** | 未系统考虑 | ⭐⭐⭐ **要补** |
| 权限 | ✅ 有 | 第 10 步 | ⭐⭐ |
| 插件系统 | ❌ **没有公开的**（MCP/hooks/skills 是接口） | 第 3–6 步 | ⭐⭐ **对照** |
| 会话持久化 | ⚠️ 未知格式 | 第 7 步 JSONL | ❌ |
| 不变量（Model-visible ⟺ logged） | ❓ **不知道有没有** | 第 7 步明确实现 | ❓ |
| 开源 | ❌ | ✅ | — |

### 3.1 最值得注意的一行：**插件系统**

**我没有在任何可信来源里看到 Claude Code 有"正式的插件系统"**（像 DSH 的 Service Definition 那样）。

**它提供的是**：

| 扩展方式 | 形态 |
|---|---|
| **MCP** | 外部工具服务器 |
| **hooks** | 生命周期钩子（shell 命令） |
| **skills** | Markdown 工作流 |
| **子代理** | 预定义/自定义 agent |

**这些都是"接口"，不是"插件契约"** —— **你无法替换它的会话实现、它的压缩策略、它的循环。**

**对比**：

| | Claude Code | DSH / 我们的 lab |
|---|---|---|
| 能换压缩策略吗 | ❌ | ✅（换个插件） |
| 能换循环吗 | ❌ | ✅ |
| 能加工具吗 | ✅（MCP） | ✅ |
| 能加 hooks 吗 | ✅ | ✅（第 4 步的事件） |

**这个对比说明了两条路线的适用场景**：

> **Claude Code：一个产品，团队控制核心，用户扩展能力。**
> **DSH / 我们：一个平台，连核心都可替换。**

**对你的科研的意义**：

> **做"干预 vs 自我修正"的对照实验，你需要能换掉中间机制 —— 所以插件式架构更适合研究。**

## L4 · 可迁移的设计模式

### 模式 1 · 「最小核心 + 厚外围」

**核心循环什么都不做，只做"调模型 → 执行工具 → 回填"。** 其余全在外围。

**可迁移性**：⭐⭐⭐ **这是做 harness 的第一原则。**

**检验方式**：**问自己"我的核心循环里有多少个 `if`？"** —— 每多一个，就说明有个机制本该在外围。

### 模式 2 · 「缓存友好的架构约束」

**把"前缀不变"当作硬约束**，它约束了：系统提示、工具顺序、消息序列化、压缩时机。

**可迁移性**：⭐⭐⭐

**具体落到我们的第 8 步**：

| 约束 | 我们的做法 |
|---|---|
| 系统提示别改 | 第 12 步的"冻结快照" |
| 工具顺序别变 | `ToolRegistry` 保持插入顺序（第 2 步已做到） |
| 消息序列化别变 | `rawArguments` 保真（第 1 步已做到） |

**我们已经**无意中**做对了两条，但没有系统地想它。**

### 模式 3 · 「分层压缩」

**按压力大小分层，每层的代价不同。**

**可迁移性**：⭐⭐⭐ 直接对应第 10 步的改进。

### 模式 4 · 「压缩 = 重建工作现场」

**压缩后要恢复"继续干活所需的最小状态"**，不只是"变短"。

**可迁移性**：⭐⭐⭐

### 模式 5 · 「子代理默认隔离，但可选择性共享缓存」

**非 fork 完全隔离；fork 共享缓存前缀。**

**可迁移性**：⭐⭐（我们不做子代理，但"隔离 vs 缓存"的权衡是通用的）

### 模式 6 · 「熔断」

**一个反复失败的操作必须能停下来。**

**可迁移性**：⭐⭐⭐ **直接对应我们第 4、7 步发现的"挂起/失败没有上限"缺陷。**

## L5 · 弱点与争议

### 5.1 架构上的（❓ 推断）

| 弱点 | 理由 |
|---|---|
| **没有公开的插件契约** | 用户无法替换核心机制 |
| **闭源** | 无法审计（**对科研是硬伤**） |
| **绑定 Anthropic 模型** | 换模型的优化无从谈起 |
| **复杂度在外围** | "12 层"的说法如果是真的，**外围会很难理解** |

**第二条对你是最关键的**：

> **你的研究要"可复现、可审计" —— 而一个闭源系统的内部行为你无法验证。**
>
> **所以把 Claude Code 当作"对照基线"可以，当作"研究对象"不行。**

### 5.2 信源层面的争议（★ 这一条最重要）

**我在调研过程中发现的最大问题不是 Claude Code 本身，而是关于它的信息生态**：

| 现象 | 后果 |
|---|---|
| 大量"深度分析"文章 | **无法分辨哪些基于真源码** |
| 带未来日期的论文/预印本 | **可能是 AI 生成的推测** |
| 精确的常量与函数名 | **最容易是幻觉，也最容易被引用** |
| 相互转载 | **错误会被放大成"共识"** |

**这不是 Claude Code 的问题，是这个领域的"信源污染"。**

## L6.5 · 怎么读逆向分析 ★ 比本篇任何事实都有用 ★

**这一节是方法论。它不只用于读 Claude Code，也用于读任何闭源系统的分析文章。**

### 6.5.1 三个层级的信息

**读一篇逆向分析时，先把它的内容分成三层**：

| 层 | 特征 | 可信度 |
|---|---|---|
| **结构性** | "它有一个压缩机制" / "它用子代理" | **通常可信**（能从行为观察到） |
| **机制性** | "压缩是分层的：先清工具结果，再删中间，最后摘要" | **中等**（需要读代码才能得出） |
| **参数性** | "阈值是 13,000" / "函数名是 `s$`" | ⚠️ **最低**（最容易幻觉） |

**危险的是**：**文章往往把三层混在一起写，读起来一样确定。**

### 6.5.2 五个危险信号

| 信号 | 为什么危险 |
|---|---|
| **精确到个位的数字** | 真源码里的阈值常是整数（`13_000`），但**引号里的"精确值"最爱被编** |
| **混淆后的符号名**（`s$`、`nO`） | 这些名字**看起来"很像真的"** —— 但正因如此最难验证 |
| **"内部 bug 报告显示…"** | 无法核实，且**故事性好**（易传播） |
| **带未来日期的引用** | 直接暴露生成来源 |
| **单一来源** | 没有交叉验证 |

### 6.5.3 三个验证动作

**① 找"官方文档里有吗"**

```bash
# 官方文档说的（如 subagent 的 worktree 隔离）→ 可用
# 官方文档没说、只有逆向文章说的 → 标注"据逆向分析"
```

**② 找"多个独立来源一致吗"**

**两个互相不知道对方存在的分析得出同一结论 → 可信度大增。**

**三个以上来源引用同一个"原始出处" → 其实只有一个来源。**

**③ 问"这个结论能在行为上验证吗"**

| 结论 | 能验证吗 |
|---|---|
| "它有压缩" | ✅ 跑长任务，观察上下文变化 |
| "阈值是 13000" | ⚠️ 要构造精确的边界测试 |
| "反蒸馏会注入假工具" | ❌ 几乎无法验证 |

**能验证的结论才值得引用。**

### 6.5.4 一个实用的写法

**引用这类信息时的模板**：

```
据[来源等级]，Claude Code 的压缩是分层的
（⚠️ 多来源一致，但具体阈值未核实）。

如果这一条成立，那么对我们的启示是……
```

**关键是把"事实"和"启示"分开** —— 因为**即使事实是错的，启示可能仍然有用**。

**这一条也适用于你读我自己写的这份文档。**

**关于信源（★ 本篇特有）**

5. ★ **我读的那篇分析里，哪些是结构性的、哪些是参数性的？**
6. ★ **那个数字有几个独立来源支持？**
