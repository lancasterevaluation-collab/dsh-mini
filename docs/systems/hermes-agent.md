## 第 0 节 · 这个系统是什么

### 0.1 一句话定位

> **一个"从经验中长技能、并且自动修剪技能"的自改进智能体。**

**官方的一句话**（✅ 来自官方文档 / PyPI）：

> "the only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, and builds a deepening model of who you are across sessions."

### 0.2 基本事实

| 项 | 值 | 等级 |
|---|---|---|
| 作者 | Nous Research | ✅ |
| 许可证 | MIT | ✅ |
| 语言 | Python（`uv` 管理依赖） | ✅ |
| 形态 | 长运行运行时 / 研究导向的记忆·技能智能体 | ✅ |
| 入口 | CLI（`cli.py`）、Gateway（20+ 消息平台）、**ACP**（VS Code / Zed / JetBrains） | ⚠️ |
| 工具 | 70+ 工具 / 28 toolsets，`tools/registry.py` 中心注册表 | ⚠️ |
| 会话存储 | **SQLite + FTS5 全文检索** | ⚠️ |
| 文档 | `hermes-agent.nousresearch.com` | ✅ |

### 0.3 它与其他 harness 的根本差异

**一句话**：

> **别的 harness 问你"要装什么插件"；Hermes 问自己"这次学到了什么"。**

**具体对比**：

| | OpenClaw | DSH | **Hermes** |
|---|---|---|---|
| 技能从哪来 | **用户手写** | 插件自带 | **agent 从经验生成** |
| 谁维护技能 | 用户 + 社区 | 包作者 | **Curator 自动** |
| 记忆 | 未知 | 会话日志 | **有界文本 + 用户建模** |
| 闭环 | ❌ | ❌（只有 `extensions/` 的运行时改插件） | **✅ 完整** |

**DSH 没有这个东西** —— 这正是我们 lab 的差异化定位（见 `../00-course-map.md`）。

### 0.4 在 Harness-Bench 里的位置

| harness | 总分 | 完成度 | 过程分 | 工具 | 一致性 | token(K) | 轮数 |
|---|---|---|---|---|---|---|---|
| **Hermes** | **71.2** | 80.4 | 100.0 | 88.5 | 88.4 | **139.7** | **22.6** |
| NanoBot | 76.2 | 81.6 | 100.0 | 93.8 | 93.7 | 68.7 | 7.3 |

**两个观察（❓ 我的解读）**：

1. **它的 token 和轮数都是最高的**（139.7K / 22.6 轮）—— 说明它**愿意花更多步骤**。
2. **但总分不是最高**（NanoBot 用一半的 token 拿到更高分）。

**论文自己的解读**（✅ 你本地中译）：

> "token 与轮数用量也随配置变化：NanoBot 取得可配置 harness 中最高的分数，同时使用的 token 少于 Hermes、ZeroClaw、NullClaw 与 Moltis，**这说明更长的轨迹本身并不决定性能**。"

**但这里有一个值得追问的点**：

> **Hermes 的"多花的轮数"，有多少是花在"学习和记忆"上的？**
>
> **如果它的轮数包含"复盘"和"技能维护"，那这个对比就不是同维度的** —— 因为那些轮数产生的是**跨会话的资产**，而 Harness-Bench 是单次评测。

**这是一个真实的方法论问题**，也是**你可以研究的点**：

> **"学习型 harness 的价值，能不能用单次任务的 benchmark 衡量？"**

## L0 · 它要解决的问题

**Hermes 的问题陈述比 OpenClaw 更明确**（因为它自己反复强调"learning loop"）。

### 0.1 它明确针对的三类失败

| 失败 | Hermes 的解法 |
|---|---|
| **重复踩同一个坑** —— 每次任务都从零开始 | **有界记忆**（MEMORY.md） |
| **用户偏好每次都要重说** | **用户建模**（USER.md + Honcho） |
| **摸索出来的流程用完就忘** | **技能自动生成**（SKILL.md） |

### 0.2 但真正的创新在"怎么防止这些东西烂掉"

**这是 Hermes 最有洞察的地方**：

> **一个"能自己积累知识"的系统，如果不加约束，会积累出一堆垃圾。**

**它用三道防线解决这个问题**：

| 防线 | 机制 | 防的是什么 |
|---|---|---|
| **1. 有界** | 文件有硬字符上限，**写满就拒绝** | 无限膨胀 |
| **2. 自动修剪** | Curator 按时间归档不用的技能 | 陈旧内容堆积 |
| **3. 可审计** | 追加式账本 + 备份 + 回滚 | 自动修改失控 |

**这三条防线就是你要在第 12–16 步实现的东西。**

### 0.3 一个反直觉的设计：写满时**失败**，而不是**丢弃最旧的**

**这是 Hermes 最值得学的机制**（⚠️ 二手，但多个来源一致）：

```
模型想往 MEMORY.md 加一条
   ↓
如果加了会超过 2,200 字符
   ↓
★ 不写入，并返回「当前所有条目」★
   ↓
模型必须自己决定：合并哪些、删哪些、怎么压缩
```

**对比两种设计**：

| 设计 | 行为 | 后果 |
|---|---|---|
| **自动淘汰最旧的**（常见做法） | 静默丢弃 | **模型不知道丢了什么** |
| **加不进去，返回现状**（Hermes 的做法） | **强迫模型做决策** | 模型必须真的思考"什么值得留" |

**为什么这个设计好？**

> **它把"信息压缩"的责任从"淘汰策略"转移到了"模型"身上。**
>
> **而有上下文的模型，比一个 LRU 算法更知道什么重要。**

**代价**：**模型可能反复尝试写入并失败**（浪费轮数）。

**这解释了 Harness-Bench 里 Hermes 轮数最高的现象**（22.6 轮）—— ❓ 部分轮数可能花在"合并记忆"上。

**对你的启示**：

> **你的第 12 步必须实现"写满即拒绝 + 返回现状"。**
> **这不是"省事"，而是这个设计的核心。**

## L1 · 架构地图

### 1.1 核心类与入口（⚠️ 二手，但引用了具体文件）

```
run_agent.py            ★ AIAgent 类 —— ReAct 循环
                          负责：provider 选择、prompt 构建、工具执行、
                                重试/降级、回调、上下文压缩、持久化
cli.py                  CLI 入口
gateway/run.py          Gateway 入口（20+ 消息平台）
gateway/session.py      网关侧的会话管理
acp_adapter/            ACP 入口（VS Code / Zed / JetBrains）
hermes_state.py         状态/存储（SQLite + FTS5）
```

**注意 `AIAgent` 的职责列表**（⚠️ 二手）：

> provider 选择、prompt 构建、工具执行、重试/降级、回调、上下文压缩、持久化

**它把七件事放在一个类里。**

**对比我们的设计**：

| 职责 | Hermes（⚠️） | 我们的 lab |
|---|---|---|
| provider 选择 | `AIAgent` | 第 1 步的 `Provider` + 第 6 步配置 |
| prompt 构建 | `AIAgent` | 第 8 步计划 |
| 工具执行 | `AIAgent` | 第 2 步 `ToolRegistry` |
| 重试 | `AIAgent` | 第 9 步独立插件 |
| 上下文压缩 | `AIAgent` | 第 10 步独立插件 |
| 持久化 | `AIAgent` | 第 7 步 `Session` |

**Hermes 是"一个大的 agent 类"，我们是"一组插件"。**

**这不是"谁更好"，是**两种架构哲学**：

| | Hermes（单体类） | 我们 / DSH（插件树） |
|---|---|---|
| 可读性 | ✅ 一处看全 | ⚠️ 要跨文件 |
| 可替换性 | ❌ 换重试策略要改类 | ✅ 换个插件 |
| 可测试性 | ⚠️ 要构造整个 AIAgent | ✅ 单测那个插件 |
| 上手难度 | ✅ 低 | ⚠️ 高（要先懂框架） |

**对科研的意义**：

> **你要做"干预 vs 自我修正"的对照实验 —— 插件架构让"换掉一个机制"变得容易。**
> **而单体架构下，你要 fork 一份代码。**

**这是我们选择插件架构的一个实际理由。**

### 1.2 工具系统（⚠️ 二手）

| 项 | 值 |
|---|---|
| 中心注册表 | `tools/registry.py` |
| 数量 | 70+ 工具 / 28 toolsets |
| 注册方式 | **每个工具文件在 import 时自注册** |
| 执行后端 | 7 种终端（local / Docker / SSH / Singularity / Modal / Daytona / Vercel Sandbox） |
| 其他 | 5 种浏览器、4 种 web、MCP |

**两个值得注意的点**：

**① "import 时自注册"**

```python
# 伪代码
# tools/xxx_tool.py 的末尾
register(MyTool())
```

**这是"模块副作用即注册"** —— 简单，但**依赖 import 顺序**。

**对比我们第 3 步的 `provide()`**：我们是**显式调用**（`ctx.provide('name', value)`），**副作用是登记的**（可撤销）。

**Hermes 的方式不可撤销** —— 一旦 import 就注册了。

**② 7 种终端后端**

**这是一个"执行世界可替换"的设计** —— 和我们第 5 步的 scope（服务隔离）思路不同：

| | Hermes | 我们 / DSH |
|---|---|---|
| 换执行环境的方式 | **换终端后端** | 换 `subprocess` / `sandbox` provider |
| 粒度 | 整个工具执行 | 按能力接缝 |

**DSH 的对应**：`packages/subprocess/`（本地进程树）+ `packages/ssh/`（远程）+ `packages/sandbox/`。

### 1.3 会话存储（⚠️ 二手）

**SQLite + FTS5 全文检索。**

**这个选择的意义**：

```
会话很多之后：
  纯文件遍历 → 慢
  SQLite FTS5 → 快（~200ms 级检索）
```

**对比 Hermes 自己的记忆存储**：

| 数据 | 存储 | 为什么 |
|---|---|---|
| **记忆**（MEMORY.md / USER.md） | **纯文本文件** | **可读、可审计、可手改** |
| **会话历史** | **SQLite** | **量大会话的检索** |

**同一个系统里两种存储** —— **这是"按用途选存储"而不是"统一技术栈"。**

**对你的直接启示**：

> **第 12 步的记忆用纯文本（可审计），第 14 步的检索用 SQLite FTS5（快）。**
> **这不是"两个技术"，是"两个用途"。**

**而 Node 内置的 SQLite 恰好支持 FTS5**（我们在环境核查时验证过）。

### 1.4 设计原则（⚠️ 二手，但很有参考价值）

**据一份架构分析，Hermes 明示的设计原则包括**：

| 原则 | 对应我们的 |
|---|---|
| **prompt stability**（系统提示在会话中途冻结，以保留 Anthropic 的 prefix cache） | 第 1 步提过 KV cache |
| **observable execution** | 第 7 步的会话日志 |
| **interruptibility** | 第 8 步的取消 |
| platform-agnostic core | ❌ 我们不做多渠道 |
| loose coupling | 第 3 步的插件 |
| **profile isolation**（`hermes -p <name>`） | 第 6 步的 profile |

**第一条最值得注意**：

> **"系统提示在会话中途冻结"** —— 因为改了它就会**破坏 prefix cache**，让后续所有请求变贵。

**我们在第 1 步讨论过 KV cache**（`rawArguments` 保真），**但没有"冻结系统提示"这个约束**。

**为什么 Hermes 需要？** 因为它要往系统提示里注入**技能内容**。

**而它的解法很巧妙**（见 2.4）。

## L2 · 关键机制拆解 ★ 本篇核心 ★

**这一节是你第 12–16 步的直接参考。**

### 2.1 有界记忆（第 12 步的参考）

#### 两个文件

| 文件 | 存什么 | 上限 | 等级 |
|---|---|---|---|
| `MEMORY.md` | agent 自己的笔记（环境事实、项目约定、工具怪癖） | **2,200 字符** | ⚠️ |
| `USER.md` | 用户的偏好、沟通风格、习惯 | **1,375 字符** | ⚠️ |

**为什么要分成两个？**

> **因为它们的"失效模式"不同。**
>
> - `MEMORY.md` 的内容**随项目变化**（换个环境就过时）
> - `USER.md` 的内容**跨项目稳定**（用户偏好不会因为你换项目就变）

**这个区分对应你的第 14 步的"用户建模"** —— 它也是要独立于环境事实的。

#### 核心机制：写满即拒绝

**（0.3 节已详述）** 关键在于：

```
add 失败 → 返回现有条目 → 模型自己合并
```

**还有一个细节**（⚠️ 二手）：

> `MemoryStore` 维护着"实时可写的条目" **加上一个在会话开始时拍的冻结快照**。

**为什么要有"冻结快照"？**

```
会话开始时：拍一个快照
   ↓
会话中模型改了记忆
   ↓
但**当前会话看到的系统提示**用的是快照（不变）
   ↓
下次会话才看到新的
```

**这是"prompt stability"原则的具体实现** —— **记忆变了，但不改当前会话的提示。**

**代价**：模型在本次会话里"看不到"自己刚写的东西。
**收益**：prefix cache 不被破坏 → **成本大幅降低**。

**这是一个非常好的取舍案例** —— **用"即时性"换"成本"。**

#### `target` 参数（⚠️ 二手）

`memory` 工具有一个 `target` 参数（`user` vs `memory`）。

**并且有一个 PR（#30227）专门修"用户画像的事实被写进环境事实存储"这个路由 bug。**

**这个 bug 的类型值得注意**：

> **两个存储的语义边界，在实际使用中很容易被模型搞混。**

**我们的第 12 步应该显式地在工具描述里写清"什么该写哪个"** —— 而不是靠模型猜。

#### 安全检查（⚠️ 二手）

> 记忆内容会被扫描 prompt-injection / deception / exfiltration 模式（`_MEMORY_THREAT_PATTERNS`）。

**为什么？**

> **因为记忆会被注入到系统提示里** —— 而系统提示是**最高优先级**的。
>
> **如果有人能污染记忆文件，就等于能在系统提示里注入内容。**

**这是一个真实且严峻的攻击面**，而 Hermes **把它当作一等公民处理**。

**对你的启示**：

> **第 12 步实现记忆时，必须意识到"记忆 = 持久化的提示注入入口"。**
>
> 尤其是在**多用户**或**从外部导入记忆**的场景下。

### 2.2 技能系统（第 13 步的参考）

#### 格式（⚠️ 二手）

```
~/.hermes/skills/<name>/SKILL.md      ← YAML frontmatter: name / description / version
                          references/  ← 可选
                          templates/   ← 可选
                          scripts/     ← 可选
```

**遵循 `agentskills.io` 开放标准**。

**这个"一个目录 + 多种可选子目录"的结构**，正是**渐进式披露**的物理形式：

```
只给模型看 name + description
   ↓ 需要时
读 SKILL.md 全文
   ↓ 需要时
读 references/ 下的具体文件
```

**这是"三层披露"** —— 比我们第 13 步计划的"两层"更细。

#### 自动创建的条件（⚠️ 二手，引用 tool schema）

**模型会在这些情况下创建技能**：

| 条件 | 含义 |
|---|---|
| **复杂任务成功（5+ 次工具调用）** | 这个流程值得记 |
| **克服了错误** | 这里有个坑，值得记 |
| **用户纠正后的方法奏效** | 用户的偏好值得记 |
| **发现了非平凡的流程** | 有复用价值 |

**注意第一条的"5+"是个硬阈值** —— **它防止"每个小任务都生成一个技能"。**

**这是"生成门槛"的设计** —— 值得你在第 13 步直接采用。

#### 自我修补（self-patching）（⚠️ 二手）

> **`_patch_skill()` 用模糊匹配的查找-替换引擎**，让 agent 做定点修复而不是整篇重写。

**工具 schema 里的原话**：

> "If you used a skill and hit issues not covered by it, patch it immediately."

**为什么"定点修复"很重要？**

| 做法 | 后果 |
|---|---|
| 整篇重写 | **已验证的部分可能被改坏** |
| **定点修补** | 保留已验证内容，只改出问题的地方 |

**这是"最小改动"原则在自动演化里的应用。**

**而它的技术前提是"模糊匹配的查找替换"** —— 因为 agent 记不住确切文本。

#### 注入策略（★ 这个设计最精妙 ★）

**（⚠️ 二手，但多来源一致）**

> **加载的技能内容作为 User Message 注入，而不是追加到 system prompt。**

**为什么？**

> **因为追加到 system prompt 会破坏 Anthropic 的 prefix cache。**

**具体机制**：

```
system prompt（冻结，不变）          ← 缓存命中
user: 任务描述
assistant: ...
user: [SYSTEM: 以下是技能 X 的内容]   ← ★ 技能作为 user 消息注入
      ...技能正文...
```

**`[SYSTEM: ...]` 前缀是为了提高模型的遵从度** —— 但它在**格式上仍是 user 消息**。

**这个取舍太精彩了**：

| 方案 | 遵从度 | cache |
|---|---|---|
| 追加到 system prompt | ✅ 高（系统级） | ❌ 破坏（后续全贵） |
| **作为 user 消息注入** | ⚠️ 中（但加 `[SYSTEM:]` 前缀补偿） | ✅ 保留 |

**它用"前缀标记"来弥补"格式降级"带来的遵从度损失。**

**官方仓库里甚至有一条硬规则**（⚠️）：

> **"Prompt Caching Must Not Break."**

**对你的启示**：

> **第 13 步注入技能时，要用 user 消息 + 显式标记，不要改系统提示。**

### 2.3 Nudge Engine 与后台复盘（★ 第 12 步的另一半 ★）

#### Nudge Engine（⚠️ 二手）

**周期性内部提示**，催 agent 在上下文填满前沉淀知识。

**为什么需要它？**

> **因为"想记"和"真的记"之间有一条鸿沟。**
>
> 模型在任务中途不会主动停下来写记忆 —— 它专注于任务。
> **所以框架要主动提醒它。**

**这对应我们第 12 步计划里的 `nudge.ts`。**

#### 后台复盘 fork（⚠️ 二手，但细节很具体）

**会话结束后**：

```
fork 一个 AIAgent
  ├─ max_iterations = 8
  ├─ quiet_mode = True（stdout/stderr 重定向到 /dev/null）
  ├─ 审查整个轨迹
  └─ 写 skills / memory
```

**两套提示**：

| 提示 | 针对 |
|---|---|
| memory review | **用户偏好** |
| skill review | **非平凡流程** |

**两套提示的结尾都是同一句**：

> **"If nothing is worth saving, just say 'Nothing to save.' and stop."**

**这句话太重要了。**

**为什么？**

因为它**明确给了模型"什么都不做"的许可**。

**对比"反例"**（同一个系统的早期版本）：

> 早期提示有 "Be ACTIVE… a pass that does nothing is a missed learning opportunity" 这样的**施压语言**。

**后来 PR #30227 把它去掉了**，因为：

> **它导致模型为了"显得有在学习"而写入低价值内容。**

**这是一个极有价值的教训**：

> **如果你给模型施加"必须学到点什么"的压力，它会开始编造学习成果。**
>
> **"Nothing to save" 必须是一等公民的结果，而不是失败。**

**这正是你工作手册里"沉默型问题"的一个新实例**：

| 表现 | 真相 |
|---|---|
| 记忆/技能在增长 | **但增长的是垃圾** |
| 复盘"有产出" | **产出的是为了交差的内容** |

**而它不报错、不掉分。**

#### 递归防护（⚠️ 二手）

> **把复盘 agent 自己的 nudge 间隔清零**，防止复盘又触发复盘。

**这是一个必要的防护** —— 否则复盘会无限递归。

**同时它"共享主 agent 的 `_memory_store`"** —— 这样复盘写的东西主 agent 立刻可见。

### 2.4 Curator：技能的自动维护者（★ 第 13 步的核心参考 ★）

**这是 v0.12.0 的核心特性**（✅ 来自官方 release notes 和 docs）。

#### 运行方式（✅）

```
hermes curator
  ├─ 作为后台 agent 跑在 gateway 的 cron ticker 上
  ├─ 默认周期：7 天（interval_hours: 168）
  ├─ min_idle_hours: 2（闲置 2 小时才跑）
  ├─ umbrella-first prompt（先归并，再逐个处理）
  ├─ 继承父配置
  └─ 无迭代上限
```

#### 两个阶段（✅ 这是最值得学的部分）

```
阶段 1：自动的确定性转换（★ 不用 LLM ★）
   ├─ 30 天没用 → stale
   └─ 90 天没用 → 移到 ~/.hermes/skills/.archive/

阶段 2：LLM 评审（单个辅助模型，max_iterations = 8）
   ├─ 巡视 agent 创建的技能
   ├─ 可以用 skill_view 看任意一个
   └─ 决定：保留 / 修补 / 合并 / 归档
```

**为什么分两阶段？**

| 阶段 | 用什么 | 为什么 |
|---|---|---|
| **确定性转换** | **纯规则，不用 LLM** | **便宜、可预测、不会出错** |
| LLM 评审 | 辅助模型 | 需要判断力（"这两个技能该合并吗"） |

**这是一个极其重要的设计模式**：

> **能用确定性规则做的，绝不交给 LLM。**
> **LLM 只用来做真正需要判断的事。**

**我在你的课程里已经埋了这条**（第 2 步的 `assertNever`、第 10 步的"守卫必须单调"），**但 Hermes 把它用在了"自动维护"这个新场景**。

#### ⚠️ 一个细节：`use_count == 0` 不等于"陈旧"

**Curator 源码里有一句**（⚠️ 二手，引用源码注释）：

> **`use_count == 0` 被视为"证据的缺失，而不是陈旧"。**

**为什么这个区分重要？**

```
一个刚创建但还没用过的技能：
   use_count = 0
   ↓
如果按"0 = 没人用 = 该归档"
   → ★ 刚学会的东西立刻被删掉 ★
```

**这又是一个"沉默型错误"的例子** —— **它不会报错，只是让学习成果不断蒸发。**

#### 配置（✅ 官方 docs）

```yaml
# config.yaml
curator:
  enabled: true
  interval_hours: 168        # 7 天
  min_idle_hours: 2
  stale_after_days: 30
  archive_after_days: 90
```

**LLM 评审用 `auxiliary.curator` 模型槽位。**

**"辅助模型槽位"这个设计值得注意**：

> **技能评审不需要最强的模型** —— 用一个便宜模型就够了。
>
> **这让"自动维护"的成本可控。**

**我们的第 13 步应该也有这个概念**（用 MockProvider 或者一个小模型做评审）。

#### CLI（✅）

```
hermes curator status | run | --dry-run | backup | rollback
              | pause | resume | pin | unpin | restore | ledger
```

**注意这几个命令**：

| 命令 | 作用 |
|---|---|
| `--dry-run` | **演练，不实际改** |
| `backup` / `rollback` | 备份与回滚 |
| `pause` / `resume` | 暂停自动维护 |
| `pin` / `unpin` | **钉住某个技能不让动** |
| `ledger` | **查审计账本** |

**这是一个"自动化功能"该有的完整控制面**：

> **能跑、能演练、能暂停、能回滚、能审计、能钉住例外。**

#### 备份与审计（★ 直接对应我们的第 16 步 ★）

**✅ 官方 docs 明确**：

| 机制 | 位置 |
|---|---|
| **合并前的 tar.gz 快照** | `~/.hermes/skills/.curator_backups/` |
| **追加式 JSONL 审计账本** | `~/.hermes/skills/.curator_ledger.jsonl` |

**账本支持"单次编辑回滚"**（通过内容寻址的 blob 存储）。

**注意这是 append-only JSONL** —— **和我们第 7 步的会话日志、DSH 的会话格式完全一致！**

**三个独立系统都用"追加式 JSONL 做审计"**：

| 系统 | 用途 |
|---|---|
| Hermes | 技能维护的审计账本 |
| DSH | 会话日志 |
| 我们的 lab | 会话日志（第 7 步） |

> **这是一个被反复验证的设计收敛。**

#### 只动自己创建的技能（✅）

**Curator 只管理 agent 自己创建的技能，绝不碰上游/用户手写的。**

**它用 `.bundled_manifest` 和 `.hub/lock.json` 区分来源。**

**这个"provenance（来源追踪）"设计非常重要**：

> **如果你分不清"这个技能是谁写的"，你就不敢自动改它。**

**我们的第 13 步必须实现这个区分。**

### 2.5 用户建模（第 14 步的参考）

#### Honcho 集成（⚠️ 二手）

**Plastic Labs 的 Honcho 集成**：

| 特性 | 说明 |
|---|---|
| 运行方式 | **异步**（不阻塞主流程） |
| 存什么 | **结论**（"用户偏好 TypeScript"），**不是原始对话** |
| 检索 | ~200 ms |
| 接口 | `honcho_profile` / `honcho_search` / `honcho_context` / `honcho_reasoning` / `honcho_conclude` |

**"存结论不存原文"这一条最关键**：

| 方案 | 存储量 | 检索速度 | 信息保真 |
|---|---|---|---|
| 存原始对话 | 大 | 慢 | ✅ 全 |
| **存派生结论** | **小** | **快** | ⚠️ 有损 |

**它牺牲了保真度换取"可用性"** —— 而且**它同时保留了原始对话**（在 SQLite 里），所以需要时还能回溯。

**这是"两级存储"**：

```
原始对话 → SQLite（全量，检索慢）
    ↓ 异步派生
结构化结论 → Honcho（少量，检索快，注入提示）
```

**对你的启示**：

> **第 14 步的"用户建模"不该只做检索，而应该做"派生结论"。**
> **因为结论可以被注入提示（小），原文不能（大）。**

## L4 · 可迁移的设计模式

### 模式 1 · 「有界 + 写满即拒绝」

// 伪代码
function add(entry: string): Result {

**迁移价值**：⭐⭐⭐ **直接可用在第 12 步。**

| 生成什么 | 建议门槛 |

**给模型明确的"什么都不做"许可，并且不施加"必须学到东西"的压力。**

**迁移价值**：⭐ **这是防"编造学习成果"的关键。**

**迁移价值**：**自动化功能必须能被停下来、被检视、被撤销。**

### 模式 8 · 「两级存储：原文 + 派生结论」

**迁移价值**：⭐⭐ 直接对应第 14 步。

## L5 · 已知问题与弱点

### 5.1 从 Harness-Bench 看

```
Hermes: 总分 71.2 / token 139.7K（最高）/ 轮数 22.6（最高）
```

**两个可能的解读**（❓ 都是推断）：

| 解读 | 支持证据 | 反对证据 |
|---|---|---|
| 它的"学习机制"消耗了额外轮数 | 轮数最高 | 单次评测里学习机制可能不触发 |
| 它更"肯干"（不轻易放弃） | 轮数最高，分数也不低 | token 成本高 |

**注意 Harness-Bench 是"每次任务独立评测"** —— **所以它的跨会话学习能力完全没被衡量。**

**这是一个真实的评测盲区**：

> **"学习型 harness"的价值无法在单次 benchmark 上体现。**

**这可以作为你的一个研究点**（"怎么评测会学习的 harness"）。

### 5.2 架构上的风险（❓ 推断）

| 风险 | 理由 |
|---|---|
| **`AIAgent` 类太大** | 七个职责在一个类里，改动风险高 |
| **记忆的注入是攻击面** | 记忆进系统提示 → 记忆污染 = 提示注入 |
| **技能质量不可控** | 自动生成 + 自动修补 + 自动归档，链条长 |
| **成本** | 辅助模型调用 + 复盘 fork + Curator，都是额外开销 |
| **`import` 时自注册的工具** | 不可撤销，依赖 import 行为 |

**第 3 条与第 5 条值得展开**：

**技能质量链条**：

```
生成（LLM 判断"值得记"）
  → 修补（LLM 判断"哪里该改"）
    → 归档（时间规则 + LLM 评审）
```

**每一环都可能出错，而且出错不会被立刻发现** —— **这正是"沉默型问题"的典型。**

**Hermes 的对策是"备份 + 账本 + 回滚"** —— **承认错误会发生，所以保证可撤销。**

> **这是"自动化"的正确态度：不是"保证不出错"，而是"出错能回退"。**

## L7 · 提问训练

### 本篇引出的 12 个好问题

**关于设计**

1. **为什么记忆要分两个文件（MEMORY / USER）？** 合成一个会怎样？
2. **为什么"写满即拒绝"比"淘汰最旧"好？** 代价是什么？
3. **为什么技能要以 user 消息注入？** 有没有别的办法既保遵从度又保 cache？
4. **为什么 Curator 分两个阶段？** 全程用 LLM 会怎样？
5. **为什么 `use_count == 0` 不算陈旧？** 不算会有什么后果？

**关于系统**

6. **`AIAgent` 把七个职责放在一个类里 —— 这对它有什么好处和代价？**
7. **复盘 fork 和主 agent "共享 memory store" —— 这会不会有并发问题？**
8. **"冻结快照"机制下，模型在本次会话看不到自己刚写的记忆 —— 这会不会导致重复写？**

**关于你的研究**

9. ★ **它没有"失败诊断"层 —— 这是它没想到，还是刻意的？**
10. ★ **"基于成功的学习"和"基于失败的学习"，哪个更适合你的任务域？**
11. ★ **怎么评测"会学习的 harness"？** 单次 benchmark 不行，那该设计什么？
12. ★ **把 Curator 的"备份 + 账本 + 回滚"和 HarnessX 的"确定性门控"结合，是什么样子？**
