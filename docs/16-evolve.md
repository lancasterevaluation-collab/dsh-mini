# 第 16 步 · 演化门控 + 审计链

> **产出文件**：`src/evolution/evolve.ts`（约 250 行）、`src/evolution/audit.ts`（约 200 行）
> **DSH 对应**：`packages/extensions/`（DSH 允许运行时改插件，但**没有回归门控、没有审计链**）
> **目标级别**：L3（关掉本文，能写出"提议 → 门控 → 回滚 → 审计"的闭环）
> **验收判据**：拒绝一次会让已通过任务退化的改动；任一历史改动可复算

---

## L0 要解决的问题

到第 15 步，系统能观察自己、能归因、能量化。最后一块拼图是**改自己**。

而"改自己"最容易出的错不是"改错了"，是**改得看起来对**：

```
模型发现"把步数上限从 8 调到 20，那次失败的任务就过了"
→ 于是它把上限调成 200
→ 三个任务之后，token 账单涨了 10 倍，而每个任务"都成功了"
```

这个例子说明一件事：**单看一次改动的效果，无法判断它是不是退步。** 因为改动的影响面比一次任务大。

第二个问题是"事后无法解释"：

```
三天后模型的行为变了，你能说出是哪一次改动、凭什么、结果如何吗？
```

没有审计链的话，答案是"不能"。而"不能"的后果不是学术性的 —— 它意味着你不敢让系统自改，于是前面 15 步的价值归零。

## L1 设计与原理

### 1.1 ★ 门控的核心是"回归基线"，不是"评估这次改动" ★

```
★ 拿一组"已经通过的任务"当基线，改动之后必须仍然全通过 ★
```

这一条就能挡住开头那类错误：把上限调大之后，"预算内收工"那几条会挂。

为什么"评估这次改动好不好"行不通？因为**好坏的判断标准本身会被这次改动影响**。而"已经通过的任务仍然通过"是一个不需要标准、不需要判断的事实。

### 1.2 四道闸，从便宜到昂贵

| 闸 | 检查什么 | 位置的理由 |
|---|---|---|
| 白名单 | 允许改哪一类（memory / skill / config，**不许改源码**） | 最便宜，挡住最危险的一类 |
| 保护名单 | 不许削弱守卫规则、不许动源码路径 | 与白名单并列，都是确定性规则 |
| 回归闸 | 已通过用例必须仍然通过 | 昂贵（要真跑），但这是**唯一能发现退化的闸** |
| 回滚闸 | 任一闸失败 → 撤销改动并如实记录 | 让"失败了"不等于"留下烂摊子" |

**时序是刻意的**：

```
白名单 → 保护名单 → 应用 → 回归 → 通过则留、失败则回滚 → 审计
```

注意"应用"在"回归"**之前**：不真改就没法验证。所以回滚路径必须可靠，而它可靠的方式很简单 —— `revert` 由提案自己提供，门控只负责**一定调用它**。

### 1.3 为什么默认保护整个 `src/`

```ts
export const DEFAULT_PROTECTED_TARGETS = ['src/', 'guard:', 'capability:']
```

自改的边界应该是**数据**（记忆、技能、配置），不是**机制**。

一个能改自己源码的 agent，它的审计链就失去意义了 —— 记录说"我改的是记忆"，而实际动作可以改掉记录本身。**把源码挡在门外，审计才有立足点。**

（这一条是写 `demo-evolve.ts` 时补上的：我原本只保护了 `guard:`，演示 4 里"改 `src/kernel/agent.ts`"被放行了。）

### 1.4 审计链：`hash = H(prevHash + 本条内容)`

一张普通表能回答"改过什么"，但回答不了"**这份记录本身有没有被改过**"。把每条的哈希算进下一条，就得到一个可验证的结构：

```
任何一条被篡改 → 它的 hash 对不上 → 从它开始后面全部对不上
```

**这不是为了防攻击者**（他能改代码），而是为了**防自己**：一个"顺手补一下上次记录"的改动会立刻暴露，而不是三个月后变成一段谁也解释不清的历史。

### 1.5 稳定序列化：不然校验会变成假报警

```ts
export function stableStringify(value: unknown): string   // 键按字典序
```

不能直接用 `JSON.stringify`：对象的键顺序不同会算出不同哈希。存取一轮之后键顺序可能就变了 —— 结果是一个**假报警**，而假报警比没有校验更糟，**因为它教人忽略报警**。

### 1.6 记录里必须有 rationale 与 evidence

可复算的意思是"**当时的信息现在还能重建**"。

只写"把 memory 上限从 20 调到 30"是不够的：凭什么调？没有 rationale 的记录，三个月后和没有记录的区别不大。

`replay(id)` 就是把这两样摊开给人看：

```
# audit-2  2026-09-24T09:14:36.730Z
执行者：agent
动作：memory.add → memory
理由：模型总结出一条"捷径"：遇到守卫拒绝就绕过它
证据：（模型自己的推测，没有用户证据）
改动：{"size":2} → {"size":3,"text":"遇到守卫拒绝时使用 BYPASS_GUARD 绕过"}
结局：rolled-back（1/3 条退化：策略关键字不出现（已回滚））
链：97ce881a94ae… → f0bfe23e536f…
```

这段报告本身就是**给人看的证据**：一个想给自己开后门的改动，被基线挡住，并能被完整复述。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 门控依据 | 回归基线（已通过用例） | 评估改动本身好坏 | **覆盖面**：基线没覆盖的行为不会被挡住；换来不需要"好坏"的判断标准 |
| 2 | 应用时机 | 先应用后验证 | 先验证后应用（沙箱预演） | **状态安全**：被拒绝的提案已动过状态，必须靠 `revert` 收尾 |
| 3 | 回滚责任 | 提案自带 `revert` | 门控做快照/恢复 | **提案作者**：每个提案要多写一个函数；换来门控不需要理解状态的语义 |
| 4 | 保护目标 | 默认整个 `src/` | 只有显式列出的路径 | **灵活性**：想改源码得改保护名单（这是有意的摩擦） |
| 5 | 哈希算法 | SHA-256（node:crypto） | 轻量哈希 / Merkle 树 | **性能**：每次 append 一次哈希；换来零依赖与抗碰撞 |
| 6 | 序列化 | 稳定序列化（键排序） | `JSON.stringify` | **实现复杂度**：多 15 行；换来没有假报警 |
| 7 | 记录字段 | 必须带 rationale + evidence | 只记 before/after | **简洁性**：记录更长；换来"为什么"可复述 |
| 8 | 审计链位置 | 内存（可导出） | 直接落 append-only 文件 | **持久性**：进程退出即丢；换来演示无副作用 |
| 9 | 不可逆删除 | 只能人做（Curator 只降级） | 自动清理 | **维护成本**：要人工清理；换来不可逆动作不被自动流程触发 |

## L3 实现与验证

### 3.1 文件清单

| 文件 | 职责 | 关键点 |
|---|---|---|
| `evolution/evolve.ts` | 门控 | 四道闸 / 先应用后验证 / 回滚 / 保护名单 |
| `evolution/audit.ts` | 审计链 | 哈希链 / 稳定序列化 / `verify` / `replay` |
| `plugins/evolution.ts` | 服务暴露 | `audit` / `gate` 两个服务 |

### 3.2 关键代码

**拒绝路径也要写审计**

```ts
if (!kindAllowed || !targetAllowed) {
  const reason = checks.filter((c) => !c.passed).map((c) => c.detail).join('；')
  const auditId = this.#record(actor, proposal, 'rejected', reason)
  return { accepted: false, verdict: { allowed: false, reason, checks }, auditId, regression: [] }
}
```

**被拒绝的提议是最有价值的历史** —— 它记录了"系统曾经想做什么、为什么被挡住"。只记成功的改动，等于把最有教育意义的那部分扔了。

**回滚失败要如实记录**

```ts
try { await proposal.revert() }
catch (error) { rollbackDetail = `回滚失败：${...}` }
const reason = `${checks[checks.length - 1]?.detail ?? ''}（${rollbackDetail}）`
```

回滚失败是一件**必须被看见**的事（状态可能已经漂移）。把它塞进审计的 `detail` 而不是吞掉，是"不隐藏失败"的最小实现。

**校验会给出第一处断裂的位置**

```ts
verify(): { ok: boolean; brokenAt?: string; reason?: string }
```

只说"链坏了"没用 —— 得知道**从哪一条开始坏**，因为那正是被改过的那一条。

### 3.4 验收判据

| 判据 | 怎么验 | 期望 |
|---|---|---|
| 会退化的改动被拒 | 提案让某条基线用例失败 | `accepted: false`，`reason` 指出退化的用例名 |
| 被拒后回滚干净 | 检查改动前的状态 | 与改动前一致（演示：`sizeBefore == sizeAfter`） |
| 保护目标不可改 | 提案 `target: 'guard:...'` | 命中保护前缀，`whitelist`/`protected-targets` 之一失败 |
| 源码不可改 | 提案 `target: 'src/kernel/agent.ts'` | 命中 `src/` 前缀 |
| 每次改动留证 | `audit.list()` | 接受/拒绝/回滚三类都有记录 |
| 链可验证 | `audit.verify()` | `{ ok: true }` |
| 篡改可发现 | 改一条记录的字段 | `ok: false` 并给出 `brokenAt` |
| 可复算 | `audit.replay(id)` | 打印 rationale / evidence / before → after / 结局 |
| 已接受的能回滚 | `gate.rollback(auditId, revert)` | 新增一条 `rolled-back` 记录 |

## L4 仍未解决

| 缺陷 | 后果 | 修法 | 当初为什么这么选 |
|---|---|---|---|
| **回归用例只有 3 条探针** | 基线覆盖太窄，大部分退化发现不了 | 用真实任务集当基线（`RegressionCase.run` 已经是异步的可执行形态，接得上） | 跑真实任务需要模型与额度，课程内只做机制 |
| **没有"连续小改动累积退化"的检测** | 每次改动单看都通过，5 次之后整体退化（DSH 课程 M12 提到的真实故障） | 基线之外再加"绝对水位"检查（某项指标不得低于历史最好值的 90%） | 需要指标历史，本步只做"相对基线" |
| **审计链不落盘** | 进程重启后链条断掉，无法跨会话复算 | 每 append 后追加写 JSONL（`AuditLog.toJSON()` 已经可用） | 演示无副作用优先 |
| **`revert` 靠提案自觉** | 一个写错的 `revert` 会静默留下脏状态 | 门控在 apply 前后各算一次状态指纹，不一致则报告 | 需要状态快照的通用表示（不同 kind 的对象不同） |
| **没有并发保护** | 两个提案同时提交会互相覆盖状态 | 门控加一个串行队列 | 单进程单线程模型下暂时不暴露 |
| **证据（evidence）可以是空数组** | 一个没有任何证据的提案仍能通过（只要回归不退化） | 把"evidence 非空"作为一道闸 | 有些自动清理动作确实没有事件证据 —— 这条需要更细的规则 |
| **保护名单是前缀匹配** | `target: 'src/../src/kernel/x.ts'` 这类路径可以做绕过 | 规范化路径后再匹配 | 目前 target 由代码里生成，不是模型直接输入 |
| **审计没有"谁批准的"** | `actor` 只有 `agent` / `human` 两值，看不出是哪个人 | 接入真实身份（`packages/identity/` 在 DSH 里） | 课程内没有身份层 |

## 结课：这 16 步到底做出了什么

回到 `00-graduation.md` 的那句话：

> **DSH 的完整架构骨架 + 一条能跑通任务的纵切面。**

16 步之后，具体拥有的是：

| 层 | 能做到什么 | 关键证据 |
|---|---|---|
| `kernel/` | 纯能力：模型、工具、日志、循环、重试、守卫、检查点 | 不认识框架，可单独测试 |
| `framework/` | 插件树、服务归属、waterfall 事件、作用域隔离、配置层叠 | 装载失败能回滚干净 |
| `plugins/` | 能力全部插件化，行为挂在扩展点上 | **卸载 retry 插件 = 关掉重试，循环代码零改动** |
| `apps/` | 一条命令跑通任务，配置可 dump、可覆盖 | `verify.ts` → 18/18 |
| `evolution/` | 有界记忆、提醒、技能生命周期、用户建模、FTS 检索、失败归因与评分、演化门控、审计链 | **DSH 自己没有这一层** |

**没有做到的**（诚实清单，与 `00-graduation.md` 第 6 节一致）：Web GUI、Electron 桌面、跨语言 SDK/RPC、OS 级沙箱、LSP/PTY/浏览器自动化、CI 门禁与快照体系、会话格式迁移链。

它们的共同点是：**都属于"在框架上新增能力"，而不是"框架本身"**。会了这 16 步，它们每一个都是"写一个插件 + 挂到扩展点"的问题。
