# 第 13 步 · 技能库 + Curator

> **产出文件**：`src/evolution/skills.ts`（约 230 行）、`src/evolution/curator.ts`（约 160 行）、`skills/*.md`
> **DSH 对应**：`packages/skill/`（DSH 有技能加载，但**没有生命周期管理**）
> **目标级别**：L3（关掉本文，能自己写出"目录/全文两级"的技能库）
> **验收判据**：只暴露名字列表，按需读全文；长期不用的技能转 archived，上游技能不动

---

## L0 要解决的问题

第 12 步有了记忆，但记忆只能存"一句话的结论"。有一类东西它装不下：

```
一条流程 = 6 个步骤 + 每步的判断依据 + 三个反例
```

把它塞进记忆，一条就吃掉了整个容量；而如果每条任务都把全部流程全文喂给模型，20 个流程就是几万 token —— 其中 19 个与当前任务无关。

于是有两个具体现象：

**现象 1：上下文被"用不到的规范"吃满。** 模型每轮开头都要读一遍全部技能全文，而它真正需要的是其中一条。

**现象 2：技能只会越攒越多。** 三个月前的技能还在目录里，模型每次都要在一堆无关条目里挑 —— **渐进披露的收益被自己的目录吃回去**。

更进一步的问题藏在维护侧：技能有两个来源（上游规范 / 本地总结），如果它们混在一起，"这条到底是谁写的"永远说不清，而清理动作会变得危险。

## L1 设计与原理

### 1.1 两级暴露：成本从"技能总数"降到"实际用到的条数"

```
第一级（永远可见）：  name + 一句话描述 + 触发词        ← 几十字节
第二级（按需读取）：  全文                               ← 几千字节
```

演示里的实测：**3 条技能的目录 504 字节，全文 3550 字节，压缩 7.0×**。技能越多、全文越长，这个比值越大。

模型先看目录，判断"这条与我有关"之后才 `read(name)` 拿全文。

**代价落在模型身上**：它必须多花一次工具调用，而且**可能判断错** —— 该读的没读、不该读的读了。这就是为什么 `description` 与 `triggers` 的质量比全文更重要：目录写歪了，渐进披露就退化成"谁也找不到"。

### 1.2 ★ 唯一能拿全文的路径是 `read(name)` ★

```ts
// SkillLibrary 刻意**不提供** all() 这样的"把全文都给我"的方法
catalog(includeArchived = false): readonly SkillSummary[]
read(name, now = Date.now()): SkillReadResult
```

为什么不做 `all()`？因为**那种方法一旦存在，调用方就会（在压力下）用它** —— 加一个"临时调试"的用途，三个月后就变成了默认路径，渐进披露名存实亡。

把"能拿到全文"限制在唯一一个入口，等于把这条纪律写进了类型系统。管理类用途（Curator、导出、审计）走单独的 `adminList()`，名字里带 `admin` 就是提醒。

### 1.3 读一次 = 用一次：生命周期挂在真实使用上

```ts
read(name) { skill.lastUsedAt = now; skill.useCount += 1; ... }
```

生命周期不靠人工标记，靠**真实使用**。"从来没被读过"和"三个月没被读过"是两种不同的状态，前者按创建时间起算（`considerUnusedAsFresh`），否则刚加进来的技能会立刻被判为过期。

### 1.4 Curator：两档降级 + 一条硬规则

```
stale     目录里还在，只是被标出"很久没用了"      ← 可逆
archived  从日常目录里消失，但仍可被显式读到      ← 可逆
删除      不可逆 —— 留给**人**
```

**为什么分两档而不是直接删？** 因为"没用"是概率判断，而删除不可逆。Curator 只负责把候选挑出来。

**硬规则：上游技能只能降到 stale，永远不能被归档。**

```ts
if (skill.source === 'upstream' && target === 'archived') {
  if (skill.status !== 'stale') this.#library.setStatus(skill.name, 'stale')
  protectedUpstream.push(skill.name)
  continue
}
```

如果 Curator 有权归档上游技能，那么某次"打扫"就可能把团队规范悄悄藏起来，而现象只是"模型忽然不遵守规范了" —— 排查会花掉一整天。**这条规则的代价是目录会略微变脏**（永远不会消失的上游条目），换来的是"规范不会无故消失"。

`setStatus` 与 `remove` 里也都做了同样的拦截（上游不能归档、不能删除），所以**绕过 Curator 也删不掉** —— 关键规则必须在数据层，不能只在流程层。

### 1.5 降级必须经过 stale

```ts
if (skill.status === 'stale' && idleMs > staleAfterMs + archiveAfterMs) return 'archived'
return 'stale'
```

从 active 直接到 archived 会**跳过那一次"被看见"的机会**。多一档就多一次人工发现"这条其实还在用"的机会。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 暴露粒度 | 目录 + 按需读全文 | 全量注入 / 只给名字 | **模型**：多一次工具调用，且可能判断错 |
| 2 | 拿全文的入口 | 只有 `read(name)` | 提供 `all()` | **开发者**：调试时略麻烦；换来的是纪律不可绕过 |
| 3 | 匹配方式 | 触发词字面命中 | 向量检索 / 模型挑选 | **召回率**：同义表达匹配不到；换来的是"为什么选中它"可解释 |
| 4 | 来源区分 | `upstream` / `local` 两类 | 只用一个池子 | **维护者**：多一层判断；换来的是清理不会误伤上游 |
| 5 | 降级档数 | 两档（stale / archived） | 一档（直接归档） | **使用者**：目录里多一批 stale 条目 |
| 6 | 谁有权删除 | 只有人（Curator 只降级） | Curator 可删除 | **维护者**：要手动清理；换来的是不可逆动作不被自动流程触发 |
| 7 | 生命周期依据 | 真实使用（`read`） | 人工打标 / 创建时间 | **准确性**：老技能第一次被读会被判"刚用过" |
| 8 | 技能存储 | `.md` 文件（第一行描述、`triggers:` 行） | 写进 JSON 配置 | **编辑体验**：JSON 多行字符串难写；换来的是可 diff、可手改 |

## L3 实现与验证

### 3.1 文件清单与技能文件格式

| 文件 | 职责 |
|---|---|
| `evolution/skills.ts` | 技能库（两级暴露、状态、来源保护） |
| `evolution/curator.ts` | 生命周期（降级、归档、恢复、普查） |
| `skills/*.md` | 技能落盘形式 |
| `plugins/evolution.ts` | 装载技能目录（`skillsDir`） |

`skills/adding-a-capability-plugin.md`：

```markdown
# 新增一个能力插件（4 步）

triggers: 插件, plugin, 新能力, 加一个工具, 扩展点

## 什么时候用
...
```

**为什么用文件而不是配置？** 因为技能会被人手写和编辑，而 JSON 里的多行字符串既难写也很难 diff。

### 3.2 关键代码

**目录只返回便宜字段**

```ts
catalog(includeArchived = false): readonly SkillSummary[] {
  return [...this.#skills.values()]
    .filter((skill) => includeArchived || skill.status !== 'archived')
    .map((skill) => ({ name, description, triggers, status }))   // 没有 body
}
```

**重复技能名必须报错**

```ts
if (this.#skills.has(skill.name)) {
  throw new Error(`技能名重复："${skill.name}" —— 覆盖上游技能必须显式删除后再加`)
}
```

静默覆盖 = 上游技能被本地悄悄替换，而没人知道。这条报错让"覆盖"变成一个显式动作。

**Curator 的幂等性**

`review()` 只依赖"上次使用时间"与"当前状态"，不做累积计数 —— 所以跑两次结果一样。这不是优化，是**可测试性**：幂等的打扫可以在任意时刻安全触发（`turn-end` 上每轮都调）。

### 3.4 验收判据

| 判据 | 怎么验 | 期望 |
|---|---|---|
| 只暴露名字列表 | `catalog()` 的返回结构 | 不含 `body` 字段 |
| 按需读全文 | `read(name)` 后再看 `useCount` | 计数 +1，`lastUsedAt` 更新 |
| 渐进披露有收益 | 目录字节 / 全文字节 | 比值 > 1（实测 7.0×） |
| 长期不用转 archived | `review(now + 200天)` | `archived` 列表非空 |
| 上游技能不动 | 同一次 review 的 `protectedUpstream` | 上游条目在列表里且状态是 stale |
| 上游不可删 | `remove('debugging-waterfall')` | 抛错，技能仍在 |
| 归档可逆 | `curator.restore(name)` | 状态回 `active` |

## L4 仍未解决

| 缺陷 | 后果 | 修法 | 当初为什么这么选 |
|---|---|---|---|
| **匹配靠字面触发词** | 用户说"写个扩展"时匹配不到 `插件` | 加同义词表或字符 n-gram 相似度 | 语义匹配会让"为什么选中它"不可解释 |
| **没有全文去重** | 两条技能讲同一件事，模型会读到互相矛盾的步骤 | 加入库时做相似度检查（复用 `memory.suggestMerge` 的思路） | 需要人工裁定"哪条对"，属于第 16 步门控的范围 |
| **`useCount` 只增不减** | 一条技能历史上被读 100 次后，即使一年没用也不会降级 | 用滑动窗口计数（近 90 天的读数） | 需要时间序列存储，本步只做"最后使用时间" |
| **技能之间不能互相引用** | 大流程无法拆成"总纲 + 子步骤"，只能写成一长条 | 支持 `!include <skill-name>` | 引用会引入加载顺序与循环依赖两个新问题 |
| **没有技能质量信号** | 被读了 100 次但每次都导致失败的技能，和有用的技能地位一样 | 把 `diagnose` 的归因结果接回技能（"用了这条技能后失败率如何"） | 需要第 15 步，且需要对照组 |
| **Curator 不看内容变化** | 上游技能被上游更新后，本地的 `lastUsedAt` 不会重置，可能正好在这次更新后被判定为 stale | 记录内容哈希，变化即视为"新技能" | 先做时间维度，内容维度留给后续 |
