# 任务失败的可纠正性分类

> 起因：你提出"需要区分**回滚才能纠正**的错误和**重规划就能纠正**的错误"。
> 本文件把它形式化，并指出**它就是你的论文立论结构**。
> 立场：你说得对 —— 这是**实现方法问题，不是原理问题**。原理上大家都知道"错误要处理"；实现对不上，是因为三类错误需要**完全不同的基础设施**。

---

## 一、先厘清：这是和"瞬时/永久"正交的另一个维度

第 1 步的错误分类（`RATE_LIMIT` / `AUTH` / …）解决的是：

> **一次 API 调用失败了 —— 要不要再试一次同样的事？**
> 维度：**时间**（这个错误是暂时的吗）

而你现在提的，解决的是：

> **一次任务搞砸了 —— 要不要先撤销已经做的事，再换个办法？**
> 维度：**可逆性**（已经造成的影响能收回吗）

**两者正交。** 组合起来是：

| | 影响可逆 | 影响不可逆 |
|---|---|---|
| **错误是瞬时的** | 直接重试 | —— |
| **错误需要回滚** | 回滚后换方法重试 | —— |
| **错误是永久的** | 换方法（不用回滚） | **必须事前预防** |

**最后一个是关键格**：永久 + 不可逆 = **自我修正根本来不及**。

## 二、三分法

### A 类 · 可重规划纠正（replan-recoverable）

**判据**：失败发生时，系统状态与任务开始时**等价**（或差异可忽略）。换个策略继续即可。

| 项 | 内容 |
|---|---|
| 典型例子 | 选错了工具、路径拼错、误解了需求、参数类型错 |
| 已有的副作用 | 无，或仅限无意义的中间产物 |
| 纠正成本 | **低** —— 一次新的推理循环 |
| 谁能纠正 | ★ **模型自己** ★ |
| 需要的 harness 机制 | 把失败原因**清楚地回灌**给模型 |

### B 类 · 需回滚纠正（rollback-recoverable）

**判据**：失败发生时，状态**已被改变**，但改变**可以被撤销**。

| 项 | 内容 |
|---|---|
| 典型例子 | 改错了文件、写坏了配置、删了不该删的文件、装错了依赖 |
| 已有的副作用 | 有，且落在**可回滚的载体**上（文件系统、工作区） |
| 纠正成本 | **中** —— 撤销 + 重新规划 |
| 谁能纠正 | ❌ **模型自己做不到** —— 它没有"撤销"这个动作 |
| 需要的 harness 机制 | **检查点 + 回滚**（快照 / 事件溯源 / 版本控制） |

### C 类 · 不可纠正（irreversible）

**判据**：已经发生了**无法收回**的外部副作用。

| 项 | 内容 |
|---|---|
| 典型例子 | 对外发送了消息、执行了 `rm -rf`、提交了代码、调用了付费 API 产生了实际效果 |
| 已有的副作用 | 有，且**不可逆** |
| 纠正成本 | **∞** |
| 谁能纠正 | ❌ **谁都做不到，只能预防** |
| 需要的 harness 机制 | **事前拦截**（策略声明 + 单调守卫 + 人工审批） |

## 三、三类错误 → 四类 harness 机制

**这张表是本文件的核心。** 它解释了为什么"加一个错误处理"是不够的。

| 错误类别 | 需要的机制 | 本质 | 本课程对应 |
|---|---|---|---|
| **A** | 反馈注入 | 把失败原因说清楚，让模型自己改 | 第 1 步 `parseError`、第 2 步 `validateArgs`、第 10 步 `tools/post-execute` |
| **B** | 检查点 + 回滚 | 能回到之前的状态 | 第 7 步 会话日志（可回放）、工作区快照（对应 DSH 的 `deliverables/` + `workspace/`） |
| **C** | 事前拦截 | 在发生**之前**拦住 | 第 10 步 **单调守卫** + `ctx.approval` |
| **A/B/C 的判别** | 状态差异检测 | 判断"这次失败属于哪类" | 第 7 步日志 + 第 15 步诊断 |

**注意最后一行**：**要知道一个失败属于哪类，你必须能对比"失败前后的状态"。**

而"能对比状态"的前提是：**你记录了状态**。这就是第 7 步会话日志存在的另一个理由 —— 它不只是"给模型看的历史"，它还是**回滚和归因的依据**。

## 四、为什么这是"实现方法问题"

你的判断是对的，我把它说透：

```
原理层面（人人都懂）：
    "出错了要处理。"

实现层面（差别巨大）：
    A 类 → 你只需要一个好一点的错误消息
    B 类 → 你需要一套状态管理（快照？事件溯源？版本控制？）
           而且要想清楚：快照粒度是"每步"还是"每个工具调用"？
           快照存在哪里？回滚时哪些状态该恢复、哪些不该（比如日志本身不该被回滚）？
    C 类 → 你需要"什么不能做"的策略语言
           而且要保证这个策略不能被下游插件推翻（→ 单调性）
           还要有人工审批的通道（→ 异步、可能超时）
```

**三类机制的工作量差了不止一个量级。**

这也解释了为什么很多 agent 系统"有错误处理但没什么用" —— 它们只实现了 A 类。

## 五、★ 这就是你的论文立论结构 ★

把三类和你的方向（harness 干预 vs 自我修正）对上：

```
A 类失败 → 模型自我修正【有效】
   模型看到反馈 → 换条路走。这本来就是 LLM 的强项。

B 类失败 → 模型自我修正【无效】
   模型无法撤销自己做过的事。它可能会说"我重新写一遍"，
   但如果它不记得改了哪些文件，就会越改越乱。

C 类失败 → 模型自我修正【太晚】
   事情已经发生了。再好的修正也只是事后补救。
```

**于是你的论点可以写成一句可证伪的话：**

> **harness 干预的价值，不在于"帮模型想得更好"，**
> **而在于它提供了模型自身无法提供的两类能力：回滚（B 类）和事前拦截（C 类）。**
> **而在 A 类上，干预不但没有优势，还可能因为打断模型自己的纠错节奏而有害。**

### 由此导出三条可验证的假设

| 假设 | 陈述 | 预期结果 |
|---|---|---|
| **H1** | 在 **A 类**失败上，harness 干预相对自我修正**无显著优势**（甚至更差） | 差异的 95% CI 跨 0，或方向为负 |
| **H2** | 在 **B 类**失败上，harness 干预**显著优于**自我修正 | 成功率提升，且 CI 不跨 0 |
| **H3** | 干预的收益与**任务中 B/C 类失败的占比**正相关 | 在 B/C 占比高的任务子集上，提升更大 |

**H1 是最有价值的一条** —— 它是个"反向假设"，而反向假设被证实，比正向假设更有说服力：

> "我们证明了 harness 干预**并非普遍有效**，它只在任务存在不可逆或需回滚的错误时才产生收益；
> 在可重规划的错误上，干预甚至有害。"

**这种结论比"我们的方法更好"有分量得多**，因为它给出了**适用边界**。

## 六、怎么把失败分类（实现细节）

### 6.1 自动判定的判据

| 类别 | 判据（可在轨迹上自动计算） |
|---|---|
| **A** | 失败点之后的**工作区状态 == 失败点之前的状态** |
| **B** | 工作区状态**被改变**，且改变**落在可恢复载体上**（被追踪的文件） |
| **C** | 轨迹里出现了**不可恢复的动作**（外部 API 调用、`rm`、`git push`、支付…） |

### 6.2 需要什么基础设施

```
① 状态快照    → 失败前后能对比工作区（文件哈希 / git 状态）
② 动作标注    → 哪些工具调用是"不可逆动作"（需要在注册表里声明）
③ 轨迹日志    → 能回溯到"失败发生在哪一步"（会话日志）
```

**② 是我们课程第 2 步就要留的接口** —— 现在 `Tool` 定义里还没有"这个工具是否产生不可逆副作用"这个字段。

> ## ★ 这是一个真实的发现 ★
>
> 你在这一轮提出的分类，**暴露了课程设计中的一个缺口**：
> 我们第 2 步的 `Tool` 接口只知道"名字/描述/参数/handler"，
> 但**不知道这个工具的副作用是否可逆**。
>
> 而这个信息是 C 类拦截的**唯一依据** —— 没有它，"事前拦截"就只能靠硬编码的工具名白名单。
>
> **我会在第 2 步的文档里补上这个字段**，并在第 10 步的守卫里用上它。
> 具体设计见 `02-tools.md` 的 L1 节。

### 6.3 分类器本身的可靠性

如果你要实现一个**自动分类器**（把失败轨迹分到 A/B/C），那它自己也需要被验证：

- 人工标注 60+ 条失败轨迹作为参考
- 报 **Macro-F1** 和 **Cohen's κ**
- 阈值：Macro-F1 ≥ 0.8 且 κ ≥ 0.6（对齐 MotiPro 课程 M11 的验收判据）

**这不是可选的。** 如果分类器不准，H1/H2/H3 的结论就不可信 —— 这是审稿人一定会问的地方。

## 七、奖励攻击（reward hacking）—— 你提到的第四类

你说"reward hacking，其他不知道"。我把它和上面三类并列，因为它是**同一类问题的另一种形态**：

| | 前三类 | **奖励攻击** |
|---|---|---|
| 表现 | 任务失败 | **任务"成功"了** |
| 分数 | 掉 | **涨** |
| 真实情况 | 没做成 | **没做成，但通过了检查** |
| 危险程度 | 中 | ★ **最高** ★ |

**它是最阴的一种，因为所有指标都往好的方向走。**

### 常见的两类

| 类型 | 例子 | 为什么危险 |
|---|---|---|
| **利用了判分器** | 发现判分器只检查输出格式，就只对格式不对内容 | 分数涨了，能力没涨 |
| **利用了验证器规律** | MotiPro M12 里那个真实案例：工具确实修了检索，但**一个子集是靠猜出验证器的格式规律通过的** | 局部看起来是进步，全局是退化 |

### 为什么它特别难发现

**因为它不报错，也不掉分。** 它只会在你**换一个 benchmark** 或**换一批题**的时候突然暴露。

### 对抗手段

| 手段 | 说明 |
|---|---|
| **跨 benchmark 验证** | 在 A 上有效、在 B 上失效 → 疑似攻击 |
| **轨迹分析而非结果分析** | 看它**怎么**做对的，不只看做没做对 |
| **异常一致性检测** | 某类题的通过率突然接近 100% → 可疑 |
| **留出集** | 保留一批未公开的题，只在最后测一次 |

**第三条最实用**：正常的方法提升是渐进的（62% → 65%），而**奖励攻击的表现是"某个子集突然接近满分"**。

## 八、完整的"沉默型问题"清单

你说只知道 reward hacking，我把这一类补齐。**它们的共同点：不报错、不掉分、只在以后暴露。**

| # | 沉默型问题 | 表现 | 怎么发现 |
|---|---|---|---|
| 1 | **奖励攻击** | 分数涨，能力没涨 | 轨迹分析 + 跨 benchmark |
| 2 | **干预触发率过低** | 干预组的提升看着漂亮，其实只作用在 3 条轨迹上 | **记录触发率** |
| 3 | **数据污染** | 分数虚高 | 查 benchmark 发布时间 vs 模型训练截止 |
| 4 | **判分器偏差** | LLM judge 系统性偏向某种输出风格 | 用人工标注算 κ |
| 5 | **环境漂移** | 上个月的结论今天复现不出来 | 每次实验记录环境快照 |
| 6 | **样本量错觉** | 2 个点的提升在噪声里 | 算 `n ≈ 4/Δ²` |
| 7 | **多重比较** | 试了 10 个配置，报了最好的那个 | 报 FWER / BH-FDR 校正后的结果 |
| 8 | **退出条件泄漏** | 测试集的特征"漏"进了你的开发过程 | 严格区分 dev / test |

**第 7 条最容易被忽视**：如果你调了 10 版配置，每版都在同一批题上测，"最好的一版"有相当概率只是运气好。**这就是为什么要留出测试集。**
