# 路线 A 执行方案：全推理期 + 本地 7B–14B

> 决策记录：**路线 A（不跑任何训练）** + **本地推理（7B–14B）** + **2×RTX 4090（48GB）**
> 这个组合把"训练臂"换成"引用臂"，代价是失去一个卖点，收益是**样本量不再被 GPU 时间锁死**。

---

## 0. 这个决策改变了什么

| | 原计划 | 路线 A |
|---|---|---|
| 因子 2（矫正类型 C） | **{C₀ 无, C₁ 模仿, C₂ 纠错, C₃ RL}** | **{S₀ 无, S₁ 自查重试, S₂ 自查+换策略, S₃ 结构化反思}** |
| C 轴性质 | **训练臂**（需要 LoRA / GRPO） | **推理臂**（只改 prompt 与流程） |
| 硬件 | 200–600 GPU 小时 | **48GB 本地推理** |
| 样本量上限 | 被训练时间锁死 | **每天上万 trial** |
| 失去什么 | — | 训练侧数据不是自己的（改为引用） |

**关键**：**"模型自校正"从"训练出来的能力"变成了"推理期的行为"** —— 而这正好落在你自己认定的边界里
（SCoRe 证明训练期可以，你的空间是**推理期**）。

## 1. 模型选型与 vLLM 配置

### 1.1 显存账（估算）

| 模型 | 精度 | 权重 | 建议部署 | 可行性 |
|---|---|---|---|---|
| **Qwen2.5-7B-Instruct** | fp16 | ~15GB | 单卡 | ✅ 最省事，首选 |
| **Qwen2.5-14B-Instruct** | **4-bit（AWQ/GPTQ）** | ~9GB | 单卡 | ✅ |
| Qwen2.5-14B-Instruct | fp16 | ~28GB | 双卡 TP=2 | ⚠️ 留给 KV cache 的空间少 |
| Qwen2.5-32B | 4-bit | ~19GB | 双卡 | ⚠️ 勉强，不推荐做主力 |

**建议主力**：**7B fp16（单卡）+ 14B 4-bit（另一卡）** —— 这样两卡各跑一个模型，可以做"模型维度"的对照，
而且**两个模型互不抢显存**。

### 1.2 vLLM 启动配置

**7B（单卡）**：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --tensor-parallel-size 1 \
  --gpu-memory-utilization 0.88 \
  --max-model-len 32768 \
  --max-num-seqs 8 \
  --port 8000
```

**14B 4-bit（另一张卡）**：

```bash
CUDA_VISIBLE_DEVICES=1 vllm serve Qwen/Qwen2.5-14B-Instruct-AWQ \
  --tensor-parallel-size 1 \
  --gpu-memory-utilization 0.88 \
  --max-model-len 32768 \
  --max-num-seqs 4 \
  --port 8001
```

### 1.3 ⚠️ `--gpu-memory-utilization` 是**预分配**

**它会把指定比例的显存一次性占满** —— 不是"用到才占"。

**后果**：如果你在同机跑别的吃显存的进程（比如另一个 vLLM、或某个本地 embedding 模型），**会直接 OOM**。

**建议**：**留 10%–12% 余量**（所以上面写 0.88，不是 0.95）。

## 2. 因子重新设计（路线 A 版）

```
因子 1  H 剂量 d      {0, 1, 2, 3, 5, 8, 12}       ← 保留（harness 编辑数，不训练）
因子 2  S 自校正策略   {S₀, S₁, S₂, S₃}              ← ★ 重新定义（原为训练臂）★
因子 3  τ 干预时点     {τ₁ 轨迹内, τ₂ 完成时, τ₃ 诊断后}  ← 保留
模型     {7B, 14B}（本地）+ 文献里的更大模型结果（引用）
```

### 2.1 新的 S 轴（每一步都对应一个已发表的做法）

| 水平 | 做法 | 文献锚点 |
|---|---|---|
| **S₀** | **无自校正** —— 一次生成到底 | 基线 |
| **S₁** | **自查重试** —— 让模型检查自己的回答并重写一次 | 复现 R06 的"intrinsic self-correction"设定 |
| **S₂** | **自查 + 换策略** —— 检测失败后换一种做法（而非原地重写） | 对应你提的"**可重规划纠正**"（A 类） |
| **S₃** | **结构化反思** —— 显式产出"错误诊断 → 修正动作" | 对应 Reflexion / 结构化 reflect 那一类 |

**这个 S 轴的好处**：**四个水平都是推理期的，全部不用训练**，而且每个都能指回一篇文献。

### 2.2 与原 C 轴的映射（用于论文里对接）

| 原计划 | 路线 A 的处置 |
|---|---|
| **C₀ 无** | → **S₀**（自己跑） |
| **C₁ 异策略模仿** | → **引用 R50**（"全轨迹模仿使 7 任务全部退化，均 −14.9"） |
| **C₂ 同策略纠错** | → **引用 R50 / R59**（同策略纠错是修复臂） |
| **C₃ 同策略 RL** | → **引用 SCoRe（ICLR 2025 Oral）** |

**论文里的写法**：

> "训练侧的三种矫正类型（C₁–C₃）我们**不复现**，直接采用 [R50][SCoRe] 的报告结果作为对照臂；
> 本文的贡献在于**推理期**的 S 轴与 H 轴、τ 轴的交互。"

## 3. 吞吐核算（★ 这是路线 A 的最大收益 ★）

### 3.1 单题成本

| 项 | 估算 |
|---|---|
| 一道 agent 任务 | 10–30 步 |
| 每步上下文 | 2K–8K tokens（随轨迹增长） |
| 单题总生成 | ~15K–80K tokens |
| 7B + vLLM 单卡吞吐 | ~2000–4000 tok/s（batch 下） |
| **单题 GPU 时间** | **约 5–30 秒** |
| **加工具执行**（CPU/IO） | 再 5–60 秒（取决于任务） |

**所以单题墙钟时间大约 15–90 秒**，取决于工具密集程度。

### 3.2 每天能跑多少

```
并发 8 路 × 3600 秒 / 30 秒每題 ≈ 960 題/小时
   ↓
★ 约 1 万–2 万题/天（本地，零边际成本）★
```

### 3.3 对样本量的意义

按 `n ≈ 4/Δ²`：

| 要检测的差异 | 需要 trial | 本地耗时 |
|---|---|---|
| 20 个百分点 | ~100 | 几分钟 |
| **10 个百分点** | **~400** | **不到 1 小时** |
| 5 个百分点 | ~1600 | 几小时 |
| **2 个百分点** | **~10000** | **1 天内** |

**结论：路线 A 下，样本量几乎不是约束。** 这是"不跑训练"换来的最大红利。

## 4. 本地推理的五个坑

### 坑 1 · agent 的 KV cache 会挤爆显存 ★

**agent 任务和普通问答不同**：轨迹长（10–30 步）、上下文持续增长。

**所以**：
- `--max-model-len` **按实际需要设**（别贪大设 128K）
- `--max-num-seqs` **保守**（4–8，别设 256）
- 如果发现 OOM，**先降 `max-num-seqs`，再降 `max-model-len`**

### 坑 2 · `gpu-memory-utilization` 预分配

见 1.3。**留 10% 余量**。

### 坑 3 · 工具执行不是 GPU 时间

**你的 rollout 里，大量时间花在**：shell 命令、文件读写、测试运行。

**这意味着**：
- **GPU 利用率可能很低**（大部分时间在等工具）
- **GPU 空闲时可以做别的**（比如并行跑另一批任务）
- **瓶颈在 CPU/IO，不在 GPU** —— 所以**并发数可以比显存允许的更高**（只要工具能并行）

**实测建议**：先测单题墙钟时间，再定并发。

### 坑 4 · 模型版本必须冻结 ★

**必须在实验开始前固定**：
- 模型的确切 revision（HuggingFace 的 commit hash，不是 `main`）
- vLLM 版本
- sampling 参数（temperature / top_p / seed）

**否则**：
```
三个月后重跑，模型 repo 更新了
   ↓
★ 你无法复现自己三个月前的数据 ★
```

**具体做法**：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct --revision <commit-hash>
```

**并且把 revision 写进实验台账**。

### 坑 5 · 单卡双模型 vs 双卡单模型

**两个选择**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **两卡各跑一个模型**（7B + 14B） | 模型对照方便 | 单模型吞吐没提升 |
| **双卡跑一个 14B（TP=2）** | 大模型可行 | 只能测一个模型 |

**建议**：**先按"两卡各一个模型"** —— 因为**你要的样本量大，而模型维度的对照可以后补**。

## 5. 与"引用臂"的对接

**哪些结论直接引用，不自己跑**：

| 你想证明的 | 引用哪篇 | 它的结论 |
|---|---|---|
| 全轨迹模仿会退化 | **R50**（Co-Evolving） | 7 任务**全部退化**，均 −14.9；规划失败 1.1% → 14.6% |
| 同策略纠错有效 | **R50 / R59** | 规划桶仅 1.1% → 1.8%，均值 +1.7 |
| 训练期 RL 可以教会自校正 | **SCoRe**（ICLR 2025 Oral） | MATH +15.6%，HumanEval +9.1% |
| 内在自校正（推理期）不可靠 | **R06 / Stechly / Kamoi** | 见 `oral-spotlight-evidence-search.md` |

**论文里的表述**：

> "训练侧的对照臂来自 [R50][SCoRe] 的公开结果。
> **我们选择不复现它们，是为了把全部算力投入到推理期的样本量上** ——
> 因为本研究的核心因变量（H × S × τ 的交互）**在推理期即可完全观测**。"

**这个理由完全站得住** —— 而且它解释了为什么你的样本量能比别人大。

## 6. 执行顺序

```
第 0 步  P0（问题存在性）        ← 不需要 gpu 集群，100 条基线轨迹
           ▲ 先做这个：它的结果决定后面做不做
           │
第 1 步  冻结环境                ← 模型 revision + vLLM 版本 + sampling 参数
           │
第 2 步  单题成本实测            ← 测墙钟时间、工具 vs GPU 占比，定并发
           │
第 3 步  S 轴单因子扫描          ← S₀/S₁/S₂/S₃ × {7B, 14B}，固定 H₀
           │   （这就是"推理期自校正到底行不行"的直接回答）
           │
第 4 步  H × S 二维              ← 加入 harness 剂量
           │
第 5 步  τ × H × S               ← 加入干预时点
           │
第 6 步  复现域                  ← 换一个任务域重跑关键格子
```

**第 3 步是关键**：**它直接回答"推理期自校正有没有用"** ——
而这个结果决定 H 轴（harness 干预）是否有意义。

## 7. 这个路线的两个风险（必须提前说清）

### 风险 1 · "训练侧靠引用"会被质疑

**可能的质问**：*"你的对照臂是别人的数据，可比性怎么保证？"*

**回应**：

> "可比性问题存在，所以我们在论文里**不把 C₁–C₃ 的结果和我们的 S 轴做数值比较**，
> 只用来**定性说明**'训练侧已被研究过'。
> **本文的所有数值比较都发生在我们自己的推理期实验内部。**"

**这个划界很重要** —— 它避免了"跨实验比较"这个方法论陷阱。

### 风险 2 · 7B–14B 的结论未必迁移到大模型

**小模型的 agent 行为和 32B/72B 差异可能很大**。

**缓解办法**：
1. **用两个规模**（7B + 14B）做**趋势一致性**检查
2. 在"已知可行"的格子上，**用 API 跑一次大模型抽样验证**（你计划里本来有 API 预算）
3. 论文里**明确写出规模边界**

**第 2 条是性价比最高的** —— **在关键结论上用 API 跑 100-200 道题做确认**，成本可控。
