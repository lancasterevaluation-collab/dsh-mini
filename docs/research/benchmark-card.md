# Benchmark 速查卡

> 你导师问的那一串，其实是**六个标准问题**。任何 benchmark、任何一次汇报，都该能当场答出这六条。
> **本文档给模板，不填具体数字** —— 数字必须来自一手来源（论文 / 官方仓库 / leaderboard），填错比留空更糟。

---

## 一、六个问题 ↔ 六个字段

| # | 导师的问法 | 对应的字段名 | 他在验证什么 |
|---|---|---|---|
| 1 | **是什么任务的** | 任务域与任务形式 | 你的结论能覆盖哪类能力 |
| 2 | **有多少道题** | 规模与划分 | 你的样本量够不够支撑结论 |
| 3 | **啥时候出的** | 发布时间 + 版本 | **数据污染风险**、时效性 |
| 4 | **设计点什么** | 设计目标与规避项 | 这个 benchmark **故意不想测什么** |
| 5 | **测评什么的** | 评测维度与判分协议 | 你报的分数是怎么算出来的 |
| 6 | **现在大家的表现怎么样 / 怎么用** | SOTA 区间 + 解读方式 | **你的结论有没有可能成立** |

**第 6 问是最深的**，也是最能体现水平的一问。它包含两个子问题：

- **大家的表现是多少** → 你处在什么位置（有没有天花板效应）
- **这些数字怎么用** → 你打算用它做什么判断

---

## 二、第 6 问为什么最要命

因为**benchmark 的 SOTA 分布直接决定你的实验有没有意义**。

```
情况 A：SOTA 已经 95%+
   → 天花板效应。你想证明 +5 个点，几乎不可能（只剩 5 个点的空间）
   → 必须解释：为什么这个 benchmark 还能测出差异

情况 B：SOTA 在 40–70%
   → 甜区。差异有空间，但方法之间有真实差距
   → 这是大多数有影响力的 agent 工作所在的区间

情况 C：SOTA 只有 15–30%
   → 任务很难。你要证明的差异可能被"任务本身太难"淹没
   → 需要额外说明：这份分数是"部分完成度"还是"全或无"

情况 D：不同 harness 之间差距巨大（比如 70% vs 20%）
   → ★ 这正是你的研究方向 ★
   → harness 效应 ≥ 模型效应，这就是 Harness-Bench 那类工作的立论基础
```

**所以在汇报里，第 6 问的正确答法不是"某某做到 70%"**，而是：

> "当前 SOTA 区间是 40–70%，不同 harness 之间差距可达 20+ 个点。
> 我的方法在这个区间里想要证明 +5 个点的提升，需要的样本量是 `4/0.05² ≈ 1600` 个 trial，
> 也就是 300 题 × 5 次重复。**这就是我打算扩大规模的原因。**"

**这一句话里有：区间、差距、目标差异、样本量、实验计划。** 它把六个问题串成了一条逻辑链。

## 三、可填的速查卡（复制到你的实验记录里）

```markdown
## Benchmark: <名称>

### 1. 任务域与形式
- 任务类型：<如 代码修复 / 网页导航 / 工具调用 / 多轮对话>
- 输入形式：<题目怎么给的>
- 输出形式：<怎么判断做完了>
- 单题预算：<最大步数 / 最大 token / 最大时间>

### 2. 规模与划分
- 总题数：<N>
- 官方划分：<train / dev / test 各多少>
- 我实际使用：<N'> ，抽样方式：<随机 / 按难度分层 / 全量>
- 为什么是这个 N'：<写清理由。导师一定会追问这个>

### 3. 发布时间与版本
- 首次发布：<年-月>
- 我用的版本：<v?，以及该版本的题目数与前一版是否不同>
- 污染风险：<该 benchmark 是否在模型训练截止之前发布>

### 4. 设计目标与规避项
- 它想测：<核心能力>
- 它故意避免：<如 避免依赖特定 API / 避免需要外部网络 / 避免多语言>
- 已知的构造偏差：<如果论文里提到了，照抄>

### 5. 评测维度与判分协议
- 主指标：<成功率 / 解决率 / 部分分>
- 判分器：<精确匹配 / 单测通过 / LLM-as-judge / 人工>
- 部分完成的处理：<全或无 还是 按比例给分>
- 判分器的一致性：<若有 LLM judge，它和人工的一致率是多少 —— 一手来源里应该有>

### 6. 他人表现与解读
- 参考区间：<模型侧 / harness 侧的分数区间>
- 主要来源：<leaderboard 链接 / 论文表格>
- 天花板判断：<离 100% 还有多少空间>
- ★ 我打算怎么用这些数字：<要证明多大差异、需要多少样本、打算怎么扩规模>
```

## 四、每个字段去哪取（别猜）

| 字段 | 一手来源 | 注意 |
|---|---|---|
| 任务域与形式 | 论文的 Task / Dataset 章节、官方仓库 README | 别用第三方博客的描述 |
| 规模与划分 | 同上；**以官方仓库的当前数据为准**（论文常滞后） | 版本更新会改题数 |
| 发布时间与版本 | arXiv 首次提交日期 + 仓库 release tag | 两者可能差半年 |
| 设计目标与规避项 | 论文的 Motivation / Design 章节 | 这里往往写着"我们刻意不测什么" |
| 判分协议 | 论文的 Evaluation 章节 + 仓库里的评测脚本 | **以脚本为准**，论文可能简化了描述 |
| 他人表现 | 官方 leaderboard > 论文表格 > 第三方汇总 | leaderboard 有时标注提交的 harness 配置 |

**规则**：**能查到一手来源的，绝不引用二手。** 查不到就标"未核实"，不要估。

## 五、这套卡片怎么用

### 汇报前

把这六个字段的数字抄到一张纸上（不要靠记忆）。**如果某个字段你答不出来，那就是你这周要补的。**

### 被追问时

导师的追问基本都在这六问之内。如果超出，说：

> "这个数字我记录在实验文档里，我确认一下，稍后发给您。目前记得大概是 X。"

**但更重要的是**：如果这个问题**每周都出现**，说明这个字段该被**自动记录**进台账（见 `agent-research-playbook.md` 第 5 章）。

### 主动汇报的模板

> 本周做了什么 → **六问里的关键数字** → 遇到的假设与验证情况 → 下周计划

**主动把六问答完，导师就不会追着问。**

## 六、把这六问接到你的项目里

你的研究方向是 **harness 干预 vs 自我修正**。这六问在你的场景下有一个特殊形态：

| # | 通用问法 | 你的场景下要额外答的 |
|---|---|---|
| 1 | 是什么任务的 | 任务是否**允许中途干预**（有些 benchmark 不允许） |
| 2 | 有多少道题 | **失败题占比是多少** —— 干预只对失败路径有意义 |
| 3 | 啥时候出的 | 模型训练数据里有没有这批任务 |
| 4 | 设计点什么 | benchmark 是否**规定了 harness 的行为边界** |
| 5 | 测评什么的 | 判分器是否**只看到最终状态**（如果看不到过程，干预的价值就无法体现） |
| 6 | 怎么用 | ★ **干预触发率**必须和成功率一起报，否则等于没测 |

**第 6 条要展开说**：

> 如果你报"干预组 70% vs 对照组 62%"，导师一定会问：
> **"干预触发了几次？"**
>
> 如果干预只在 10% 的轨迹上触发，那这 8 个点的差异**几乎全部来自那 10% 的样本** ——
> 换算到全量，实际影响是 8% ÷ 10% = 80 个点，听起来更惊人，
> **但样本量也缩到了十分之一，置信区间会宽得没法看。**
>
> **所以正确报法是**：
> ```
> 干预触发率：12%（180/1500 步）
> 触发子集成功率：72% (n=27)
> 未触发子集成功率：62% (n=273)
> 全量成功率：63.2%
> 触发子集 n=27，95% CI 宽度约 ±18 个点 —— 当前样本不足以判定触发子集内的提升
> ```

**这段数字连起来，才是"怎么用这些数字"。**
