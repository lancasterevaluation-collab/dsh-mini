# Agent 科研工作手册

> 面向：正在做 agent 科研、需要应付组会与论文写作、感觉"想不全 / 记不住 / 验证不了"的研究者。
> 原则：**凡是能被程序算出来的事实，就不该靠记忆。**

---

## 0. 核心判断

三个症状（想不全、记不住、验证不了）看起来是三件事，实际上是**同一件事的三个层次**：

```
症状                          真实缺失                        解法层次
─────────────────────────────────────────────────────────────────────
想不全应该了解的点      没有「结构化提问清单」            清单层（第 3 章）
记不住具体数字          事实没有外化，或外化形式不可查      事实层（第 2 章）
无法验证假设            假设不可证伪 / 变量没控 / 样本不足   假设层（第 4 章）
─────────────────────────────────────────────────────────────────────
                          共同根因：科研过程没有工程化        自动层（第 5 章）
```

**贯穿全文的一条原则**：

> 手工维护的台账一定会烂。**能让程序产出的数字，绝不要手工填。**

---

## 1. 问题诊断

### 1.1 为什么"想不全"不是记忆力问题

大脑回忆分两种模式：

| 模式 | 过程 | 在压力下的表现 |
|---|---|---|
| **开放式回忆** | "关于数据集我该说什么？" → 在记忆里搜索 | 压力下搜索范围急剧收缩，只想到最近想到过的两三条 |
| **清单式检查** | "数据集有 9 个字段，逐个确认" → 逐项核对 | 压力下仍能完成，因为不需要"想起来" |

**"想不全"几乎总是因为你在用第一种。** 解决办法不是"更努力地记"，而是**切换成第二种**。

### 1.2 为什么"记不住数字"是假问题

导师问的这些问题 —— 数据集、环境配置、benchmark 构成、平均步数、最高分 —— **全部是事实性信息**，本就不该靠记忆。

真正的问题有两个：

1. 这些事实**散落在**脚本、日志、聊天记录、临时文件里，没有一个地方能一次查全
2. 更糟：有些事实**根本没被记录下来**，跑完就丢了

第 2 条才是致命的。**一个跑完没留下结构化记录的实验，等于没做过。**

### 1.3 为什么"验证不了假设"是最严重的一条

前两条影响组会，这一条影响**论文能不能成立**。而且它有三个完全不同的根因，混在一起就永远解决不了（详见第 4 章）。

## 2. 事实层：让事实不再需要记忆

### 2.1 事实的三种生命周期

| 类型 | 变化频率 | 例子 | 外化方式 |
|---|---|---|---|
| **静态配置** | 一次确定，长期不变 | 数据集来源、环境版本、benchmark 构成 | 写进配置文件，**可 dump** |
| **运行结果** | 每次实验都变 | 平均步数、最高分、成功率、token 消耗 | **由 harness 自动记录** |
| **过程事实** | 每次运行都产生 | 哪一步失败了、调了哪些工具、干预是否触发 | **由 session log 自动记录** |

关键洞察：**第 2、3 类根本不需要你填**。一个设计良好的 agent harness 天然会产生它们。

### 2.2 数据集字段（完整清单）

导师问"用的什么数据集"时，他其实想确认 9 件事：

| # | 字段 | 为什么会被问 | 陷阱 |
|---|---|---|---|
| 1 | 名称与版本 | 复现性 | 同一个 benchmark 不同版本题目数不同 |
| 2 | 来源与获取方式 | 别人能否复现 | 私有数据要说明 |
| 3 | 总规模 | 结论的强度 | 100 题和 1000 题的结论可信度差一个量级 |
| 4 | **实际使用的子集** | 你跑的是全集还是采样 | 最容易含糊的一问 |
| 5 | 划分方式 | 是否泄漏 | test 集有没有被调参污染 |
| 6 | 题型分布 | 结论的适用范围 | "在 80% 是导航题的集合上"≠"通用能力提升" |
| 7 | 难度分布 | 天花板效应 | 全部题都做不出 → 指标无区分度 |
| 8 | 评测协议 | 怎么判对错 | 精确匹配？LLM 判分？人工？ |
| 9 | 预处理 | 是否公平 | 你的预处理是否对 baseline 也做了 |

**第 4 条最容易被追问。** 如果你的实验只跑了 150 题，就必须说清"是从 500 题里随机抽的 150"还是"是全集的 150"，以及**为什么是 150**。

### 2.3 环境字段

| # | 字段 | 说明 |
|---|---|---|
| 1 | 硬件 | GPU 型号与数量、显存、CPU |
| 2 | 操作系统与版本 | 不同 OS 上 agent 工具行为可能不同 |
| 3 | 运行时版本 | Python / Node / CUDA / 关键依赖版本 |
| 4 | **模型与推理参数** | 基座模型、是否微调、temperature、top_p、max_tokens |
| 5 | **随机种子** | 有没有固定？固定了哪些？ |
| 6 | 复现命令 | **一条能跑起来的命令** |
| 7 | 并发与环境隔离 | 多个 agent 并行是否共享状态 |

**第 5 条是 agent 科研的重灾区。** LLM 推理本身有随机性，如果你连种子都没固定，两次跑出不同结果时你无法判断是改动生效了还是随机波动。

**第 6 条是"导师印象"的转折点**：当你说出"复现命令是这一条"并当场发出去时，专业感立刻不同。

### 2.4 Benchmark 字段

| # | 字段 | 说明 |
|---|---|---|
| 1 | 名称与版本 | 同 2.2 |
| 2 | 题目总数 / 你用的数量 | 同 2.2 第 4 条 |
| 3 | 题型分类与占比 | 你的结论覆盖哪些能力 |
| 4 | **评测指标定义** | 成功/失败怎么判？部分成功算几分？ |
| 5 | **判分器** | 精确匹配 / 单测通过 / LLM-as-judge / 人工 |
| 6 | 单题预算 | 最大步数、最大 token、最大时间 |
| 7 | 参考基线分数 | 别人做到多少，你说的"提升"是相对谁 |

**第 6 条直接决定第 2.5 节的"平均步数"有没有意义** —— 如果预算 30 步、平均用了 28 步，说明大量任务是被预算截断而不是完成。

### 2.5 结果字段

每次实验都必须记：

| # | 字段 | 说明 |
|---|---|---|
| 1 | 实验 ID | 唯一标识，能追溯到原始日志 |
| 2 | 日期与配置版本 | 对应哪个 commit / 配置 hash |
| 3 | 相对上次的**唯一变更** | 一次只改一个变量（见 4.2） |
| 4 | 成功率 | 主指标 |
| 5 | **平均完成步数** | 加"完成"的限定更重要（见下） |
| 6 | **最高分 / 最好单题** | 影响力上限的证据 |
| 7 | 步数分布 | 平均会被极值扭曲，要看中位数与分位数 |
| 8 | token / 成本消耗 | 效率维度，且是审稿人会问的 |
| 9 | 失败案例分类计数 | 第 4 章诊断的输入 |
| 10 | 与基线的差 + 置信区间 | **没有 CI 的差值不可汇报** |

**关于第 5 条的一个重要提醒**：单说"平均完成步数 12.3"没有信息量。必须区分：

```
全部题的平均步数          ← 被失败题污染（失败题可能跑满预算）
成功题的平均步数          ← 有意义的效率指标
失败题的步数分布          ← 看是"快速失败"还是"耗尽预算"
```

导师如果追问"平均步数"，问的通常是**成功题的平均步数**，因为他关心的是"能做的题做得多快"。

**第 10 条是科研与"感觉"的分界线。** 提升 2 个点，在 100 题样本上可能完全在噪声范围内。这需要第 4.3 节的功效计算。

### 2.6 对比与消融字段

| # | 字段 | 说明 |
|---|---|---|
| 1 | Baseline 是什么 | 原始模型？公开 harness？你的旧版本？ |
| 2 | 对比是否公平 | 预算、模型、判分器是否一致 |
| 3 | 消融表 | 每个组件去掉后的分数 |
| 4 | 对照实验设计 | 见 4.2 |

## 3. 清单层：用检查清单代替开放式回忆

### 3.1 为什么清单有效

清单的作用**不是提醒你细节，而是消除"我是不是漏了什么"这个焦虑本身**。焦虑一消失，回忆能力反而恢复。

所以清单必须满足三个条件：

| 条件 | 反例 |
|---|---|
| **可勾选**（不是可阅读） | "数据集相关说明" —— 无法勾选 |
| **数量固定**（每次都是同样那些） | 每次重新想"该列哪些" |
| **能在 2 分钟内过完** | 50 个问题的清单你不会用第二次 |

### 3.2 Agent 科研的六个提问域

**域 1 · 数据**
- [ ] 数据集全名 + 版本
- [ ] 总题数 / 我实际跑的题数 / 抽样方式
- [ ] 题型分布（top3 题型及其占比）
- [ ] 评测协议与判分器
- [ ] 有没有数据泄漏风险

**域 2 · 环境**
- [ ] 模型名 + 推理参数 + 是否固定种子
- [ ] 硬件：GPU 型号数量
- [ ] 一条可复现命令
- [ ] 单题预算（步数 / token / 时间）

**域 3 · 结果**
- [ ] 成功率 + **置信区间**
- [ ] 成功题平均步数
- [ ] 最高分 / 最好单题
- [ ] token 成本
- [ ] 与 baseline 的差值

**域 4 · 失败**
- [ ] 失败案例按类型计数（至少分 3 类）
- [ ] 最大的一类是什么
- [ ] 有没有"耗尽预算"型失败，占多少

**域 5 · 假设**
- [ ] 本周想验证的假设是什么（一句话）
- [ ] 如果为真，观察到什么；如果为假，观察到什么
- [ ] 什么实验能区分这两种情况
- [ ] 最小验证实验跑了吗

**域 6 · 对照**
- [ ] baseline 是什么
- [ ] 这次相对上次**只改了什么**
- [ ] 消融做了吗

### 3.3 使用方式

**不要贴显示器旁** —— 那还是靠记忆触发。

正确用法：**把清单做成 harness 的一个技能（第 13 步），每次任务结束自动问一遍。** 见第 5 章。

## 4. 假设层：无法验证的三种根因

"验证不了"是个笼统的说法，实际有三类完全不同的原因。**分不清是哪一类，就永远修不好。**

### 4.1 根因一：假设不可证伪

| | 例子 |
|---|---|
| ❌ 差 | "加入记忆机制有用" |
| ❌ 也差 | "harness 干预能提升 agent 表现" |
| ✅ 好 | "加入长期记忆后，在 X benchmark 上**成功题平均步数下降 ≥10%**，成功率提升 ≥5%，且 95% CI 不跨 0" |

一个好假设必须包含四要素：

```
1. 干预是什么          ← 加入长期记忆
2. 在什么上测          ← X benchmark（哪个子集）
3. 指标与方向          ← 成功题平均步数 ↓、成功率 ↑
4. 多大才算成立        ← ≥10% / ≥5%，且 CI 不跨 0
```

**缺第 4 条是最常见的错误。** 没有阈值，任何结果都能被解释成"支持"。

### 4.2 根因二：变量没控制

**症状**：跑完发现分数涨了 8 个点，但你这周同时改了提示词、换了模型温度、加了记忆模块。**这个 8 个点无法归因。**

**修法**：

```
一次实验只允许一个变量。

对照组：基线配置                → 62.0%
实验组：基线 + 记忆模块          → 70.0%   ← 唯一差别是记忆模块
```

如果必须同时改多个，就做成**消融表**：

| 配置 | 记忆 | 提示词改动 | 分数 |
|---|---|---|---|
| A | ✗ | ✗ | 62.0 |
| B | ✓ | ✗ | 70.0 |
| C | ✗ | ✓ | 65.0 |
| D | ✓ | ✓ | 74.0 |

这样 4 行就能说明两个变量的**主效应**和**交互效应**。

**agent 科研特有的失控点**（比传统 ML 多得多）：

| 失控点 | 说明 |
|---|---|
| 工具输出不确定性 | 同一条 shell 命令两次输出可能不同 |
| 模型非确定性 | 即使 temperature=0，部分 provider 仍不稳 |
| 环境状态残留 | 上一次运行留下的文件影响了这一次 |
| 上下文长度差异 | 不同题目的历史长度不同，影响模型行为 |
| 并行干扰 | 多个 agent 共享工作目录 |

**每一条都必须在实验设计里显式处理**，否则你的"提升"很可能来自这里。

### 4.3 根因三：样本量不足

**症状**：你的方法比 baseline 高 2.3 个点，导师问"这个差异显著吗"，你答不上来。

**核心公式（记住这一个就够）**：

要检测的差异是 Δ，那么**每组**大约需要

```
n ≈ 4 / Δ²        （Δ 用小数，如 0.10 表示 10 个百分点）
```

| 想检测的差异 Δ | 每组所需试验数 |
|---|---|
| 20 个百分点 | ~100 |
| 10 个百分点 | ~400 |
| 5 个百分点 | ~1600 |
| 2 个百分点 | ~10000 |

（推导依据：两比例检验，α=0.05、功效 0.80，基准成功率约 50% 时
`n = (1.96+0.84)² × [p₁(1-p₁)+p₂(1-p₂)] / Δ² ≈ 8 × 0.5 / Δ² = 4/Δ²`。
基准成功率偏离 50% 越远，所需样本越少，所以这是**保守上界**。）

注意这里的 n 是**试验数（trials）**，不是题目数。LLM 评测里"样本"包含两层：

```
题目数 × 每题重复次数 = 总试验数
```

**这就是为什么 agent 评测必须看重"每题跑几次"。** 把上表换算成实际规模：

| 阶段 | 题目 × 重复 | 总试验数 | 能检测的最小差异 |
|---|---|---|---|
| 探索（找方向） | 30 × 1 | 30 | ~37 个百分点 —— **只能看方向，不能下结论** |
| 初步验证 | 100 × 3 | 300 | ~12 个百分点 |
| 论文级 | 200 × 5 | 1000 | ~6 个百分点 |
| 论文级（严格） | 300 × 5 | 1500 | ~5 个百分点 |

**读一下第二行**：`100 题 × 3 次 = 300 试验`，只够检测 **12 个百分点**的差异。
如果你观察到 4 个点的提升，**这个实验规模根本无法支持任何结论** —— 它既不能证明有效，也不能证明无效。

**"探索阶段不下结论"这一条极其重要。** 15 道题上 3 个点的差异是纯噪声，报出去会被一句话问倒。

### 4.4 最小验证实验的设计

不要一上来跑全量。标准流程：

```
第 1 步：把假设写成四要素句（4.1）
第 2 步：找出"如果为真 / 如果为假"各应观察到什么
第 3 步：设计能区分这两种情况的最小实验 —— 通常 15–30 题
第 4 步：跑，看趋势对不对
        ├─ 完全没区别 → 假设可能本身就错，或干预没生效（查干预触发率！）
        ├─ 方向对但幅度小 → 扩大样本量到能检测的规模
        └─ 方向反了 → 这是个有价值的发现，重复一次确认
第 5 步：只有第 4 步通过，才投入全量实验
```

**第 4 步的括号是关键**：agent 科研里"干预没生效"比"干预没用"常见得多。**必须先确认干预真的触发了**（触发率、触发次数），再谈效果。

### 4.5 假设台账

每个假设一行，永不删除：

| ID | 假设（四要素句） | 验证实验 | 状态 | 结论 | 日期 |
|---|---|---|---|---|---|
| H01 | 加入记忆后成功率 ≥5% ↑ | exp012 vs exp001 | 未验证 | | |
| H02 | 干预触发率 <20% 时无效果 | exp015 | 部分验证 | 触发率 18%，差异在噪声内 | |

**状态只能是四选一**：未验证 / 部分验证 / 已支持 / **已推翻**。

**"已推翻"必须单独列出来。** 被推翻的假设是最有价值的资产之一 —— 论文的 Discussion 章节、以及避免重复犯错，都靠它。

## 5. 自动层：让 harness 自己产出这些数字

这是本文档与"手工台账"的根本区别。

### 5.1 我们正在建的 16 步，正好覆盖全部三个层次

| 层次 | 需要的字段 | 由哪一步产出 |
|---|---|---|
| 事实 · 静态配置 | 环境、benchmark 构成、预算 | **第 6 步**（loader + dump-config） |
| 事实 · 运行结果 | 步数、token、成功率、最高分 | **第 7 步**（session log） |
| 事实 · 过程 | 每步做了什么、哪里失败 | **第 7 步**（append-only 事件） |
| 清单 | 六个提问域 | **第 13 步**（技能库 = 可勾选清单） |
| 记忆 | "上次这个配置跑出过什么问题" | **第 12 步**（有界记忆）+ **第 14 步**（FTS 检索） |
| 诊断 | 失败案例分类、干预触发率 | **第 15 步**（失败归因） |
| 验证 | 对照、消融、门控 | **第 16 步**（演化门控 + 审计） |

### 5.2 具体怎么落地

**① 环境配置 → 自动 dump**

```powershell
node src/apps/dump-config.ts research
```
输出当前 profile 的完整生效配置。把它存进实验记录目录，就是"环境配置"字段。

**② 步数与 token → 从 session log 算出来**

第 7 步的会话日志记录每个事件。于是：

```ts
// 不需要手工填，直接算
const steps = session.events.filter(e => e.type === 'step/end').length
const tokens = session.events.filter(e => e.type === 'assistant/message')
                            .reduce((sum, e) => sum + e.usage.total_tokens, 0)
const toolCalls = session.events.filter(e => e.type === 'tool/call').length
```

**导师问"平均完成步数"，你运行一条统计命令就能答。**

**③ 实验台账 → 一次运行一行，自动追加**

每次运行结束，harness 把一个 JSON 追加进 `experiments/index.jsonl`：

```jsonc
{ "id": "exp012", "date": "2026-03-14", "config": "abc123",
  "tasks": 150, "repeats": 3,
  "success_rate": 0.70, "mean_steps_success": 9.4, "max_score": 1.0,
  "tokens": 1842000, "failure_classes": { "tool_error": 12, "budget_exhausted": 21, "wrong_plan": 8 } }
```

**这是最关键的一步**：把"记数字"从人的责任变成程序的责任。

**④ 清单 → 技能**

第 13 步的技能库支持"渐进式披露"。把第 3.2 节的六个提问域写成一个技能：

```
skills/agent-research-checkin/SKILL.md
```

每次任务结束时，nudge（第 12 步）提示 agent 过一遍这个清单，把没填的字段问出来。

**⑤ 假设台账 → 结构化文件**

```
research/hypotheses.jsonl
{"id":"H01","claim":"...","experiment":"exp012 vs exp001","status":"unverified","conclusion":""}
```

第 15 步的诊断会把新的实验结果**自动关联回最相关的假设**。

## 6. 汇报层：组会速查表

### 6.1 生成方式（组会前 10 分钟，不是 30 分钟）

有了第 5 章的自动层，速查表是**一条命令的输出**：

```powershell
node src/apps/research-brief.ts --since 2026-03-07
```

输出应该长这样：

```
本周变更（唯一变量）
  exp012: 加入长期记忆模块（相对 exp011 唯一变更）

关键数字
  成功率      62.0% → 70.0%   (+8.0pt, 95% CI [+1.2, +14.8])
  成功题步数   12.3 → 9.4      (-23.6%)
  最高分      0.85 → 1.00
  token       2.1M → 1.8M     (-14%)

失败分布（exp012）
  budget_exhausted  21 (47%)   ← 最大一类
  tool_error        12 (27%)
  wrong_plan         8 (18%)

假设状态
  H01 记忆提升成功率 ≥5%    → 已支持（CI 不跨 0）
  H02 触发率 <20% 时无效     → 未验证

下周计划
  验证 H02；针对 budget_exhausted 类失败做干预
```

**注意这个输出的结构**：变更 → 数字（带 CI）→ 失败分布 → 假设状态 → 计划。这就是"主动汇报结构"，而且**每个数字都可追溯**。

### 6.2 被问到不知道的

不要硬编，也不要说"我忘了"。说：

> "这个数字在我实验文档里，我确认一下，稍后发给您。目前记得大概是 X。"

**但更重要的是：如果这道题每周都出现，说明它应该被加进自动台账。** 让"不知道"的清单每周变短，比练话术有用得多。

### 6.3 导师预期下降的真实原因

通常不是"你知道得少"，而是**沟通中缺少掌控感**：

| 缺掌控感的表现 | 有掌控感的表现 |
|---|---|
| 说"大概"、"好像"、"应该" | 说"62.0%，95% CI ±7" |
| 被追问才发现没记录 | 主动给出数字和它的问题 |
| 实验之间关系说不清 | "相对上次只改了 X，其它都锁死" |
| 失败停在"模型不行" | "失败按三类计数，最大一类占 47%" |

**掌控感来自系统，不来自准备。** 你带着一套自动产出的数字去组会，几周内印象就会扭转。
