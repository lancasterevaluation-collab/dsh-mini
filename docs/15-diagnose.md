> **目标级别**：L3（关掉本文，能写出规则分类器 + Macro-F1/κ/95% CI 的评分）
> **验收判据**：失败归因到组件，报出 Macro-F1 与 Cohen's κ 及 95% 置信区间

## L0 要解决的问题

第 12–14 步让系统能**观察**自己。但"能观察"不等于"能定位"：

```
一次任务失败了。是模型的问题？工具的问题？守卫拦的？还是预算用完了？
```

没有分解，值班时的第一句话就无法回答。更麻烦的是**趋势**：

```
昨天的工具失败率是 3%，今天 11% —— 是哪一类失败在涨？
```

如果每次失败都只记一句"任务失败"，这个趋势永远看不出来。

另有一个**方法论**问题：直觉上我们"看一眼就知道是谁的锅"。但那只在没有压力的时候成立。到了需要自动化（比如让 agent 自己决定"要不要改配置"）的时候，"我猜是工具的问题"必须变成**可以被评分的判断**。

## L1 设计与原理

### 1.1 归因必须是规则，而不是"让模型看一眼"

| | 规则（我们选的） | 模型判定 |
|---|---|---|
| 可解释 | 命中哪条规则、看了哪些证据，逐条能说 | "我觉得是工具" |
| 可评分 | 拿标注算 κ，能判断规则好不好 | 判定器本身不稳定，无法评估 |
| 成本 | 0 | 每次失败一次调用 |
| 覆盖面 | 只看得到写进规则的模式 | 能发现没见过的模式 |

所以规则用来做**主力归因**，模型判定留给"人工标注 / 疑难样本"这个位置（`featuresOf` 的 `injections` 参数就是给它留的口子）。

### 1.2 特征全部来自日志，没有"模型的自我报告"

```ts
export interface FailureFeatures {
  readonly status: TurnStatus          // turn 怎么结束的
  readonly steps / maxSteps            // 用了多少预算
  readonly attempts                    // 重试次数（第 9 步的持久事实）
  readonly toolErrors / failedTools    // 工具失败情况
  readonly guardDenials / guardAsks    // 守卫干预（第 10 步）
  readonly errorCodes                  // 错误码序列
  readonly feedbackIsWrong / feedbackIgnored   // 反馈类（人工或 LLM 注入）
}
```

**为什么强调"全部来自日志"？** 因为它们必须可以被**复算**：给同一份日志重新跑一遍归因，结果必须一样。而"问模型当时怎么想的"既不复现也不可靠。

`feedbackIsWrong` / `feedbackIgnored` 是唯一由外部注入的两个字段 —— 它们对应《Feedback Friction》（NeurIPS 2025）的类别划分（他们的表 1：反馈抗拒 / 反馈质量 / 其他）。把这两个口子留在特征里，是为了让**那篇论文的分类能在自己的日志上复算**。

### 1.3 ★ 归因顺序：先归因"最早发生的那一层" ★

一次失败往往是链式的：模型失败 → 重试 → 工具失败 → 步数用尽。把链尾当根因，会让所有故障都归到"步数用尽"。

```ts
// ① 守卫干预（最早的干预点：调用根本没执行）
// ② 不可重试的模型错误（重试层在这里什么都做不了）
// ③ 可重试错误重试耗尽（归到重试层，那是它的职责边界）
// ④ 工具报错
// ⑤ 步数用尽
// ⑥ 反馈类
// ⑦ unknown
```

**② 排在 ③ 前面**是这条规则里最关键的顺序：`AUTH` 这类错误在重试层是"正确地不重试"，归到 `retry` 会让人去查重试配置（而它没问题）。

### 1.4 为什么必须报 κ，而不只是准确率

假设 60 条失败里 45 条是"工具报错"。一个"永远猜工具"的傻分类器：

```
准确率 = 45/60 = 75%
Macro-F1 = (1.0 + 0 + 0 + 0 + 0 + 0 + 0) / 7 ≈ 0.14
κ = (0.75 - 0.75) / (1 - 0.75) ≈ 0
```

κ 扣掉了"随机也能蒙对"的部分：

```
κ = (p_observed − p_expected) / (1 − p_expected)
```

判读惯例（`interpretKappa`）：<0 比随机还差、0–0.2 几乎没有、0.2–0.4 一般、0.4–0.6 中等、0.6–0.8 显著、>0.8 几乎完全一致。

**同时报 Macro-F1 与 κ** 是因为它们回答不同的问题：Macro-F1 看"每个类别判得准不准"（不受类占比影响），κ 看"整体是否超出随机一致"。只看一个都会漏。

### 1.5 置信区间用 bootstrap + 固定种子

60 条样本算出的 κ=0.62 是"真的 0.62"还是"这一批恰好如此"？没有区间无法回答。

```ts
export function evaluate(gold, predicted, options: { bootstrap?: number; seed?: number } = {})
```

**★ 随机数用固定种子（默认 `20250921`）**：诊断报告必须可复现，否则没法写进事故报告或论文。演示 3 专门验证"两次运行结果完全一致"。

用线性同余生成器而不是 `Math.random()` —— 后者没法设种子。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 归因方法 | 规则分类器 | 模型判定 / 训练分类器 | **召回**：没见过的模式归到 unknown；换来可解释、可复现、零成本 |
| 2 | 特征来源 | 日志（+ 两个注入口） | 让模型自述"我为什么失败" | **准确性**：日志里没有的就归不了因 |
| 3 | 归因顺序 | 先归因最早那一层 | 按"现象最明显"的那层 | **排查路径**：链式失败时可能指向"上游原因"而不是"最终现象" —— 这是刻意的 |
| 4 | 类别数 | 8 类（含 feedback 两类） | 3 类（模型/工具/其他） | **维护成本**：8 类意味着 8 组规则；换来能对接论文分类 |
| 5 | 评估指标 | Macro-F1 + κ + 双 CI | 只报准确率 | **计算量**：bootstrap 1000 次；换来"有没有真学到东西"的答案 |
| 6 | 重采样随机 | 固定种子 LCG | `Math.random()` | **随机性**：样本间相关性略高；换来报告可复现 |
| 7 | 长度不一致 | 抛错 | 静默截断到较短者 | **便利性**：调用方要自己检查；换来不会得出虚假高分 |
| 8 | unknown 类别 | 保留且不惩罚 | 并入最近的类 | **指标**：unknown 会拉低 Macro-F1；换来"规则不够用"这件事可见 |

### 3.2 关键代码

**守卫必须同时算 deny 与 ask**

```ts
const guardInterventions = features.guardDenials + features.guardAsks
if (guardInterventions > 0 && features.toolErrors >= guardInterventions) { /* 归因 guard */ }
```

这是**集成演示（第 12–16 步一起跑）暴露的真 bug**：`irreversibleGuard` 给的是 `ask`（转人工），审批未通过时统计落在 `guardAsks`。我最初只统计 `guardDenials`，于是"不可逆操作被拒绝"整类漏掉，归因落到 `tools`。

修的时候两处一起改（`diagnose.ts` 与 `nudge.ts`）—— **同一个判断在两个地方出现时，就是"缺少一个共享谓词"的信号**。

**步数触顶有两种表现**

```ts
if (features.status === 'max-steps' || features.steps >= features.maxSteps) { ... }
```

写演示时踩到的第二个真 bug：我用 `endReason: 'complete'` 造的会话步数已经等于上限，但状态不是 `max-steps`，于是归不进 `agent-loop`。

两个条件都要认：**"结局是 max-steps"** 与 **"步数已经触顶"**。后者对应真实情况 —— turn 以 complete 结束，但它其实是烧光预算才勉强给出答案的。

**稳定序列化不是必须的，但 κ 的分母要小心**

```ts
if (pExpected >= 1) return 1
return (pObserved - pExpected) / (1 - pExpected)
```

当所有样本都是同一个类时 `pExpected` 会接近 1，分母趋近 0。这类边界要显式返回，否则会算出 `NaN` 或爆炸值。

## L4 仍未解决

| 缺陷 | 后果 | 修法 | 当初为什么这么选 |
|---|---|---|---|
| **规则只看"有没有"，不看"多少"** | 一次工具失败和十次工具失败归因相同 | 特征里加入频率阈值（如 `toolErrors > 3` 触发更激进的归因） | 先做可解释的二值判断，阈值调优没有数据支撑 |
| **没有时间维度** | 无法回答"今天比昨天差在哪" | 按 `time` 分桶，算各组件失败率的时间序列 | 需要一个时间窗口参数与存储，属分析层 |
| **`unknown` 没有回流机制** | 归不了因的样本只是被记下来，不会变成新规则 | 把 unknown 样本导出成"待补规则"清单（半自动） | 自动生成规则会引入错误规则，需要人工确认 |
| **标注只有 60 条** | κ 的 CI 宽达 0.78–0.96，判读不够稳 | 扩到 200+ 条（课程挑战题 2 就是这件事） | 手工标注成本高，先做通链路 |
| **`injections` 靠外部传** | 反馈类归因需要人工/LLM 先判定，链路不闭环 | 用一个专门的 judge prompt 自动填这两个字段 | 引入 LLM 判定会让"可复现"打折 |
| **κ 没有做多标注者一致性** | 只有"规则 vs 人工"，没有"人工 vs 人工"，所以无法判断标注本身的噪声 | 双人标注算一次 κ 作上限参考 | 单人可以完成，双人成本翻倍 |
| **置信度是手调常数** | 每条规则给 0.7–0.9 全凭直觉，没校准 | 用标注数据做 reliability diagram 校准 | 校准需要更多标注，先给一个"证据强度"的粗略表示 |
