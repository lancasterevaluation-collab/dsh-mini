## 本篇新词

| 词 | 一句话 | 为什么必须懂 |
|---|---|---|
| **副作用等级** | 工具改不改状态、改了能不能收回 | ★ 守卫的**全部依据** ★ |
| **守卫（guard）** | 在工具**执行之前**检查它的那道关卡 | C 类失败的**唯一机会** |
| **裁决（verdict）** | 守卫给出的结论：放行 / 拒绝 / 问人 | 三分不是二分 |
| **单调性** | 守卫链**只能越管越严**，拒绝不可被翻案 | 防止晚注册的插件推翻安全策略 |
| **审批人（approver）** | 当守卫说"拿不准"时，由谁拍板 | 把"人来决定"变成可替换的依赖 |
| **检查点（checkpoint）** | 工作目录在某一时刻的完整样子 | B 类回滚的依据 |
| **回滚（rollback）** | 把工作目录恢复到某个检查点 | ★ 要**撤销新增**，不只是还原修改 ★ |
| **守卫历史** | 本次任务里已经执行过的调用 | 循环检测的唯一输入 |
| **配额守卫** | 限制调用**总数**（不是步数） | 一步可以调多个工具，步数管不住成本 |

### 0.3 这一步和上一步的关系

第 9 步解决的是：**请求失败了怎么办**（时间维度 —— 暂时性还是永久性）。
第 10 步解决的是：**任务搞砸了怎么办**（可逆性维度 —— 影响能收回吗）。

**两者正交。** 组合起来是一张 3×3 的表：

| | 影响可逆 | 影响不可逆 |
|---|---|---|
| **错误是瞬时的** | 直接重试（第 9 步） | —— |
| **需要回滚** | 回滚后换方法重试（**本步**） | —— |
| **错误是永久的** | 换方法，不用回滚（**本步**） | ★ **必须事前预防** ★（**本步**） |

**最后一格是关键**：永久 + 不可逆 = **自我修正根本来不及**。

```
第 10 步 守卫        —— ★ 让"不该发生的动作"不发生 ★
```

**前九步都在处理「已经发生的事」**：
- 模型失败了 → 重试
- 工具报错了 → 把错误说清楚
- 上下文满了 → 压缩
- 步数超了 → 停下

**第 10 步第一次处理「还没发生的事」。**

### 0.5.2 为什么必须补这一层 —— 一句话论证

```
如果所有失败都能事后纠正，
    那么守卫就是多余的 —— 出错了纠正就行。

但存在一类失败：影响**无法收回**。
    对外发了消息、删了文件、付了钱、提交了代码……
    ★ 事后再怎么纠正，都已经发生了 ★

对这类失败，**唯一的机会在执行之前**。
    这就是守卫存在的全部理由。
```

## L0 · 问题：为什么"把错误说清楚"不够

### 0.1 三个真实场景

**场景 A · 循环**

```
模型想读一个文件，读错了路径 → 失败
模型想读一个文件，读错了路径 → 失败
模型想读一个文件，读错了路径 → 失败
...（一直重复到步数上限）
```

**第 1、2 步的做法**：每次失败都把"文件不存在"回灌给模型。
**问题**：模型**看不到自己已经试过 5 次了** —— 因为那 5 次失败都是"工具结果"，
它在上下文里但**没有形成"我在重复"这个判断**。

**结果**：20 步上限用完，任务失败，**烧掉了 20 步的成本**。

**场景 B · 不可逆动作**

```
模型觉得"这个临时文件没用了"，调用 delete_file("config.json")
→ 成功
→ 但那是配置文件，不是临时文件
```

**第 1、2 步的做法**：删除成功，返回"已删除"。
**问题**：**没有任何东西能撤销它。** 模型可以说"抱歉我错了"，但文件回不来。

**场景 C · 路径越界**

```
模型拼出 write_file("../outside.txt")
```

**第 2 步的做法**：`resolveInsideWorkspace` 会抛错，注册表转成失败结果。
**这个其实做对了** —— 但请注意：**它是在 handler 里拦的**，
也就是"已经进入了执行函数"。对写文件来说这没问题（还没写），
但如果某个工具的 handler 是"先写后检查"，就已经晚了。

### 0.2 三个场景的共同结构

| 场景 | 事后纠正管用吗 | 为什么 |
|---|---|---|
| A · 循环 | ⚠️ 管用，但**太贵** | 能纠正，可是要烧 20 步 |
| B · 不可逆 | ❌ **完全不管用** | 影响已经发生 |
| C · 越界 | ⚠️ 管用，但**靠的是 handler 自觉** | 换个工具就漏了 |

**三类问题指向同一个结论**：

> **"把错误说清楚"这个策略，只对"状态没变、且模型能自己看出来"的失败有效。**
> **一旦涉及状态改动，就必须在**执行之前**有一道关卡。**

## L1 · 原理：四个设计决策

### 1.1 决策一：给工具贴一个"副作用等级"

**问题**：守卫要拦"危险的调用"。但**什么是危险**？

**直觉答案**：硬编码一串工具名（`delete_file`、`rm`、`git push`……）。

**为什么不行**：

```
① 新工具加进来时，你得记得去改那串名字 —— 忘了就是安全漏洞
② "危险"其实不是工具的属性，而是**一次具体调用**的属性
   —— delete_file("tmp.log") 和 delete_file("config.json") 危险性不同
③ 最重要：硬编码的名单**没法回答"为什么它危险"**
```

**我们的做法**：在 `Tool` 接口上声明一个**等级**：

```ts
export type SideEffect = 'none' | 'reversible' | 'irreversible'
```

| 等级 | 含义 | 例子 |
|---|---|---|
| `none` | 不改变任何状态 | `read_file`、`list_dir`、搜索 |
| `reversible` | 改了，但能收回来 | `write_file`（旧内容还在检查点里） |
| `irreversible` | 改了，收不回来 | `delete_file`、发消息、`git push`、付款 |

**这个等级的三重作用**：

| 作用 | 说明 |
|---|---|
| **给守卫判据** | `irreversibleGuard` 只看这一个字段 |
| **给检查点判据** | 只有 `!== 'none'` 才值得拍快照（省掉大量 IO） |
| **给诊断器判据** | 第 15 步把失败分到 A/B/C 时，依据就是它 |

### 1.2 ★ 为什么 `sideEffect` 必须必填、且不给默认值 ★

**这是一个刻意的设计。**

如果写成：

```ts
readonly sideEffect?: SideEffect   // 可选
```

或者：

```ts
const sideEffect = tool.sideEffect ?? 'none'   // 有默认值
```

**会怎样**：

```
开发者写一个新工具，忘了声明 sideEffect
   ↓
默认成 'none' → 守卫认为它无害 → 直接放行
   ↓
★ 一个会删数据的新工具，被静默地当成只读工具放过去了 ★
```

**这就是"不安全的默认值"** —— 而它最坏的地方是**静默**：
没有报错、没有警告，直到出事。

**必填的好处**：

```
忘记声明 → 编译不过 → 在写下第一行 handler 之前就被迫想清楚
```

**摩擦是刻意的。** 我们宁可让加新工具时多写一行，也不要让一个危险工具悄悄溜过去。

> **这条规则可以推广**：**安全相关的字段，永远不要给它一个"宽松"的默认值。**
> 默认值应该是**最保守**的那个（这里是"报错"，不是 `'none'`）。

### 1.3 ★ 决策二：守卫链的单调性 ★

**问题**：多个守卫注册到同一条链上，它们意见不一致时听谁的？

**场景**：一个安全策略插件注册了"一律拒绝写操作"，另一个业务插件注册了"一律允许"。

**三种可能的规则**：

| 规则 | 后果 |
|---|---|
| **先注册的赢** | 顺序决定一切 —— 但顺序是**加载顺序**，不稳定 |
| **后注册的赢** | ★ **晚来的插件可以推翻早先的承诺** ★ —— 安全策略形同虚设 |
| **最严的赢** | 拒绝 > 问人 > 放行 |

**我们选第三种，它叫"单调"**：**裁决只能越跑越严，不能越跑越松。**

**实现非常短** —— 但它是整个 guard.ts 里最重要的几行：

```ts
check(request, history) {
  let best = { verdict: allow(), byRule: '(默认)' }

  for (const rule of this.#rules) {
    const verdict = rule.inspect(request, history)
    // ★ 只有"更严"才替换 —— 遇到更松的不动它 ★
    if (severityOf(verdict) > severityOf(best.verdict)) {
      best = { verdict, byRule: rule.name }
    }
  }

  return best
}
```

**关键就是那个 `>`**：如果是 `!==`，后注册的规则就能翻案了。

**验证它**（演示 6 的实际输出）：

```
chain.add(lockdownRule)    // 一律 deny
chain.add(permissiveRule)  // 一律 allow

--- 裁决 ---       { "kind": "deny", "reason": "全局封锁" }
--- 是哪条规则给的 ---   lockdown
```

**后注册的 `permissive` 没能推翻先注册的 `lockdown`。**

**单调性的现实意义**：

> **它让"策略"成为一件可以承诺的事。**
> 一个系统说"我不会删除你的数据"，这句话只有在**后续加载的任何代码都无法改变它**时才成立。

**配套机制是 `seal()`**：

```ts
seal(): void   // 封存，之后不能再 add
```

**为什么需要它**？因为单调性还漏了一种情况：

```
如果攻击者在第一位置插入一条 "一律 allow" 的规则呢？
```

不会发生 —— 因为 `allow` 是**默认值**，没有任何规则能给出"比其他规则更宽松"的裁决。
**`add` 只能添加规则，而每条规则最多把裁决收紧。**

**但 `seal()` 防的是另一件事**：**"时机"**。

```
先注册了安全规则 → 系统开始工作 → 某个插件在运行中途又注册一条
```

中途注册的规则**可能做出与初始化时完全不同的判断**（因为它能看到运行期的状态）。
`seal()` 是在"策略已定稿"这个动作上的显式表达。

### 1.4 决策三：裁决三分，而不是二分

**问题**：`allow` 还是 `deny`？二选一够吗？

**不够。** 因为真实世界里大量动作属于**"规则说不清，得人看一眼"**：

| 动作 | 该放行吗 |
|---|---|
| 删除 `.tmp` 文件 | 大概率该放行 |
| 删除 `config.json` | 大概率不该 |
| **删除 `notes.md`** | ★ **取决于人在干什么** ★ |

**二分的后果**：

```
要么把「删除任何文件」都归为危险 → 用户被无休止的确认打断 → 关掉守卫
要么都放行 → 守卫形同虚设
```

**加一个 `ask` 之后**：

```ts
export type GuardVerdict =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string }
  | { kind: 'ask'; question: string }
```

**严重度**：

```ts
allow = 0  <  ask = 1  <  deny = 2
```

**`ask` 在中间**这个位置很重要 —— 它意味着：

- 它能**压过** allow（所以"拿不准"比"放行"严）
- 它**被 deny 压过**（所以明确的禁止不需要问）

### 1.5 决策四：检查点保存"内容"，而不是"引用"

**问题**：怎么让工作目录能回到之前的状态？

**三种做法**：

| 做法 | 优点 | 缺点 |
|---|---|---|
| **调用 git**（如果工作目录是仓库） | 省空间、快 | 依赖外部工具，且"未提交的改动"语义复杂 |
| **文件系统快照**（Windows VSS / LVM） | 快 | 平台相关，权限要求高 |
| **直接存内容**（我们的做法） | 简单、可读、跨平台 | ★ **大文件会吃内存** ★ |

**我们选第三种**，理由是教学项目要能"关掉文档自己写出来"。

**已知代价**（写进 L9）：**快照一个 100MB 的文件，就会在内存里留 100MB。**
生产级系统会用前两种 —— 但**接口是一样的**：

```
snapshot()  →  记下"现在是什么样"
rollback(id) →  变回那个样子
```

**★ 真正重要的不是怎么存，而是"回滚要撤销什么"** —— 见下一条。

### 1.6 ★ 回滚必须撤销"新增"，不只是还原"修改" ★

**这是本步最容易漏的一点。**

**直觉的回滚**：

```
对每个快照里的文件：
  如果现在的版本和快照里的不一样 → 写回快照版本
```

**漏掉了什么**：**快照之后**新创建的文件**。

**为什么这是致命的**：

```
模型犯错的过程常常是「多建了一个文件」：
  写了个错误的实现到 helper.ts（应该是别的名字）
  写了测试到 fake_test.ts
  写了笔记到 notes.md
   ↓
回滚时如果只还原"被改坏的"，这三个新文件**都留着**
   ↓
★ 而它们会被下一次快照当成"原本就有的" ★
   ↓
★ 错误从此固化进基线，再也回不去了 ★
```

**所以回滚要做三件事**：

| # | 情况 | 动作 |
|---|---|---|
| 1 | 快照里有、现在没了 | **写回去** |
| 2 | 快照里有、现在变了 | **写回去** |
| 3 | **快照里没有、现在有了** | ★ **删掉** ★ |

**演示 7 的验证**（实际输出）：

```
--- 回滚报告 ---
{ "restored": ["a.txt"], "removed": ["b.txt"], "unchanged": 1 }
```

`a.txt` 是"被改坏的"（情况 2），`b.txt` 是"多出来的"（情况 3）—— **两个都被处理了。**

### 1.7 ★ 哪些状态不该被回滚 ★

**问题**：回滚把工作目录变回去了 —— 那**日志**呢？

**如果日志也回滚**：

```
回滚 → 日志被恢复到 1 小时前 → ★ 你失去了"曾经回滚过"这个事实 ★
```

**所以有一条边界**：

> **描述事实的载体不参与回滚，被描述的世界才参与。**

**具体地**：

| 载体 | 参与回滚吗 | 为什么 |
|---|---|---|
| 工作目录里的文件 | ✅ 是 | 它们是"被描述的世界" |
| 会话日志 | ❌ 否 | 它是"描述事实的载体" |
| 检查点目录自身 | ❌ 否 | 否则回滚会吃掉回滚的依据 |

**实现方式**是一个忽略名单：

```ts
export const WORKSPACE_IGNORES: readonly string[] = ['.git', '.checkpoints', 'node_modules', 'tmp']
```

**注意 `.checkpoints` 在里面** —— 它保证检查点自己不会被自己回滚掉。

> **这条边界在更广的范围内都成立**：
> **审计日志、事件流、区块链 —— 所有"记录事实"的东西，都不能被它记录的那个过程所修改。**
> 否则"发生过什么"这个问题的答案，就取决于"谁最后改的"。

### 1.8 ★ 拦截也要走"配对通道" ★

**这是第 8 步留下的一个约束，第 10 步必须遵守。**

**第 8 步的规则**：

> assistant 带 N 个 `tool_calls`，后面就必须跟 **N 条** tool 消息 —— 少一条服务端直接 400。

**直觉的做法**：被守卫拦下的调用 → **跳过它，不产生结果**。

**后果**：

```
assistant 要求调用 3 个工具
   ↓
守卫拦下第 2 个 → 只产生 2 条 tool/result
   ↓
★ 下一条 assistant 的消息数对不上 → 服务端 400 ★
```

**正确做法**：

```ts
if (outcome.verdict.kind === 'deny') {
  const reason = outcome.verdict.reason
  this.#session.recordGuard(call.name, 'deny', outcome.byRule, reason)
  this.#pushHistory(call, true, reason)
  return fail(reason)          // ★ 仍然返回一条结果 ★
}
```

**一句话**：

> **拦截改变的是结果的内容，不是结果的存在。**

**而且这个做法还有一个额外好处**：**拒绝的理由会回灌给模型**，
所以模型知道"我想做的事被拦了，原因是……" —— **它可以换个做法**。

这是第 1 步"失败是数据不是异常"那条原则的延续：
**被守卫拒绝，也是一种"失败数据"，不是异常。**

### 1.9 检查点的时机：只在"有副作用"时拍

**问题**：什么时候拍快照？

**三个选项**：

| 时机 | 代价 | 问题 |
|---|---|---|
| 每一步开始前 | 高（每步都扫一遍目录） | 绝大多数步是只读的，白拍 |
| **每个有副作用的调用前** | 中 | ★ **我们选这个** ★ |
| 用户手动指定 | 低 | 那就不是自动恢复了 |

**为什么"有副作用才拍"是对的**：

```
只读调用不会改变任何东西 → 拍了也没用
被拒绝的调用不会执行   → 更没必要拍
   ↓
只有「确定要做、且会改状态」的调用才值得付这个代价
```

**这也解释了 `#runGuarded` 里那个顺序**：

```
① 守卫裁决     ← 最便宜，且能挡掉一部分
② 拍检查点     ← 只有通过了①、且会改状态才付这个代价
③ 真正执行
④ 记入历史
```

**为什么不先拍再裁决？** 因为对**被拒绝**的调用拍快照是纯浪费 —— 它根本不会执行。

## L2 · 决策表

### 2.1 什么动作该标哪个等级

| 动作 | 等级 | 判断依据 |
|---|---|---|
| 读文件、列目录、搜索、读网页 | `none` | 不改变任何状态 |
| 写文件、改配置、建目录 | `reversible` | 旧内容还在（检查点 / git / 备份里） |
| 删文件（无回收站、无 git） | `irreversible` | 内容本身没了 |
| 删文件（工作目录是 git 仓库） | `reversible` | ★ 还能从 git 取回 ★ |
| 发消息、发邮件、发帖 | `irreversible` | 收不回来 |
| `git commit` / `git push` | `irreversible` | 历史改了，别人可能已经拉走 |
| 调用付费 API | `irreversible` | 钱花了 |
| 写数据库（有事务） | `reversible` | 能 rollback |
| 写数据库（无事务、无备份） | `irreversible` | —— |

**⚠️ 注意表里的两个"删文件"**：

> **同一个动作，等级不同** —— 取决于**它跑在什么 harness 里**。

**这就是那条主张的落地**：

> **"不可逆"不是任务的客观属性，而是「动作 × harness 能力」的联合属性。**

**实践含义**：如果你想让一个危险工具变安全，**不是改那个工具，而是给 harness 加能力**
（加检查点、加 git、加回收站）。**这是"harness 干预"最有说服力的形态。**

### 2.2 该注册哪些守卫

| 场景 | 该注册的守卫 | 参数建议 |
|---|---|---|
| 通用 agent | `loopGuard` + `quotaGuard` | 阈值 3、配额按预算定 |
| 能改文件 | 再加 `pathGuard('path')` | —— |
| 有不可逆工具 | 再加 `irreversibleGuard` | 必须配 `approver` |
| 无人值守 | `irreversibleGuard` + `denyAllApprover` | 危险动作一律拒绝 |
| 演示 / 测试 | `irreversibleGuard` + `allowListApprover([...])` | 按名字自动批准 |

**注册顺序不影响裁决**（因为单调性），但**影响可读性** —— 建议按"从粗到细"排。

### 2.3 阈值怎么定

| 参数 | 默认 | 怎么定 |
|---|---|---|
| `loopGuard` 阈值 | **3** | 太小会误伤（正常的"重试一次"会被拦）；太大浪费步数 |
| `quotaGuard` 上限 | 无默认 | 按 token 预算反推：每次调用平均消耗 × 次数 |
| 检查点频率 | 每个有副作用的调用 | 如果文件很大，改成"每步一次" |

**关于循环阈值的取舍**：

```
阈值 2：试一次，失败，再试一次 → 被拦
        ★ 但"确认性重试"是正常策略 ★ → 误伤

阈值 3：试三次才拦
        ★ 3 次相同调用几乎不可能是正常策略 ★ → 合适
```

### 2.4 快照粒度怎么选

| 粒度 | 空间代价 | 回滚精度 |
|---|---|---|
| 每个有副作用的调用 | 高 | ★ 最细 ★ |
| 每步一次 | 中 | 中等 |
| 每个 turn 一次 | 低 | 只能整轮重来 |

**建议**：**从"每个有副作用的调用"开始** —— 因为教学项目的工作目录很小。
**如果目录变大（超过几十 MB），改成"每步一次"。**

### 2.5 什么时候不该用守卫

| 情况 | 为什么不该用 |
|---|---|
| 只是想让模型少犯错 | ★ 那是 A 类问题，**反馈注入**（第 1、2 步）比拦截更好 ★ |
| 想限制成本 | 用 `maxSteps`（第 8 步）+ `quotaGuard`，不要用守卫拦具体工具 |
| 工具本身已经安全 | 加了只是噪音（比如给 `read_file` 加 `irreversibleGuard`） |

**第一行最重要**：

> **守卫不是"更严的错误处理"。** 它只解决**事后无法挽回**的那一类。
> 对 A 类失败，**打断模型自己的纠错节奏反而有害** —— 这条是第 16 步演化实验要验证的假设之一。

### 2.6 三类失败 → 四类机制（这张表来自 `error-taxonomy.md`）

| 失败类别 | 需要的机制 | 本质 | 本课程对应 |
|---|---|---|---|
| **A** | 反馈注入 | 把失败原因说清楚，让模型自己改 | 第 1 步 `parseError`、第 2 步 `validateArgs` |
| **B** | **检查点 + 回滚** | 能回到之前的状态 | ★ **本步的 `checkpoint.ts`** ★ |
| **C** | **事前拦截** | 在发生**之前**拦住 | ★ **本步的 `guard.ts`** ★ |
| **A/B/C 的判别** | 状态差异检测 | 判断"这次失败属于哪类" | 第 7 步日志 + 第 15 步诊断 |

**注意最后一行**：**要知道一个失败属于哪类，你必须能对比"失败前后的状态"。**

而"能对比状态"的前提是：**你记录了状态**。
这就是第 7 步会话日志存在的另一个理由 —— **它不只是"给模型看的历史"，它还是回滚和归因的依据。**
